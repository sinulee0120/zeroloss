# 01. 개요

## 프로젝트 이름
**ZeroLoss**: 사람이 들어가지 않고 원격으로 운영하는 **검증 자동화 플랫폼**. IPTV 스트리밍 품질 검증이 **첫 번째 모듈**이다.
- 이 작업은 IPTV만을 위한 것이 아니라 **디지털 노마드(해외에서도 시험을 지시하고 결과를 받는 것)를 위한 사전 작업**이다(`00-vision.md`). 모든 설계는 이 목표를 막지 않는 방향으로 한다.

## 개발 방향
- **공유기를 좋아하는 개인이 자기 시험을 편하게 하려고 만드는 도구**다. 판매하지 않는다. 비공개 저장소에서 개발하고, 공개한다면 누구나 쓰게 전체 공개한다.
- Python(PC)과 Android 앱을 먼저 만들고, iPad 앱은 2차에 추가한다.
- **관심 확장 방향(개인 목표):** 공유기뿐 아니라 태블릿·전자장비 검증 자동화, 무선 시험, 스트레스로 결함(손실·행·재부팅·오동작)을 유발해 한계를 찾는 시험. 쉴드룸은 장기 희망(공간·비용 때문에 당장은 아님) → 무선 스트레스는 2차 모듈로 설계.
- 나중에 무료 배포할 수 있도록, 제품에 넣는 라이브러리와 도구는 **배포에 제약이 없는 라이선스**로 고른다(D12, D15).

## 목적
개발 중인 공유기(DUT, Device Under Test)의 유선/무선 IPTV 스트리밍 품질을 **개발 초기에 자동으로 검증**한다.

### 해결하려는 문제
- 공유기 SDK 초기 버전에는 IGMP(Snooping/Proxy), M2U(Multicast-to-Unicast) 등 IPTV 관련 기능이 없거나 불완전한 경우가 많다.
- 기능 유무에 따라 WAN→LAN, WAN→WLAN 경로의 품질을 비교/확인할 방법이 없다.
- 통신사마다 IPTV 전송 방식(RTP 사용 여부, 패킷 형식, 화질)이 달라 사전 검증이 어렵다.
- 결과적으로 개발 후반에 품질 문제가 드러나 **양산 일정이 지연**된다.

### 통과 기준 (최종 목표 시나리오)
- 태블릿 **최대 3대**가 UHD 채널을 동시에 무선 수신(채널은 태블릿마다 **같아도 되고 달라도 된다**)
- 채널당 30~40 Mbps, **총 최대 120 Mbps**
- **100시간 연속 무손실(ZeroLoss)**이면 통과
- 가장 어려운 조합: **무선 3대가 서로 다른 UHD 채널** 수신. 현재 통신사들이 공유기 1대에서 유무선 합쳐 최대 3대 수신을 요구한다.

### 가장 중요한 표시값
- **Jitter**와 **Packet Loss** 두 가지. 모든 화면(실시간 대시보드, 요약, 보고서)에서 가장 크고 먼저 보이게 표시한다. 나머지 지표는 보조로 표시한다.

### 목표
- 개발 초기부터 통신사별 전송 방식을 재현해 품질을 사전 검증한다.
- 품질 문제 발생 시 **수신단 1차 분석 결과**(원인 후보 분류)를 자동으로 제공한다.
- 10초 ~ 100시간까지 테스트 길이와 관계없이 송수신 품질을 **명확한 수치와 판정(PASS/FAIL)**으로 보여 준다.

## 설계 원칙 (변경 금지)
1. **역할 분리:** Controller는 명령과 판정만 한다. 영상 데이터는 Controller를 거치지 않고 `송신 → DUT → 수신`으로만 흐른다.
2. **판정은 Controller가 직접 계산:** Agent나 태블릿의 자체 판정은 참고만 하고 게이트로 쓰지 않는다.
3. **고정 판정 기준:** 손실 0%, 순번 오류 0, 지터 150 ms 이하, 최소 1,000 패킷, 최소 100 kbps. 불합격을 합격으로 만들기 위해 기준을 내리지 않는다.
4. **조용히 틀린 합격 금지:** 수신 0개, PAT 없음 등 "측정은 됐지만 실제로는 안 나오는" 상태는 FAIL이다.
5. **도구는 DUT에 로그인하지 않는다 — 명시적으로 켠 DUT 모듈만 예외:** 1차(IPTV)는 공유기 설정을 바꾸지 않는다(필요한 설정은 공장 설정 그대로, 07 3 B 방식). 2차 DUT 모듈은 켰을 때 **읽기 전용**(로그·상태)이고, 공유기 설정은 어떤 모듈도 바꾸지 않는다(2026-10-02) — 처리량 시험은 측정 PC의 NIC 설정만 바꾼다. 규칙은 12 4-2 "DUT 접근 규칙" 한 곳.
6. **레이어·포트 분리 (`12-architecture.md`):** ZeroLoss는 IPTV 전용이 아니라 **Controller–Agent 오케스트레이션 플랫폼 + 시험 모듈** 구조다(IPTV가 1차 모듈, throughput 등은 2차 모듈). **포트 역할 분리:** 운영(시험 제어·heartbeat·데이터)은 **TCP 10992** HTTP/REST(JSON), 설치·업데이트 파일 전달은 **TCP 10991**(항상 살아 있는 별도 배포 서비스). 장비 자동 발견은 설정 단계에서만 UDP 10992를 쓰고 시험 중에는 멈춘다. SSH는 **Linux Agent 최초 설치에만** 쓴다.
7. **증거가 남고 재현 가능:** 회차마다 판정 JSON, 1초 단위 원본 기록, 5분 단위 품질 표, 재생 화면 PNG를 남긴다.
8. **안전장치:** 시험 PC 네트워크 설정을 바꿨다면 원복 확인 전까지 다음 단계로 가지 않고, 확인 실패 시 즉시 중단한다.
9. **정직한 결과:** 판정은 해당 build 기준이며, 시험하지 않은 항목은 `NOT RUN`으로 표시한다.

## 사용자
- **주 사용자: 나(검증 담당자).** 반복 시험을 자동으로 돌리고, 결과와 원인 분석을 한눈에 보는 것이 목적이다.
- 필요하면 검증 경험이 없는 사람에게도 맡길 수 있도록, 네트워크 지식 없이 화면 안내만 따라 시험을 시작하고 결과를 이해할 수 있게 만든다.
  - 목표: 입력 15분 이내로 시험 시작
  - 용어 대신 쉬운 설명, 자동 발견 후 고르기만(마법사 최소화, F14), 결과는 색상(정상/주의/실패)과 한 줄 요약
- 사람이 **조작**하고 **모니터·상태를 보는** 화면은 모두 **Controller**에 있다. 수신 PC의 모니터 창과 태블릿 앱 화면은 현장 확인용 **보기 전용**이다.

## 시스템 구성

```
                        제어 (TCP 10992, HTTP/JSON)
        ┌─────────────────────────────┬──────────────────────────────┐
        │                             │                              │
[Controller PC] ──제어──> [송신 Agent (A)]                   [수신 Agent (B)] ──USB(adb)── [태블릿 1~3]
 (Windows)                (Linux/Windows)                     (Linux/Windows)
                              │ 영상 (UDP 5004)                     ▲ 영상                 ▲ 영상
                              ▼                                     │ (LAN)               │ (WLAN)
                           ──WAN── [DUT 공유기] ──────────────────────┴──────────────────────┘
```

| 구성 요소 | 역할 | 현재 준비된 장비 |
|-----------|------|------------------|
| Controller PC | GUI, 설정 검증, Agent 지시, 실시간 수집·표시, **판정**, 장기 기록, 보고서 | Windows 1대 |
| 송신 Agent (A) | 최대 3채널 송출(멀티캐스트). 시험 연동 또는 상시 방송(F18), 전송 방식 선택 | Linux 1대 |
| 수신 Agent (B) | 유선 또는 무선으로 수신·계측·재생, 채널 전환, 태블릿 조작·데이터 중계(adb) | Linux 1대 |
| 태블릿 1~3대 | 측정 앱으로 WLAN 수신·재생, 품질 계측, 화면 캡처 | Android 3대 |
| DUT 공유기 | 검증 대상. NAT / Bridge 모드. 설정은 사람이 함 | - |

### 장비 구성 규칙
- 지원 OS: Controller는 Windows. 송신·수신 Agent는 **Windows와 Linux 모두** 지원한다.
- 최소 구성(장비가 부족할 때): **Controller와 송신 Agent를 한 대(Windows)**에서 실행할 수 있어야 한다.
  - 이 경우에도 두 역할은 별도 프로세스로 분리하고, 제어는 동일하게 HTTP(10992)로 한다.
  - **네트워크 카드 2개 필요:** 송신은 DUT **WAN**, Controller는 DUT **LAN**에 연결돼야 하므로, 이 PC는 NIC 2개(WAN용, LAN용)를 쓴다. 송출은 WAN 쪽 NIC로만 나가도록 지정한다.
  - 송출 성능에 영향이 없는지 사전 점검 항목에 포함한다(CPU/송출 속도 편차).
  - 저사양 구성에서는 **사전 준비 파일 모드**를 기본으로 권장한다.
- 송출 채널은 최대 3개.
- 시험은 **두 종류이고 서로 별개**다.
  - **태블릿 시험:** 태블릿 1~3대(1대, 2대도 가능). 채널은 태블릿마다 **같아도 되고 달라도 된다.** 수신 PC는 태블릿 제어·데이터 중계(USB/adb)를 하고, **원하면 같은 시험에서 자기도 받는다**(2026-10-23 사용자 "수신기 pc 한대, 태블릿 두대, 총 3대고 태블릿 중 한대는 다른 영화로": PC 1대 + 태블릿 1~3대, 채널마다 다른 영화 가능). 받지 않게 두면 예전처럼 중계만.
  - **PC 수신 시험:** 수신 PC **1대**가 유선 또는 무선으로 받아 계측하고, PC 화면에서도 재생해 확인한다.
- PC 수신 결과는 태블릿 결과와 **비교 검증용**이다. 수신 장비가 달라도 같은 결과가 나오는지 보고, 문제가 **공유기(DUT) 쪽인지 수신 장비 쪽인지** 구분한다. Controller는 서로 다른 회차의 결과를 나란히 비교하는 화면을 제공한다.
- 네트워크 설정은 **IP 주소만 입력하면 동작**해야 한다. VLAN 등 별도 설정은 하지 않으며, 공유기(DUT)는 있는 그대로 사용한다.
- 태블릿 데이터 경로: 태블릿은 영상만 WLAN(DUT)으로 받고, **품질 데이터와 화면 캡처는 USB(adb)로 수신 Agent를 거쳐 Controller에 전달**한다. 보고 트래픽이 DUT 무선 구간을 지나지 않으므로 측정이 오염되지 않는다.

## 핵심 기능
1. **송출:** 송신 Agent가 **최대 3채널**(서로 다른 영상)을 24시간 연속 송출. HD/UHD 화질과 전송 방식을 선택.
   - **전송 방식:** 기본값은 **RTP / MPEG-TS over UDP**. 검증용으로 **MPEG-TS over UDP(RTP 없음)** 등 다른 방식도 선택할 수 있다.
     - RTP가 없으면 RTP 순번·타임스탬프를 쓸 수 없으므로, 손실은 TS 연속성 카운터(CC)로, 지터는 도착 간격으로 계산한다. 보고서에 계측 방식 차이를 표시한다.
   - **실시간 인코딩 모드:** 송출하면서 인코딩해 화질·비트레이트를 조절한다. 송신 PC 성능이 충분할 때 쓴다.
   - **사전 준비 파일 모드:** 영상을 미리 목표 사양으로 변환해 두고, 송출 때는 **재인코딩 없이** 무한 반복한다. 송신 부하가 거의 없어 송신 쪽 원인을 배제하는 데 유리하고, **저사양 장비에서는 이 모드를 쓴다.**
   - 입력: 시중 mp4 파일 대부분(H.264, H.265/HEVC 등). IPTV 전송 형식(MPEG-TS)에 바로 담을 수 없는 코덱(예: AV1, VP9)은 사전 준비 단계에서 변환한다.
2. **수신·재생:** 수신 PC와 태블릿이 실제로 영상과 음성을 재생(PC: VLC 기본·mpv 옵션, 태블릿: 측정 앱). 채널 전환 가능. 계측은 재생과 분리되어, 플레이어 상태가 계측값에 영향을 주지 않는다.
3. **품질 계측:** 각 수신 단말이 1초 단위로 계측.
   - 네트워크(**핵심: Jitter, Packet Loss**): 수신 패킷 수, 손실, 순번 오류(RTP), 비트레이트, MDI(DF:MLR)
   - 수신 장비 자체 드롭: OS 수신 버퍼 넘침 개수. 네트워크 손실과 **따로** 집계해 수신 장비 탓인지 구분
   - 스트림: TS 188바이트 동기, PAT 존재, TS 연속성 카운터 오류
   - 재생: 화면 출력 여부(캡처), 끊김
   - 채널 전환: 전환 요청부터 첫 패킷/첫 PAT까지 걸린 시간
4. **실시간 모니터링과 5분 평가 (통신사 방식):**
   - 수신기는 지표를 **매초 정리**하고 **5분마다 요약을 Controller로 보낸다.** 통신사 셋톱박스가 5분마다 서버로 품질을 보내는 방식과 같다. (상세: `05-standards.md` 5장)
   - 실시간 화면에는 1초마다 Jitter와 Packet Loss를 표시하고, 기준 위반 시 즉시 강조한다.
   - 5분 결과는 **초록/노랑/빨강** 칸으로 표시해 한눈에 보이게 한다. 100시간이면 1,200칸.
   - **결과는 웹 브라우저에서도 볼 수 있다.** Controller가 결과 조회용 웹 페이지를 제공해, 다른 PC나 휴대폰으로도 확인한다. (조작 화면은 PySide6, 조회는 웹)
5. **1차 원인 분석:** 문제가 생기면 수신단 데이터 패턴으로 원인 후보를 자동 분류해 보고서에 적는다. (상세 규칙: `03-features.md`)
   - 예: 처음부터 0개 → 그룹 가입 경로 문제(IGMP Snooping/Proxy 미동작)
   - 예: 가입 후 수 분 뒤 끊김 → 그룹 유지(IGMP Query/멤버십 타임아웃) 문제 의심
   - 예: 유선은 정상이고 무선만 손실 → 무선 멀티캐스트 전송(M2U 미동작 등) 의심
   - 예: 모든 단말이 같은 시각에 손실 → 송신측 또는 DUT 공통 구간 의심
   - 예: 같은 조건에서 PC 수신은 정상, 태블릿만 손실 → 수신 장비(태블릿) 문제 의심
   - 예: 수신 장비 자체 드롭(버퍼 넘침)이 있음 → 공유기가 아니라 수신 장비 처리 성능 문제
6. **장기 기록·보고서:** 10초 ~ 100시간 시험 결과 저장. 1초 원본 기록, 5분 단위 품질 표, 판정 JSON, 화면 PNG, HTML 보고서.
7. **중간에 멈춰도 보고서:** 정해진 시간 전에 멈추면(사용자 중단, 자동 중단, 비정상 종료) 그때까지 측정한 자료로 보고서를 만든다. 중단된 시험은 PASS가 아니라 **INCOMPLETE**로 표시한다. (상세: `03-features.md` F10)

| 축 | 값 |
|----|----|

| DUT 모드 | NAT, Bridge |

- IGMP가 없는 SDK에서는 "뚫기(dummy)" 방식(LAN→WAN 소량 UDP로 경로를 먼저 연 뒤 받기)을 선택 옵션으로 제공한다. **(2026-09-25 사용자) 공유기 SDK 버전에는 M2U·IGMP 프록시·IGMP 스누핑이 하나도 없다 → WAN 멀티캐스트가 LAN으로 들어오지 않으므로 SDK 공유기의 IPTV 시험은 이 방식(사용자 용어 "프라임 방식", 설정 S-18)으로 해야 WAN에서 들어온다. 상용 펌웨어는 보통 IGMP·M2U가 켜져 있으므로 시작 전에 구분한다(S-18 Auto, iptv 4.5).** 자세한 동작은 20장 GAP-57(정할 것). 이 방식으로 얻은 결과는 보고서에 **통신사 실제 경로와 다른 방식**임을 표시한다.
