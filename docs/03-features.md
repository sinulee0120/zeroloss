# 03. 기능 상세

> 기능마다 동작, 입력, 출력, 예외 처리, 완료 기준을 적는다. (작성 중: 확정된 기능부터 채움)

## F10. 시험 중단과 부분 보고서

### 목적
시험은 정해진 시간(10초 ~ 100시간)을 다 채우기 전에 멈출 수 있다. **어떤 이유로 멈추든, 멈춘 시점까지 측정한 자료로 보고서를 반드시 만든다.**

### 중단 원인
| 종류 | 예 | 동작 |
|------|----|------|
| 사용자 중단 | Controller의 **Stop** 버튼 | 즉시 정상 종료 절차 → 보고서 생성 |
| 자동 중단 (안전) | 시험 PC 네트워크 설정 원복 확인 실패, 디스크 공간 부족, 송신 중단 후 복구 실패 | 즉시 종료 절차 → 보고서 생성, 중단 원인 기록 |
| 비정상 종료 | Controller 프로그램 강제 종료, PC 전원 꺼짐, 오류로 인한 종료 | 다음 실행 시 **미완료 시험을 자동 감지** → 저장된 자료로 보고서 생성 |
| 장비 연결 끊김·사망 | Agent 또는 태블릿 응답 없음 | F11의 장애 처리 정책을 따른다(기본: 전체 정지 후 보고서 생성) |

### 동작 (정상 종료 절차)
1. 모든 Agent와 태블릿에 **정지** 명령
2. 각 수신기가 현재 진행 중이던 **마지막 5분 구간을 부분 구간으로 마감**해 보낸다 (예: 2분 37초짜리 구간)
3. 1초 원본 기록 회수
4. 송신 중지, 시험 PC 설정 원복 확인
5. 보고서 생성

### 자료 보존 (비정상 종료 대비)
- Controller는 받은 5분 요약과 1초 핵심값을 **받는 즉시 디스크에 저장**한다. 메모리에만 두지 않는다.
- 수신기(Agent, 태블릿 앱)도 1초 기록과 5분 요약을 **자기 디스크에 계속 저장**한다. Controller가 죽어도 자료는 수신기에 남는다.
- 시험 상태 파일(`run-state.json`)에 시험 ID, 시작 시각, 계획 시간, 참여 장비, 마지막 저장 시각을 계속 갱신한다.
- 다음 실행 시 `run-state.json`이 "진행 중"으로 남아 있으면:
  1. "이전 시험이 비정상 종료되었습니다"를 표시
  2. 연결 가능한 수신기에서 남은 자료를 회수
  3. **복구 보고서**를 만든다(복구되었음을 표시)

### 판정 규칙 (정직한 결과)
| 상황 | 판정 |
|------|------|
| 계획 시간을 채웠고 빨강·보라·회색 없음 (노랑 허용) | **PASS** |
| 한 칸이라도 빨강 (중단 여부와 무관) | **FAIL** |
| 계획 시간 전에 멈췄거나, 회색·보라가 있고 빨강은 없음 | **INCOMPLETE** (PASS 아님) |
| 자료가 너무 적음 (최소 패킷·비트레이트 미달) | **FAIL** |

- 판정 기준의 원본은 `05-standards.md` 5.3~5.4다. 둘이 다르면 05를 따른다.

- 중단된 시험은 **절대 PASS로 표시하지 않는다.** "여기까지는 문제 없었다"는 사실만 보여준다.

### 보고서에 추가로 적을 것
- 계획 시간 / 실제 진행 시간 / 진행률(%)
- 중단 원인과 중단 시각, 중단을 요청한 주체(사용자/자동/비정상)
- 마지막 부분 구간의 실제 길이
- 장비별 자료 누락 구간(회색)과 이유
- 복구 보고서 여부

## F11. 상태 감시(Heartbeat)와 장애 복구

### 목적
Controller, Agent, 태블릿 앱 중 하나라도 **예상치 못하게 죽거나 연결이 끊기면** 바로 알아채고, 전체를 안전하게 멈춘 뒤 문제 상황을 알려준다. 사용자는 **한 번의 조작으로 전체를 리셋**하고 다시 시작할 수 있어야 한다.

### 감시 구조
| 감시하는 쪽 | 감시 대상 | 방법 | 주기 |
|-------------|-----------|------|------|
| Controller | 각 Agent | TCP 10992 `/v1/heartbeat` (시험 ID, 순번 포함) | 1초 |
| Agent | Controller | Controller의 heartbeat 요청이 계속 오는지 확인 | 1초 |
| 수신 Agent | 태블릿 앱 | USB(adb) 경로로 앱 heartbeat | 1초 |
| 태블릿 앱 | 수신 Agent | Agent heartbeat 요청이 계속 오는지 확인 | 1초 |
| OS | Agent 프로세스 | Windows 서비스 복구 / systemd `Restart=on-failure` | 상시 |

- heartbeat 응답에는 상태(IDLE / RUNNING 등), 시험 ID, 송수신 동작 여부, 마지막 저장 시각, CPU·디스크 여유를 담는다.
- heartbeat는 Controller가 먼저 여는 제어 연결(NAT 통과) 또는 USB로 다니고, 수백 바이트 이하로 최소화한다(`07-network.md` 6~7장).

### 판단 기준 (기본값, 설정 가능)
| 상태 | 조건 | 화면 |
|------|------|------|
| 정상 | 응답 정상 | 초록 |
| 의심 | 연속 3회(3초) 응답 없음 | 노랑 + 경고. 시험은 계속 |
| **사망** | 연속 10회(10초) 응답 없음, 또는 프로세스 재시작 감지 | 빨강 → **장애 처리 시작** |

- 짧은 네트워크 흔들림은 "의심"으로만 표시해 불필요한 중단을 막는다.
- Agent가 재시작된 경우(순번·기동 시각이 바뀜)는 시간과 상관없이 **사망으로 처리**한다. 그 사이 측정이 끊겼기 때문이다.

### 장애 처리 정책 (시험 시작 전에 선택, 기본: ①)
| 정책 | 동작 |
|------|------|
| **① 전체 정지 후 보고 (기본)** | 모든 장비의 송수신을 멈추고, 그때까지 자료로 보고서 생성(F10), 전체를 대기(IDLE) 상태로 돌린 뒤 **장애 안내 화면**을 띄운다 |
| ② 자동 복원 시도 | 죽은 장비가 복원 대기 시간(기본 60초) 안에 돌아오면 다시 연결해 시험을 이어간다. 끊긴 구간은 회색. **회색 구간이 있으면 최종 판정은 PASS가 될 수 없다**(INCOMPLETE). 시간 안에 안 돌아오면 ①로 처리 |
| ③ 전체 종료 | 모든 장비의 송수신과 재생을 멈추고 ZeroLoss 시험 프로세스를 모두 끈다. 보고서는 만든다. 사용자가 장비를 정리한 뒤 처음부터 다시 시작 |

### 누가 죽었을 때 어떻게 되는가
| 죽은 것 | 다른 장비의 동작 |
|---------|------------------|
| **Controller** | 각 Agent가 10초 동안 heartbeat를 못 받으면 **스스로 안전 정지**: 송신 Agent는 송출 중단(주인 없는 영상 트래픽이 DUT로 계속 흘러가지 않게), 수신 Agent와 태블릿은 측정·재생을 멈추고 자료를 저장. Controller가 다시 켜지면 미완료 시험을 감지해 복구 보고서(F10)를 만들고 장애 안내 화면을 띄운다 |
| **Controller가 재시작됨** (블루스크린·재부팅 등) | Agent는 10초 무응답으로 이미 스스로 정지한다. 10초 안에 돌아와도 Controller boot_id가 바뀌었으므로 Agent가 **옛 시험을 즉시 정지**한다(02-data 3장). 새로 켜진 Controller는 run-state에 있던 장비에 먼저 연결해 **남은 시험이 없는지 확인·정지·자료 회수**한 뒤 복구 보고서를 만든다(CTL-003). 켜지지 않는 경우 사람이 끄는 방법: CTL-008 |
| **송신 Agent** | Controller가 사망 판단 → 정책대로 처리. 수신 쪽 손실은 "송신 중단" 원인으로 표시하고 DUT 탓으로 판정하지 않는다 |
| **수신 Agent** | Controller가 사망 판단 → 정책대로 처리. 이 Agent에 연결된 태블릿 앱은 Agent heartbeat가 끊기면 스스로 측정·재생을 멈추고 자료를 저장 |
| **태블릿 앱** | 수신 Agent가 감지해 Controller에 보고 → 정책대로 처리 |
| **전원 꺼짐·재부팅** | 재시작된 Agent는 **이전 시험을 자동으로 이어 하지 않는다.** "이전 시험 X가 중단됨" 상태로 올라와 대기하고, Controller의 지시를 기다린다 |

### 송신 앱이 멈추거나(응답 없음) 꺼진 경우
멈춤(hang)과 꺼짐(crash)을 **구분해서** 잡는다. 멈춘 프로그램은 살아 있는 것처럼 보여 가장 위험하다.

| 상황 | 감지 | 자동 대응 | 판정 |
|------|------|-----------|------|
| **송출 프로세스(tsp/ffmpeg) 꺼짐** | 프로세스 감시(종료 이벤트) | 1회 자동 재시작 → 수신은 새 스트림 구간으로 이어 받음(SSRC 변경 = 새 구간, 손실로 세지 않음) → 또 꺼지면 장애 정책 적용 (SND-005) | 끊긴 구간 보라 |
| **송출 프로세스 멈춤**(살아 있지만 안 보냄) | 1초 이상 보낸 것 0 (SND-016) | 3초 계속되면 **강제 종료 후 재시작**(꺼짐과 같은 처리) | 보라 |
| **송신 Agent 서비스 꺼짐** | Controller heartbeat 무응답 + OS가 서비스 재시작 | 재시작된 Agent는 이전 시험을 이어 하지 않음. Agent가 띄운 송출 프로세스는 Job Object/프로세스 그룹으로 **함께 종료**돼 주인 없는 송출이 남지 않음 → 장애 정책(F11) | 보라/회색 |
| **송신 Agent 서비스 멈춤**(응답 없음) | ① Controller heartbeat 10초 무응답 ② **같은 PC의 Deployer(L0)가 Agent를 감시**: Agent 내부 감시 신호가 10초 끊기면 멈춤으로 판단 ③ Linux는 systemd 감시 기능(WatchdogSec)도 사용 | Deployer가 Agent를 **강제 종료 → 재시작**(자식 송출 프로세스도 함께 종료), 사건 기록 → 장애 정책(F11) | 보라/회색 |
| **송신 PC 전체 멈춤·전원 꺼짐** | heartbeat 무응답 + Deployer도 무응답 | 장애 정책(F11) ① 전체 정지·보고서. 사람 할 일(F22): "Sender PC not responding — power cycle"(3차: 원격 전원) | 보라/회색 |
| Agent Desktop(상태 창)만 멈춤 | Service가 Desktop 응답 확인 | Desktop만 재시작. **송출·계측에는 영향 없음** | 영향 없음 |

- 장애 정책 ②(자동 복원)를 고른 경우: 송신이 60초 안에 다시 정상 송출하면 수신은 계속 이어 받고, 끊긴 구간만 보라로 남는다(최종 판정은 PASS 불가 → INCOMPLETE).
- 모든 경우 송신 상태 창·Controller Problems·보고서에 **꺼짐/멈춤 구분, 시각, 재시작 횟수, 추정 원인**(CPU·메모리·디스크 기록)을 남긴다.

### 자식 프로세스 정리 (남는 프로세스 방지)
- Agent가 실행한 송출·재생 프로세스(tsp, ffmpeg, mpv, VLC)는 **Agent가 죽으면 함께 종료**되게 묶는다.
  - Windows: Job Object (Agent 종료 시 자식 자동 종료)
  - Linux: 프로세스 그룹 + 부모 사망 시 종료 신호
- Agent가 다시 켜질 때 ZeroLoss가 띄웠던 프로세스가 남아 있으면 정리하고 기록한다.

### 장애 안내 화면
- **무엇이 언제 죽었는지:** 장비 이름, 마지막 정상 응답 시각, 추정 원인(연결 끊김 / 프로세스 재시작 / 응답 없음)
- **지금 각 장비 상태:** 정지 확인됨 / 응답 없음
- **자료 상태:** 보고서 생성 여부, 자료 누락 구간
- **다음에 할 일 버튼:**
  - **[Reset All]**: 전체 리셋 (아래)
  - **[Restart Agent]**: 응답하는 Agent의 서비스 재시작
  - **[Shut Down All]**: 전체 종료(③)
  - 응답이 없는 장비는 **직접 할 일**을 안내 (예: "송신 PC에서 서비스 재시작" 명령, 또는 PC 재부팅)

### 전체 리셋 (Reset All)
1. 모든 Agent와 태블릿에 리셋 명령
2. 각 장비: 송출·재생 중지 → 멀티캐스트 그룹 탈퇴 → 자식 프로세스 종료 → **동반 작업 멈춤·정리(공유기 쪽 포함)** → 시험 PC 네트워크 설정 원복 → 시험 상태 초기화
3. 각 장비가 **깨끗한 상태 점검** 결과를 보낸다: 남은 ZeroLoss 프로세스 없음, 포트 비어 있음, 설정 원복 확인
4. 모든 장비가 IDLE(초록)이 되면 "다시 시작 가능" 표시
5. 응답 없는 장비가 있으면 리셋 완료로 표시하지 않고, 그 장비에 대한 직접 조치 안내를 보여준다

### 구현 규칙 (2026-09-25, 20장 GAP-58)
- **Reset All 대상 = 등록된 모든 장비**(11-0). Controller가 세대 번호를 올린 뒤 `POST /v1/reset`(02 4)을 보낸다 → 모두 `clean`이면 IDLE, 아니면 FAULT 그대로 + 장비별 `fix`(02 2-8). 사전 점검이 실패한 IDLE에서도 누를 수 있다(11-ui 1.10 표). CLI는 `--yes`.
- **노드의 깨끗한 상태 점검:** 상태 IDLE, 이 노드가 띄운 시험 프로그램 기록 없음(크래시가 남긴 것은 정지하고 수를 적음, 노드 자신의 도우미는 제외), 모듈 `clean_check()`가 빈 목록(IPTV: 송신·수신·영상 만들기·멀티캐스트 시험 없음), 네트워크 설정(지금은 ZeroLoss가 바꾸는 것 없음 — NIC 임시 IP가 생기면 원복 확인을 여기에).
- **[Restart Agent]** = 그 PC Deployer의 `node restart`(새 boot_id로 답할 때까지). 장비 줄마다 버튼.
- **[Shut Down All]** = 모든 PC의 **노드 서비스만 정지, Deployer(10991)는 켜둠**(2026-09-25 사용자 결정) — Deployer는 표시 파일로 감시 재시작을 멈추고, `zeroloss nodes start`로 다시 켠다. PC 전원은 건드리지 않는다. 확인을 묻는다(CLI `--yes`).
- 버튼은 한 번에 하나만 보내고 답이 올 때까지 셋 다 회색(11-ui 1.10). 결과는 S6에 장비별로(깨끗 ✔ / 깨끗하지 않음 + 이유 / 답 없음 + 할 일).

### 상태 흐름
```
IDLE → PREPARING → RUNNING → STOPPING → REPORTING → IDLE
                      │
                      └─(장애)→ SAFE_STOP → REPORTING → FAULT(안내 화면) → RESETTING → IDLE
```
- 모든 명령에는 시험 ID와 세대 번호를 붙인다. 재시작된 장비가 **이전 시험의 명령을 잘못 실행하지 않게** 한다.

## F12. 수신기 화면 표시와 기록 파일

### 역할 분담
| 어디서 | 무엇을 | 주기 |
|--------|--------|------|
| **Controller (모든 모니터·상태 화면)** | 장비 상태, **수신기별 1초 값 목록**(최근 1,000줄), 5분 칸 평가, 상태창(F17), 장애 안내(F11) | 1초 값은 **heartbeat에 실어 매초**(추가 연결 없음), 5분 요약은 5분마다 |
| 수신기 자기 화면 (수신 PC의 Agent Desktop, 태블릿 앱) | 같은 1초 값 (현장 확인용, 보기 전용) | 매초 |

- **사용자가 보는 모니터·상태 화면은 모두 Controller에 있다.** 수신기 앞에 가지 않아도 Controller에서 모든 장비의 상태와 1초 값을 볼 수 있다.
- Controller 화면 구성: 장비별 탭 또는 나란히 보기(태블릿 1~3, PC). 각 장비 칸에 현재 Jitter·Packet Loss(크게), 1초 값 목록, 채널, 연결 상태.
- 재생 화면 확인: Controller에서 장비별 **[Snapshot]** 버튼 → 저해상도 캡처 1장을 가져와 보여준다(누를 때만, 트래픽 최소). 태블릿은 USB로 가져오므로 무선 구간을 쓰지 않는다.
- `Send quality reports`가 꺼져 있으면 Controller에는 상태(연결·수신 여부)만 보이고, 1초 값은 수신기 화면과 파일에만 있다(시험 후 회수).

### 품질 보고 전송 여부 (체크박스)
- 시험 시작 전 메인 화면의 체크박스: **`☑ Send quality reports to Controller`** (기본: 켜짐)
- **켜짐:** 수신기가 5분 요약을 Controller에 전달하고, Controller는 5분 칸(초록/노랑/빨강)을 실시간으로 채운다. heartbeat에 현재 Jitter·Packet Loss도 싣는다.
- **꺼짐:** 시험 중에는 품질 정보를 **보내지 않는다.** 시험 경로로 다니는 제어 트래픽을 최소로 줄이고 싶을 때 쓴다.
  - 수신기는 계측·화면 표시·파일 저장을 **그대로** 한다.
  - heartbeat는 장애 감시(F11)를 위해 계속하되, 상태만 담고 품질 값은 싣지 않는다.
  - Controller 화면의 5분 칸은 "Reports off"(회색 빗금)로 표시한다.
  - **시험이 끝나면** Controller가 수신기의 기록 파일을 회수해 5분 요약과 판정을 **그때 계산**하고 보고서를 만든다. 판정은 여전히 Controller가 직접 계산한다.
  - 비정상 종료로 파일을 회수하지 못한 수신기는 보고서에 "자료 미회수"로 표시하고, 다시 연결되면 회수한다.
- 이 설정값은 보고서에 기록한다.
- **목적: 품질 보고 자체가 품질에 영향을 주는지 비교 확인.** 같은 조건으로 켬/끔 두 번 시험한 뒤 Controller의 **회차 비교 화면**에서 나란히 비교한다.
  - 비교 항목: Jitter, Packet Loss, 5분 칸 색 분포, 수신 장비 자체 드롭, 제어 트래픽 양(bps)
  - 두 결과에 차이가 있으면 "품질 보고가 측정에 영향을 줌" 경고를 보고서에 적는다.

### 수신기 화면
- 1초마다 한 줄씩 추가: 시각, **Jitter(ms)**, **Packet Loss(개/누적)**, 수신 패킷 수, 비트레이트, 자체 드롭, 채널
- **화면에는 최근 1,000줄까지만** 보여준다. 넘치면 오래된 줄부터 화면에서만 지운다(파일에는 남음).
- 화면 갱신은 1초에 한 번으로 묶어서 한다. 화면 그리기가 계측과 재생에 영향을 주지 않게 한다(`05-standards.md` 4.2).
- 기준 위반 줄은 색으로 강조(빨강: 손실·지터 초과, 노랑: 주의).
- 수신 PC(Agent)는 영상 재생 창과 별도로 **작은 모니터 창**을 띄운다. 태블릿 앱은 영상 위나 옆에 접을 수 있는 패널로 표시한다.

### 기록 파일 (백그라운드, 전체 저장)
- **1초 값 전체**를 백그라운드에서 파일에 계속 저장한다. 화면 1,000줄 제한과 무관하다.
- 형식: 한 줄에 1초 기록 하나(JSON Lines). 줄 단위라 중간에 끊겨도 마지막 줄만 빼고 모두 읽을 수 있다.
- 저장 방식:
  - 1초마다 한 줄 쓰고 버퍼를 비운다(flush). 디스크 동기화(fsync)는 10초마다와 파일을 닫을 때 한다.
  - **1시간마다 새 파일**로 나눈다(100시간 = 100개). 파일 하나가 망가져도 피해가 1시간 이내다.
  - 파일 맨 앞에 시작 정보(시험 ID, 장비, 채널, 설정), 정상적으로 닫을 때 맨 끝에 종료 표시(종료 시각, 이유, 줄 수)를 쓴다.
- 5분 요약 파일도 수신기에 따로 저장한다(Controller 전달 실패 대비).

### 끝날 때 파일을 제대로 닫기
| 상황 | 동작 |
|------|------|
| 정상 종료 (Stop, 계획 시간 도달) | 마지막 줄 쓰기 → 종료 표시 → fsync → 닫기 |
| Controller·다른 PC와 **연결 끊김** | 수신과 저장은 **안전 정지 판단(F11) 시점까지 계속** → 종료 표시(이유: 연결 끊김) → 닫기 |
| 사용자가 창을 닫음 / OS 종료 신호 | 종료 신호를 받아 위 정상 종료 절차 수행 (Windows 서비스 중지·창 닫기, Linux SIGTERM, Android 앱 종료 콜백) |
| **강제 종료·전원 차단** (닫을 기회 없음) | 다음 실행 시 **마무리 안 된 파일을 자동 점검**: 마지막 불완전한 줄만 잘라내고 "비정상 종료로 복구됨" 표시를 붙여 닫는다. 잃는 자료는 최대 약 10초(마지막 fsync 이후) |

### 완료 기준
- [ ] 2시간 시험에서 수신기 화면은 항상 최근 1,000줄만, 파일에는 7,200줄 전부 저장
- [x] Stop 후 모든 파일에 종료 표시가 있고 정상적으로 열림(수신 세션 시험)
- [ ] Controller 연결을 끊음 → 수신기가 안전 정지까지 계속 저장 후 종료 표시와 함께 닫음
- [x] 수신 Agent 강제 종료 → 재실행 시 파일 자동 복구, 손실은 마지막 10초 이내 (2026-09-25, `tests/core/test_node_recovery.py`, 5분 요약도 노드 디스크에서 같은 seq로)

## F13. Start / Stop 버튼 (하나의 토글 버튼)

### 동작
Start와 Stop은 **같은 자리의 버튼 하나**다. 누르면 상태에 따라 글자와 색이 바뀐다. 화면 문구는 영어(D10).

| 시험 상태 | 버튼 표시 | 누를 수 있음 | 누르면 |
|-----------|-----------|--------------|--------|
| IDLE (대기) | **Start** (초록) | 예 (사전 점검 통과 시) | 시험 시작 → PREPARING |
| PREPARING (준비 중) | **Starting…** (회색) | 아니오 | - |
| PREPARING 중 영상 만들기(iptv 1-1-2) | **Cancel** | 예 | 만들기 멈춤·되돌림 → Start (USR-006) |
| RUNNING (시험 중) | **Stop** (빨강) | 예 | 확인 창 → 정지 → STOPPING |
| STOPPING / REPORTING / SAFE_STOP / RESETTING | **Stopping…** (회색) | 아니오 | - |
| 보고서 완료 | **Start** (초록) | 예 | 새 시험 |
| FAULT (장애) | **Start** (회색, 비활성) | 아니오 | 장애 안내 화면의 **Reset All** 후 다시 활성 |

### 규칙
- **Stop 확인 창:** 긴 시험을 실수로 멈추지 않게 확인을 받는다.
  - 예: "Stop the test? 12h 34m of 100h completed. A report will be created with data collected so far (result: INCOMPLETE)."
  - [Stop] / [Cancel]
- 사전 점검(장비 연결, 도구 버전, NAT 판별 등)이 통과하지 않으면 Start는 비활성이고, 버튼 옆에 이유를 한 줄로 보여준다.
- **연속 클릭 방지:** 누른 뒤 상태가 바뀔 때까지 버튼을 잠근다. Start를 두 번 눌러 시험이 두 번 시작되는 일이 없어야 한다.
- 버튼 상태는 **Controller의 실제 시험 상태**를 따른다. 화면만 바뀌고 실제 동작은 안 된 상태가 없게 한다(명령 실패 시 원래 상태로 되돌리고 오류 표시).
- 시험 중에는 버튼 옆에 경과 시간 / 계획 시간과 진행률을 표시한다.
- 계획 시간이 다 되면 자동으로 정지 절차를 밟고 버튼은 Stopping… → Start로 바뀐다.
- **Stop을 누르면 모든 것을 시험 전 상태로 원복한다.** 원복이 끝나야 버튼이 Start로 돌아온다.
  - **정리(원복 + 파일 마감 + 보고서 생성)가 전부 끝날 때까지 버튼은 Stopping…(비활성)으로 잠겨 있어 Start를 누를 수 없다.** 진행 중인 정리 단계를 버튼 옆에 표시한다(예: "Restoring sender NIC… 3/5").
  - 이 상태에서 버튼을 누르면 **아무 동작도 하지 않고 기다리라는 팝업**을 띄운다. 예: "Cleanup in progress (3/5: Restoring sender NIC). Please wait until it finishes." [OK]
  - 구현 참고: 완전히 비활성화된 버튼은 클릭 자체가 안 되어 팝업을 띄울 수 없으므로, 회색으로 보이되 클릭은 받아서 팝업만 띄우는 방식으로 만든다. Starting…, FAULT 상태도 같은 방식으로 이유를 팝업으로 알려준다.
  - 송출 중지, 재생기·태블릿 재생 중지, 멀티캐스트 그룹 탈퇴(IGMP Leave)
  - ZeroLoss가 띄운 프로세스(tsp, ffmpeg, mpv, VLC) 종료
  - **동반 작업**(패킷 캡처, 외부 로깅 트리거, 공유기 로그·공유기 쪽 프로그램) 멈춤·확인·정리(12-architecture 4-3)
  - 시험 때문에 바꾼 설정 원복: 방화벽 임시 허용 해제, 태블릿 Wi-Fi Lock·화면 켜짐 해제
  - 각 장비가 **원복 확인 결과**를 보낸다(깨끗한 상태 점검, F11 Reset All과 같은 점검)
  - 원복에 실패한 장비가 있으면 버튼은 Start로 돌아오되 **비활성**, 실패 항목과 조치 방법을 보여준다

### 완료 기준
- [ ] Start 클릭 → Starting… → Stop(빨강)으로 바뀜
- [ ] Stop 클릭 → 확인 창 → Stopping… → 원복·보고서 완료 후 Start
- [ ] Stop 후 모든 장비가 시험 전 상태(프로세스 없음, IP·DHCP·방화벽 원복, 그룹 탈퇴)로 돌아옴
- [ ] 확인 창에서 Cancel → 시험 계속, 버튼은 Stop 유지
- [ ] Start 빠르게 두 번 클릭 → 시험 1개만 시작
- [ ] 정리 중(Stopping…)에 버튼을 누르면 동작 없이 "기다리세요" 팝업만 뜸. 정리가 끝난 뒤에만 Start 동작
- [ ] 사전 점검 실패 시 Start 비활성 + 이유 표시
- [ ] 장애 발생 시 Start 비활성, Reset All 후 활성

## F14. 화면 구성 원칙: 설정은 최소한만 보이게

### 목적
설정 항목이 많아 보이면 사용자가 거부감을 느낀다. **기본값으로 바로 시험할 수 있게** 하고, 화면에는 꼭 골라야 하는 것만 보여준다.

### 원칙
1. **기본 화면에는 꼭 필요한 것만:** 한 화면에 사용자가 고를 항목은 **최대 3~5개**.
2. **나머지는 전부 기본값 + `☐ Advanced settings` 체크박스:** 체크박스를 켜면 그 아래에 고급 설정 항목이 펼쳐지고, 끄면 다시 숨는다(기본: 꺼짐). 체크박스를 꺼도 바꾼 값은 유지되며, 기본값에서 바꾼 항목 수를 옆에 표시한다(예: "Advanced settings (2 changed)"). [Reset to defaults] 버튼으로 한 번에 기본값 복귀.
3. **툴이 알아낼 수 있는 것은 최대한 다 알아낸다. 사용자는 고르기만 한다:** 입력칸 대신 **후보 목록 + 추천 표시**를 보여준다. 직접 입력은 툴이 도저히 알 수 없는 것(아래 '사용자 입력이 남는 것')만 받는다.
4. **한 번 정한 것은 다시 묻지 않는다:** 장비 구성, 채널 배정 등은 저장해 두고 다음 실행 때 그대로 쓴다. 바뀐 것이 있을 때만 알려준다.
5. **설정 창은 단계로 나누지 않는다(마법사 최소화):** 처음 한 번만 짧은 연결 확인 화면을 보여주고, 이후에는 메인 화면에서 바로 Start.
6. **문구는 짧게:** 항목마다 한 줄 설명. 전문 용어는 마우스를 올리면 설명(툴팁).
7. **입력·설정이 필요한 곳마다 도움말 툴팁(Help tip):** 입력칸이나 설정 항목 옆에 `ⓘ` 아이콘을 두고, 마우스를 올리거나 누르면 다음을 보여준다.
   - **무엇을 넣는지:** 한 문장 (예: "IP address of the sender PC connected to the router's WAN port.")
   - **예시 값:** (예: `10.0.0.2`)
   - **어디서 확인하는지:** (예: "Shown on the sender PC's ZeroLoss window as 'My IP'.")
   - **기본값과 바꾸면 생기는 일:** 고급 설정 항목만 (예: "Default 16. Lower values may be dropped by the router in NAT mode.")
   - 입력칸이 비어 있으면 회색 안내 글자(placeholder)로 예시 값을 보여준다.
   - 잘못 입력하면 입력칸 바로 아래에 **무엇이 틀렸고 어떻게 고치는지** 한 줄로 표시한다(예: "Not in the router WAN subnet 10.0.0.0/24.").

### 태블릿 Wi-Fi 자동 연결 (S-51)
- 사전 점검 "3. Network check"에서 태블릿 SSID가 S-51과 다르거나 연결이 없으면, Controller가 adb로 연결한다: `adb shell cmd wifi connect-network "<SSID>" <open|wpa2|wpa3> "<비밀번호>"` (Android 11 이상, 명령 형식은 P1 확인 ?).
- 최대 30초 기다린 뒤 SSID·IP(DUT 대역)·신호를 다시 확인한다. 성공하면 기록하고 계속, 실패하면 TAB-014.
- 연결은 시험 뒤에도 **그대로 둔다**(시험 장비의 준비 상태이므로 원복 대상이 아님). 원래 연결되어 있던 SSID는 기록만 한다.
- 비밀번호는 Controller에만 Windows DPAPI로 암호화 저장한다. 화면·CLI에는 가림 표시, 로그·보고서·경험 DB·heartbeat에는 절대 적지 않는다. adb 명령 기록에서도 비밀번호 자리는 `***`로 바꿔 적는다.
- S-51이 비어 있으면 지금처럼 경고만 한다(자동 연결 안 함).
- PC 수신 시험의 **무선 수신 PC도 같은 S-51로 자동 연결**한다(00-vision 표). 규칙은 아래 "무선 수신 PC".

### 무선 수신 PC (2026-09-25, 20장 GAP-56)
- **계획:** 수신 PC의 `nics` 값을 `"wifi"`로 적는다(02 11-1). 뜻: 그 PC의 Wi-Fi NIC로 받는다 — 시험 Wi-Fi(S-51)에 연결하고, 받은 IP를 가입 NIC로 쓴다. IP를 적으면 지금처럼 그 NIC(유선이든 무선이든).
- **언제 연결하나(F17 3단계):**
  - Start·`zeroloss precheck`: Controller가 그 PC에 `GET /v1/wifi`(02 4)로 Wi-Fi NIC·연결된 SSID·IP를 묻는다. S-51 SSID에 붙어 IP가 있으면 그대로. 아니면 S-51이 있을 때 `POST /v1/wifi/join`으로 연결(최대 30초 IP 기다림). 받은 IP를 계획의 `nics`에 넣고 모듈 계획 검사를 한 번 더 한다(`interface_ip`로 쓰임).
  - S-51이 비어 있는데 PC가 이미 어떤 Wi-Fi에 붙어 있으면 그것을 쓰고 ⚠("S-51 is empty: using the current Wi-Fi <SSID>"). 붙어 있지도 않으면 ✖ RCV-023.
  - 대기 중 가벼운 점검은 **연결하지 않고 읽기만** 한다: 붙어 있으면 ✔, S-51이 있고 안 붙어 있으면 ⚠("Connects to <SSID> at Start"), 둘 다 없으면 ✖ RCV-023.
- **연결 방법(노드, `core/blocks/wifi_join.py`, 명령은 V14 실기 확인 ?):**
  - Linux: NetworkManager 프로필 하나 `zeroloss-test-wifi`만 만들고 고친다(`nmcli connection add|modify … ifname <Wi-Fi NIC> ssid <SSID> wifi-sec.key-mgmt wpa-psk|sae`, Open이면 보안 없음). **`ipv4.never-default yes`·`ipv6.never-default yes`**: Wi-Fi가 기본 경로를 가져가지 않아 제어 연결(유선)과 PC의 다른 연결이 그대로다. 비밀번호는 명령줄에 넣지 않고 `nmcli connection up … passwd-file <임시 파일>`(0600, 노드 데이터 폴더, 끝나면 바로 지움)로만 준다. NetworkManager가 비밀번호를 프로필에 저장하는지(재연결·재부팅 뒤 자동 연결)는 V14에서 확인.
  - **어느 Wi-Fi 카드로 붙나(2026-10-03, GAP-102):** Wi-Fi 카드가 둘 이상인 PC(예: 내장 카드 = 인터넷, USB 카드 = 시험 공유기 수신)에서 Controller가 카드를 골라 `POST /v1/wifi/join` `nic`으로 준다. 순서: 이미 S-51 SSID에 붙은 카드 → 아무 데도 안 붙은 카드 → 시험망(그 장비 등록 주소와 같은 /24)에 붙은 카드 → 그 밖이면 첫 카드 + ⚠ RCV-023 "<카드> leaves Wi-Fi <SSID>"(그 연결이 끊김). 사용자에게 묻지 않는다.
  - **숨김 SSID(2026-10-03, GAP-101):** 프로필은 늘 `802-11-wireless.hidden yes` — SSID 이름으로 직접 찾으므로 숨김 SSID(IPTV 전용 SSID 등)에도 붙고, 숨김이 아닌 SSID에도 그대로 동작한다. 숨김 여부는 묻지 않는다(S-51에 칸 없음).
  - **연결 실패 이유(RCV-023, GAP-101):** NetworkManager 출력을 나눠 보인다. ① AP가 연결 요청에 답하지 않음(인증 뒤 association 시간 초과) — Open이면 비밀번호 말은 하지 않고 "공유기의 MAC 허용 목록·접속 수 제한 확인 + 이 PC Wi-Fi MAC", 보안이 있으면 비밀번호도 함께 ② 비밀번호 거부 ③ 공유기 쪽 보안이 S-51과 다름(주변 검색 `nmcli -t -f SSID,SECURITY device wifi list`로 그 SSID의 보안을 읽어 비교: 예 "S-51은 Open, 공유기는 WPA2 WPA3". 실패 직후엔 카드가 바빠 첫 검색에 이름이 없을 수 있으므로 2초 뒤 새로 한 번 더 — 2026-10-03 실측) ④ 이 PC에서 안 보임(숨김 SSID는 검색 목록에 이름이 없을 수 있으므로 "안 보임"만으로 이름이 틀렸다고 하지 않음) ⑤ nmcli 시간 초과(`Timeout expired`) — 실측에서는 AP가 association을 거부(status 1, 셋톱박스 전용 SSID의 MAC 허용 목록으로 보임): "30초 안에 연결이 끝나지 않음, 공유기가 이 PC 요청을 거부·무응답" + MAC.
  - **실패하면 남기지 않음(2026-10-03, GAP-103, G-11):** 연결이 실패하거나 주소를 못 받으면 만든 `zeroloss-test-wifi` 프로필을 지운다. 자동 연결이 켜진 채 남으면 그 카드를 계속 잡고 재시도한다(실측: 카드가 원래 붙어 있던 Wi-Fi에서 떨어져 "connecting"에 머묾). 성공한 프로필은 남긴다(시험 중 끊겼다 다시 붙도록).
  - 노드 서비스 계정(`zeroloss`)이 NetworkManager를 쓰게 설치 때 polkit 규칙 하나를 둔다(06 4.3, 그 계정·NetworkManager 동작 세 가지만).
  - Windows: 프로필 XML(임시 파일, 비밀번호 포함, 바로 지움) → `netsh wlan add profile filename=… user=all` → `netsh wlan connect name=zeroloss-test-wifi interface=<NIC>`. **Windows의 Wi-Fi 상태 읽기(SSID·IP·신호)가 아직 없어 V18 때 함께 만든다**(그 전에는 Windows 무선 수신 PC = RCV-023 "not supported on this PC yet").
  - 유선 NIC·다른 프로필은 건드리지 않는다. 연결은 시험 뒤에도 **그대로 둔다**(태블릿과 같음). 원래 붙어 있던 SSID는 보고서에 기록만.
  - 비밀번호: Controller → 노드는 `join` 명령 안에서만(시험망, 한 번), 노드는 메모리와 임시 파일에만 두고 기록·heartbeat·응답·오류 문구에 넣지 않는다.
- **유선 수신은 M2U를 하지 않는다 — IGMP 스누핑만**(2026-09-25 사용자): 공유기는 유선 포트로 멀티캐스트를 멀티캐스트 MAC 그대로, 가입한 포트에만 보낸다(05 1.11, RFC 4541). 그래서 M2U 확인은 무선 수신기에만 하고, 유선 수신 PC는 `m2u` = `null`(보고서 칸 없음). 유선에서 볼 것은 스누핑 동작(가입 안 한 채널이 들어오는지 NET-006·R-15, Leave 뒤 끊기는지 R-06)이다.
- **M2U 확인(10 4 방법 A):** 5단계 시험 송출 때 무선 수신 PC의 듣기에 `m2u: true`를 붙인다. 노드가 그 NIC에 패킷 캡처 소켓(Linux AF_PACKET, `CAP_NET_RAW` — 06 4.3 서비스 권한에 이미 있음)을 열고 그 그룹·포트로 온 프레임 최대 50개의 목적지 MAC을 본다: 자기 NIC MAC = **active**(M2U 동작), `01:00:5e:…` = **not active**, 못 봄(권한 없음·프레임 없음·Windows) = **unknown** + 이유. 판정에는 쓰지 않는다(원인 분석·보고서용). 체크리스트 5단계 한 줄과 보고서 `devices[].m2u`(02 10).
- **시험 중:** Wi-Fi 끊김·재연결은 NET-015(기록, 판정은 규칙대로 — AP가 끊은 것은 DUT 결함일 수 있음, 05 5.3 "문제 구간으로 나누기", 2026-09-26 사용자 결정), 채널·AP 변경은 NET-016/017(이미 있음).

### 구현 규칙 (2026-09-26, 20장 GAP-63)

## F16. 5분 결과표에서 원하는 시간대만 보기

### 목적
100시간 시험이면 5분 칸이 1,200개다. 문제가 생긴 시간대나 특정 구간만 골라서 볼 수 있어야 한다.

### 구간 선택 방법 (보고서 화면 상단)
| 방법 | 동작 |
|------|------|
| **From / To 선택** | 시작·끝 시각을 고른다. 경과 시간(예: 12h 00m ~ 14h 30m) 또는 실제 시각(예: 09-24 02:00 ~ 04:30) 둘 다 가능 — **실제 시각은 2026-10-09에야 구현(GAP-129, 사용자 "시간.날짜 입력하면 필터링"): `2026-10-09 14:30`, `10-09 14:30`, `14:30`(시작 뒤 첫 그 시각)** |
| **빠른 선택 버튼** | All / First 1h / Last 1h / Around first red(첫 빨강 앞뒤 30분) / Red only(빨강 칸만) / **Problems only(초록이 아닌 칸 전부 — 빨강·노랑·보라·회색, 2026-10-09 GAP-129)** |
| **문제 칸 목록(GAP-129)** | 그리드 아래 표: 고른 구간의 초록이 아닌 칸마다 시작 날짜·시각, 경과 시간, 장비, 색, 손실, 최대 Jitter, 이유 — 칸마다 마우스를 올리지 않아도 읽힘 |
| **칸 끌어서 선택** | 5분 칸 그리드에서 마우스로 끌어 구간 선택 |
| **칸 클릭** | 그 5분 칸의 **1초 단위 그래프**(Jitter, Packet Loss)로 확대 |

### 구간을 고르면 바뀌는 것
- 5분 칸 그리드: 선택 구간만 표시
- 요약 숫자: **선택 구간 기준으로 다시 계산**(손실 합계, Jitter 평균·최대, 색 분포)
- 그래프: Jitter, Packet Loss 시간 그래프가 선택 구간으로 확대
- 원인 분석 문구: 선택 구간에서 일어난 것만
- 화면 상단에 항상 표시: "Showing 12h 00m – 14h 30m of 100h. **Overall result: FAIL** (unchanged)"
  - 구간을 골라도 **전체 판정은 바뀌지 않는다.** 구간 요약은 보기용이다.

### 기타
- 장비(태블릿 1~3, PC)별로 켜고 끄기(체크박스)
- 선택 구간 내보내기: [Export CSV] (5분 요약·1초 기록), [Export PDF] (선택 구간 보고서)
- 선택한 구간은 보고서 주소(URL)에 담아, 그 링크를 열면 같은 구간이 바로 보이게 한다(웹 조회·공유용)
- `report.html`은 **인터넷 없이** 파일만으로 이 기능이 동작해야 한다(필요한 스크립트를 파일 안에 포함)

### 구현 규칙 (2026-09-27, 20장 GAP-86)
- **시각:** 보고서의 구간·그래프는 회차 시각 `run_s`(iptv 2.4) 기준 경과 시간. 실제 시각은 `started_utc`에 더해 옆에 함께 보인다(이 PC 시각대).
- **처음 보고서**(1초 기록 회수 전)는 5분 칸만으로 구간 보기·요약·그래프(5분 단위)를 한다. **1초 기록을 가져오면**(02 2-13 `records`) 두 번째 계산(iptv 2.4)과 함께 ① `report.html` 안에 1분 요약(`minutes`) ② `data/data_h<시간 3자리>.js`(1초 값, 회차 시각 1시간마다) ③ `report.pdf`를 다시 쓴다.
- **1초 데이터 파일:** `ZL_DATA(<시간>, {"<device>|<ch>": [[run_s, lost, jit_ms, rx, br_bps, pb], …]})` — `<script>`로 불러오므로 인터넷·서버 없이 file://에서도 열린다. 칸을 누르면 그 5분이 든 파일만 불러온다.
- **URL:** 선택 구간·장비는 주소 `#from=<s>&to=<s>&dev=<a,b>`에 담는다(열면 같은 구간).
- **CSV:** 선택 구간의 5분 요약(항상)과 1초 값(불러온 시간만)을 브라우저에서 파일로.
- **구간 PDF:** [Export PDF] = 브라우저 인쇄(인쇄용 CSS, 선택 구간만). 전체 보고서 PDF는 `report.pdf`(아래).
- **`report.pdf`:** Controller가 표준 라이브러리만으로 만든다(외부 의존 없음, 2026-09-27 사용자 결정): 판정·끝난 이유·요약·장비별 5분 칸 그리드(색 + 아이콘 글자 대신 색 칸과 범례)·원인 후보·문제 목록·NOT RUN. A4, 영어, 기본 글꼴(Helvetica). 보고서를 만들 때와 두 번째 계산 때 쓴다.
- 판정은 구간을 골라도 바뀌지 않고, 화면 위에 "Overall result: … (unchanged)"가 늘 보인다.

- HTML 안의 자바스크립트로 구간 선택·재계산·그래프를 처리한다. 서버가 필요 없다.

  - 1초 기록: 보고서 폴더의 `raw\` 옆에 **1시간 단위 데이터 파일(`data_h012.js` 등)**로 저장하고, 칸을 클릭해 1초 그래프가 필요할 때만 불러온다.

## F16-2. 문제 시점의 주기 보기 (2026-09-24 사용자)
> 목적: 문제가 **일정한 주기로 되풀이되는지** 한눈에 판단하게 한다(공유기의 주기 작업 — Wi-Fi 스캔·채널 이동, 통계 수집, IGMP 질의, DHCP 갱신, 정해진 시각의 작업 등). 판정은 바꾸지 않는다(원인 후보만, iptv R-10).

- **사건 타임라인(한 화면):** 가로 = 시간(경과 시각 + 실제 시각 함께), 세로 = 사건 종류 줄 — 손실, 순서 뒤바뀜·늦은 패킷, 지터 급증, 재생 멈춤·깨짐(F23), Wi-Fi 채널·대역폭·AP 변경(NET-016/017), 링크 속도·끊김(NET-013~015), RSSI 급락, 송신 불안정. 장비별로 겹쳐 보거나 나눠 본다. 주기가 있으면 같은 간격의 눈금처럼 보인다.
- **간격 열:** 사건 목록마다 "같은 종류 직전 사건 이후 `+14m 58s`"를 적는다.
- **주기 찾기:** 종류별 간격이 몰리면(R-10 조건: 3회 이상, 표준편차 < 10%) 배너 `Loss repeats about every 15 min (6 times, ±20 s)`와 함께 타임라인에 **예측 시각 흐린 세로선**(다음 예상 시각 포함 — 시험 중이면 그 시각을 지켜볼 수 있음). 여러 종류가 **같은 시각에 함께** 나면 묶어서 표시(예: `Wi-Fi channel change → loss within 2 s, 5 times`).
- **알려진 주기와 대조:** IGMP 일반 질의 125 s, 가입 유지 260 s(IGMPv2, RFC 2236)·270 s(IGMPv3, RFC 9776 — 05 1.11), DHCP 갱신(임대 시간의 절반), 5분 칸 경계(도구 쪽 원인 점검용). 맞으면 이름을 붙이고, 도구 주기(5분 칸 경계 등)와 맞으면 도구 원인부터 의심.
- **하루 시각 접기(24시간 넘는 시험):** 사건을 "하루 중 시각"으로 겹쳐 그린다. 매일 같은 시각(예: 03:00) 작업이 드러난다.
- **내보내기:** 사건 목록 CSV(종류, 장비, 경과·실제 시각, 간격, 값). CLI `zeroloss report --run <id> --events --json`.
- 완료 기준: 합성 자료로 15분 주기 손실 6회 → 배너·예측선·간격 열이 맞음 / 무작위 간격 → 주기 표시 없음(오탐 0) / Wi-Fi 변경 직후 손실 5회 → 묶음 표시 / 100시간 사건 1만 개에서 타임라인이 2초 안에 그려짐.

## F16-1. 실시간 화면에서도 구간 보기
- Controller의 **실시간 화면**(시험 중)에서도 같은 방식으로 구간을 골라 볼 수 있다: From/To, 빠른 선택, 끌어서 선택, 칸 클릭 시 1초 그래프(1초 기록은 수신기 화면·heartbeat 값 기준, 시험 종료 후 보고서에서 전체 확인).
- **[Follow live]** 토글: 켜져 있으면(기본) 화면이 계속 최신 구간을 따라간다. 지난 구간을 고르면 자동으로 꺼지고, 다시 누르면 최신으로 돌아온다.
- 구간을 보고 있어도 **측정·저장·5분 평가는 계속** 진행된다. 새 5분 칸이 채워지면 화면 한쪽에 작게 알림(빨강이면 강조).
- 화면 갱신은 가볍게 유지한다(1초 한 번). Controller와 송신이 같은 PC일 때 송출에 영향이 없게 한다.

- [ ] Around first red → 첫 빨강 앞뒤 30분 자동 선택
- [ ] 5분 칸 클릭 → 그 5분의 1초 그래프
- [ ] 선택 구간 CSV/PDF 내보내기
- [ ] 인터넷 없는 PC에서 report.html 열어도 구간 선택 동작 (1초 데이터 파일 포함)
- [ ] 100시간 보고서가 5초 이내에 열림
- [ ] 시험 중 실시간 화면에서 지난 구간 선택 → 측정은 계속, [Follow live]로 최신 복귀

## F17. 시작이 안 될 때 상태창에서 원인 알려주기
- **시험 카드 자동 채우기(2026-10-02 첫 실기, 20장 GAP-99 ②, 사용자 결정):** 계획에 `nics`가 없는 장비는 1단계에서 Controller가 채운다 — 송신 = 통신사 역할이 `ready`면 그 주소(10.0.0.1), 아니면 Controller가 닿은 카드(`reached_ip`)가 유선일 때 그 주소; 수신 = Controller가 닿은 카드가 유선일 때 그 주소(무선 수신 PC는 `wifi` 그대로). **기준선(S-54 Baseline, 2026-10-04 GAP-115):** 공유기가 없으므로 수신 = 송신 PC 통신사 망(10.0.0.0/24, 송신 케이블이 주소를 준 카드) 안의 카드 — Controller가 어느 카드로 닿았든(집·사무실 Wi-Fi여도) 장소와 상관없이 정해진다. 공유기 통과 시험에서 닿은 카드로 못 정하는 수신 PC는 **5단계 시험 송출을 모든 카드로 들어 패킷이 실제로 온 카드**로 정한다(2026-10-08 GAP-115 ②: 수신 probe 결과 `arrived_cards`·`arrived_on`, IP_PKTINFO). 여러 카드가 받았으면(유선과 시험 Wi-Fi가 모두 공유기 LAN) 유선 수신 PC는 유선 카드. 아무 카드에도 안 오면 지금처럼 NET-022. 장소의 주소를 가정하지 않으므로 어디서 해도 같다. 공유기 LAN·SSID·주소는 시험마다 바뀌므로 정해 두지 않는다. **사람이 고를 수도 있다(2026-10-04 GAP-115):** 장비 줄의 `Card:` 목록에서 고른 카드가 있으면 그것이 먼저다(계획 `nics`, 자동 채우기는 건너뜀; 그 PC에 없는 주소면 NET-021). 못 채우면 멈추지 않고 NET-022 ⚠ + 보고서 "공유기를 안 지난 시험" + PASS 대신 INCOMPLETE. 시험망 밖 연결(NET-018)도 경고만.

### 목적
Start를 눌렀는데 시작되지 않으면, 사용자가 **어디서 무엇이 문제인지** 바로 알고 고칠 수 있어야 한다. "Failed" 한 줄로 끝내지 않는다.

### 상태창 (메인 화면 하단 고정)
Start를 누르면 시작 절차를 **단계별 체크리스트**로 보여준다. 각 단계는 진행 중(⏳) → 성공(✔) / 실패(✖)로 바뀐다.

```
Starting test…
 ✔ 1. Devices connected (Controller, Sender, Receiver PC, Tablet 1-3)
 ✔ 2. Tools ready (ffmpeg, TSDuck, adb …)
 ✔ 3. Network check (NAT mode, router WAN 10.0.0.100)
 ✖ 4. Multicast test: Tablet-2 received nothing
      Why:  Tablet-2 is connected to a different Wi-Fi (SSID "Office_5G").
      Fix:  Connect Tablet-2 to "DUT_5G" and press [Retry].
      [Retry]  [Skip Tablet-2]  [Show details]
 ⏸ 5. Start sending
 ⏸ 6. Start receivers
```

### 규칙
- 실패한 단계에서 **멈추고**, 다음을 한 덩어리로 보여준다:
  - **어느 장비**에서 (장비 이름 강조, 장비 목록의 해당 줄도 빨갛게)
  - **무엇이** 실패했는지 (한 줄)
  - **왜** (추정 원인 한 줄)
  - **어떻게 고치는지** (한 줄) + 해결 버튼(Retry, 해당 장비 빼고 진행, 도구 설치, 설명서의 해당 장 열기)
- 실패하면 이미 시작한 것(송출, 재생 등)은 **자동으로 원복**하고 버튼은 Start로 돌아온다(F13 원복 규칙).
- Start가 **처음부터 눌리지 않는 경우**(사전 점검 실패)도 같은 형식으로 상태창에 이유를 보여준다. 버튼을 누르면 상태창으로 안내하는 팝업이 뜬다(F13).
- 전문 용어 대신 쉬운 말. 자세한 기술 정보는 [Show details]를 눌러야 보인다(오류 코드, 로그 일부).
- 상태창 내용은 `events.log`에도 남긴다.

### 시작 절차 단계와 대표 실패 원인
| 단계 | 확인 내용 | 대표 실패 원인과 안내 |
|------|-----------|------------------------|
| 1. Devices connected | 모든 Agent heartbeat, 태블릿 adb 연결, 버전 호환 | PC 꺼짐·케이블 빠짐, 서비스 멈춤 → [Restart Agent] / 태블릿 USB 디버깅 허용 안 됨 / 버전 다름 → [Update] |
| 2. Tools ready | 도구 설치·버전, 다른 adb 서버, 포트 사용 중 | 도구 없음 → [Install] / 포트 사용 중 → 사용 중인 프로그램 이름 표시 |
| 3. Network check | NIC 링크 속도·이중 방식(필요 대역 × 1.1 미만이면 차단, NET-012), NAT 판별, 송신 PC와 DUT WAN 같은 대역, (DHCP 방식) DUT가 IP 받음, 태블릿 SSID 확인·자동 연결(S-51), 공유기 뒤 송신 PC 주소 충돌(ARP, SND-013 차단), 시험 PC가 시험망 밖으로도 연결됨(Wi-Fi로 닿음·NAT 없이 닿음·다른 Wi-Fi 주소, NET-018 ⚠, 20장 W-3) | 대역 다름, 다른 DHCP 서버 있음, WAN 케이블 |
| 4. Disk, time & PC speed | 디스크 여유(시험 시간에 필요한 양), 시계 차이, 재생 켠 수신 PC의 성능(RCV-015, 05 4.2-1), 재생 켠 수신 PC의 Agent Desktop(RCV-010, F20), 절전 막기 가능 여부(SYS-005) | 공간 부족 → 가능한 최대 시간 표시 / 시계 차이 2 s 넘음 → 경고만(DSC-009) |
| 5. Multicast test | 1~2초 시험 송출이 각 수신기에 도달 | 아무도 못 받음 → DUT IGMP 설정·TTL / 무선만 못 받음 → Wi-Fi 연결·M2U / 특정 태블릿만 → SSID·신호 |
| 6. Start sending | (영상 파일이 없으면 먼저 만들기: 진행률·남은 시간, iptv 1-1-2) 채널별 송출 시작, 송출 속도 정상 | 영상 파일 없음·손상, CPU 부족 → 사전 준비 파일 모드 권장 |
| 7. Start receivers | 수신·재생·계측 시작, 첫 패킷·첫 PAT 도착 | 재생기 실행 실패, 디코딩 불가(UHD HEVC 미지원 장비) |

### 구현 규칙 (2026-09-25, 20장 GAP-55)
- **순서:** 트래픽 없이 알 수 있는 것부터(1~4), 그다음 짧은 시험 송출(5), 그다음 실제 시작(6·7). 전에는 "Disk & time"이 7번(시작 뒤)이라 공간 부족을 알고도 되돌려야 했다 — 4번으로 옮김.
- **언제 도나(2026-09-25 사용자 결정):**
  - **대기 중 가벼운 점검 = 1~4:** 트래픽을 보내지 않는다. 화면이 계획을 열거나 장비가 바뀔 때와 **30초마다** Controller에 요청한다(화면 스레드 밖). 결과로 Start가 활성 / 회색 + 이유 한 줄(11-ui 1.10 "IDLE(사전 점검 실패)" 열). ⚠(경고)만 있으면 Start는 활성.
  - **Start = 1~7 전체** 체크리스트. 실패한 단계에서 멈추고 되돌린다(F13).
  - **`zeroloss precheck --plan`(CLI) = 1~5**(시험 송출 1~2초는 하지만 시험은 시작하지 않음).
- **단계별로 보는 것:**
  1. Devices connected: 계획의 장비마다 `/v1/health` 응답(DSC-014), 같은 장비인지(`device_id`, DSC-004), `protocol_version`(DSC-013)과 빌드(INS-015)가 Controller와 같은지, 계획 모듈이 그 장비에서 켜져 있는지(INS-024).
  2. Tools ready: 모듈이 **역할마다 필요한 도구**를 알려 주고(12 2 `tools`, `run_entry.required_tools`), 장비의 `/v1/info` `tools`(02 4)에 없으면 ✖(INS-029). 버전은 표시만(고정 버전 대조는 보관소 P0 뒤).
  3. Network check: 링크 속도·이중 방식(NET-012, 05 1.8), NAT 판별(07 4: 장비가 본 Controller 주소 `seen_from_ip` ≠ Controller가 그 장비에 연결한 주소 → NAT, 그 주소 = 공유기 WAN IP). 같은 대역(SND-010)과 공유기 WAN 주소 방식(`dut.wan_ip_way`: 통신사 역할이 준 주소 / 고정)은 2026-09-26부터 봄(07 3.3), 태블릿 SSID는 그 기능이 생길 때.
  4. Disk, time & PC speed: 장비마다 heartbeat `disk_free_mb` ≥ 모듈이 계산한 필요량(`run_entry.disk_need_mb`) + 1 GB(RCV-008 경고선), 모자라면 가능한 최대 시간을 함께. 시계 차이(D39)가 2 s 넘으면 ⚠(DSC-009, 막지 않음). **PC 성능(2026-09-26):** 모듈 계약 `device_checks(plan, light)`(12 2)가 준 점검을 장비마다 보내고, 답의 `warn`이 있으면 ⚠(막지 않음). IPTV = 재생 켠 PC 수신기의 RCV-015(05 4.2-1 구현 규칙). 재생 켠 수신 PC마다 모듈 `device_checks`의 `receiver/desktop`: Agent Desktop이 없으면 **실패**(RCV-010, 시작 전에 막힘, 로그인하면 다음 점검이 `clears`로 Action Required를 닫음). heartbeat `power.sleep_guard`가 `unavailable`이면 ⚠(SYS-005, 막지 않음). 빈 메모리(`resources.mem_free_pct`) 10% 미만 ⚠, 5% 미만 실패(SYS-004).
  5. Multicast test: 모듈의 시험 송출 단계(`run_entry.probe_steps`) — 수신기가 먼저 듣기 시작하고 → 송신이 채널마다 1~2초 시험 흐름을 보내고 → 수신기가 받은 수를 돌려준다. 0개면 ✖(NET-003). IPTV는 널 패킷 흐름(`tsp -I null`, 1 Mbps, RTP) — 영상 파일이 필요 없다.
  6·7. 지금까지의 시작 순서 그대로(영상 준비 → 송출 안정 → 수신 가입 → 안정화).
- **형식:** 02 2-1 `checklist`(마지막 Start·점검)·`precheck`(마지막 가벼운 점검), 10994 `POST /v1/controller/precheck`(02 2-6). 각 단계 `state` = `waiting` / `running` / `ok` / `warn` / `failed` / `skipped`, 실패·경고는 장비·코드·What/Why/Fix(09 문구). 상태창에는 `✔ ⚠ ✖ ⏳ ⏸` + 단계 이름 + 한 줄, 실패 단계 아래 Why·Fix(11-ui 3장). [Retry] = Start 다시.
- 시험 중에는 점검을 받지 않는다(RUN-012).

## F18. 송신 방식: 시험 연동 / 상시 방송

| 방식 | 동작 | 기본 |
|------|------|------|
| **시험 연동** | Start에 송출 시작, Stop에 송출 정지와 원복 | **기본** |
| **상시 방송 (Always-on broadcast)** | 통신사처럼 송신은 한 번 켜면 **계속** 돈다. Start/Stop은 **수신 측정만** 시작·정지한다 | Advanced settings에서 켬 |

- 상시 방송 모드:
  - 메인 화면 상단에 **"Broadcast: ON (3 channels)"** 표시와 [Stop broadcast] 버튼.
  - Stop(시험 정지)은 수신·계측·재생만 멈추고 원복한다. 송출은 계속된다.
  - 송출을 멈추려면 [Stop broadcast]를 누른다. 송출과 동반 작업만 멈춘다 — 송신 PC의 통신사 역할(공유기 WAN 주소, 07 3.2 B)은 시험과 상관없이 그대로 둔다.
  - 송신 Agent는 **Controller heartbeat가 끊기면 상시 방송도 멈춘다**(F11: 주인 없는 트래픽 금지). Controller가 다시 연결되면 사용자가 다시 켠다.
  - 보고서에 "Broadcast was running before the test started (since …)"를 적는다.
- Reset All은 두 모드 모두 송출까지 멈춘다.
- **구현 규칙(2026-09-27 사용자 결정, 20장 GAP-87):** S-13 Always-on이면 Start가 송출을 켜고(이미 돌고 있으면 송출 단계를 건너뜀 — 같은 계획의 채널·화질일 때만, 다르면 RUN-014 "Stop the broadcast first"), 시험 Stop은 수신·계측·재생만 멈춘다. [Stop broadcast]·`zeroloss broadcast stop`·`POST /v1/controller/broadcast` `{"on": false}` — 시험 중에는 RUN-012. 방송 중에는 Controller가 시험이 없어도 송신 노드에 heartbeat를 계속 보낸다(끊기면 송신 노드가 F11대로 방송을 멈춤). 상태 `broadcast` = `{"on", "since_utc", "channels", "sender"}`(02 2-1). 보고서 `sender_mode` = `always_on`, `broadcast_since` = 그 회차 Start 때 이미 돌던 방송의 시작 시각(없으면 `null`). **2026-10-02 구현에서 정한 것(20장 GAP-92):** 같은 방송인지 = 송신 PC·송출 채널·화질·비트레이트·그룹·포트·TTL·원본(파일)·송신 NIC가 같고 새 계획도 Always-on. 그 시험은 사전 점검 5단계 시험 송출을 건너뛰고(송신이 이미 보내는 중, 안정화가 경로를 확인) 영상 만들기도 건너뛴다. S-18 Auto면 도는 방송의 경로(멀티캐스트/프라임)를 이어받는다. 시작이 실패해도 돌던 방송은 그대로 둔다. **안전 정지(장비 끊김, F11)·Reset All·Controller 종료는 방송까지 끈다.**

## F19. 채널 전환 (수동 + 자동)

### 수동
- Controller 실시간 화면에서 장비(태블릿·PC)마다 채널 선택 목록이 있다. 바꾸면 해당 수신기가 Leave → Join 한다(`05-standards.md` 4.1, 4.2.2 두 소켓 함께).
- 수신기 쪽 화면(태블릿·PC 모니터)은 보기 전용이다. 채널은 Controller에서만 바꾼다.

### 자동 (Advanced settings)
- `Auto channel change: every [N] min` (기본 꺼짐, N 기본 10분). 수신기별로 채널 목록을 돌아가며 바꾼다.
- 목적: IGMP Join/Leave를 장시간 반복했을 때 DUT가 제대로 처리하는지 시험(가입 실패, 이전 채널이 계속 흘러옴 등).
- 전환 순서와 간격은 장비마다 조금씩 어긋나게(기본 10초 간격) 해서, 모든 수신기가 동시에 바꾸지 않게 한다(옵션으로 동시 전환 가능).

### 측정과 판정
- 손실은 채널 가입 구간마다 따로 계산하고, 전환 공백은 손실이 아니라 전환 시간으로 기록한다(`05-standards.md` 2.1).
- 전환 시간 = 명령 → **다음 채널 정상 재생(정상 FPS + 소리)**, TTAK.KO-01.0204/R1 정의와 같다(`05-standards.md` 1.6-2). 보조 시각으로 IGMP Join 송신, 첫 패킷(공유기 몫), 첫 프레임 표시(프레임 번호 표식)를 함께 기록한다. 자동 반복 모드에서는 정해진 시간(S-47, 기본 5초, 0.5~30초) 안에 정상 재생된 비율(반응 성공률)도 보여 준다. 전환 시간과 성공률은 기록·표시만 하고 PASS/FAIL 판정에는 넣지 않는다.
  - **RFC 3918 6.1·6.2 측정법(2026-09-24):** 가입 지연(Join → 첫 패킷)은 공유기 멀티캐스트 표에 그 그룹이 **없을 때(방법 A: 다른 수신기가 그 채널을 안 보고 있음)**와 **있을 때(방법 B: 다른 수신기가 이미 보고 있음)**를 나눠 기록한다. 탈퇴 지연은 Leave → 이전 채널 마지막 패킷. 보고서에 방법(A/B), IGMP 버전, 그룹 수, 송출 부하를 함께 적는다.
  - **DVB 권고(TS 102 034 7.2.2.2) 대조, 기록·표시만(2026-09-24 결정):** Join → 첫 패킷 500 ms 초과 횟수, Leave → 이전 채널 마지막 패킷 500 ms 초과 횟수를 채널 전환 통계에 보여 준다. 원인 분석(fast-leave 없음 등, 05 1.11)에 쓴다. 색·판정 무관.
- **Leave 후 이전 채널이 계속 들어오면**(기본 3초 넘게) "Leave not processed by router"로 기록하고 노랑 표시. 새 채널의 **첫 패킷이 5초 안에 안 오면** 빨강("Join failed").
- **세 가지 시간을 섞지 않는다:**
  | 시간 | 기준 | 영향 |
  |------|------|------|
  | Join 실패 한계 | 첫 패킷 5초(고정, 네트워크 전달 여부) | 넘으면 빨강 — 공유기가 새 채널을 안 보냄 |
  | 측정 재개 안정화 | 첫 패킷 뒤 최대 5초(05 2.1-2 4번) | 이 구간은 판정 제외, 그 뒤부터 손실·지터 판정 |
  | 반응 성공 시간 S-47 | 정상 재생까지(기본 5초, 0.5~30초) | **색·판정에 영향 없음.** 반응 성공률 기록만 |
  - 예: S-47을 1초로 두면 2초 걸린 전환은 "반응 실패"로 성공률에만 반영되고 색은 초록 그대로다.

### 구현 규칙 (2026-09-27 사용자 결정, 20장 GAP-87 — PC 수신기, 태블릿은 앱과 함께)
- **명령:** Controller 창구 `POST /v1/controller/channel`(02 2-13)·CLI `zeroloss channel <장비> <채널>`(13)·화면 장비 줄의 채널 상자. **시험 중(RUNNING)에만**, 자동 전환(S-21)이 켜져 있으면 수동은 잠금(K-11). 같은 채널이면 아무것도 하지 않음.
- **수신기(PC, 2026-10-01 구현 순서, 20장 GAP-90):** ① 옛 채널 분석을 마감(열린 틈은 손실로, 마지막 부분 초까지 기록) ② 재생기 정지 → 분석 소켓 닫기(= Leave, 05 4.2.2 두 소켓 함께) → 새 소켓 열기(= Join) → 새 분석 시작 → 새 채널 재생기 시작. 재생기는 새로 켠다(PC는 비교용이라 그 시작 시간이 전환 시간에 들어감). 새 가입 구간(`join_segment` + 1)마다 분석을 새로 시작한다(중간 가입 규칙, 05 2.1-2). **가입 뒤 5초까지 첫 패킷이 없으면 가입 실패**(NET-003), 첫 패킷이 오면 안정화는 **그때부터 최대 5초**(그 전에 조건이 맞으면 일찍 끝남, 5초가 지나면 조건이 안 맞아도 측정 시작 — 전환은 시험을 FAIL시키지 않으며, 안 맞은 조건은 기록에 남김). 안정화 초와 전환 공백은 1초 기록에 쓰지 않고(손실 아님), `e`는 실제 시간대로 이어진다. **가입 실패 뒤에도 1초 기록은 계속 쓴다**(수신 0 → 그 칸이 빨강, 송신·링크 문제가 설명되면 보라). 진행 중이던 5분 칸은 그 순간 닫혀 구간별로 요약된다(02 6). 시험 Stop은 진행 중인 전환을 `stopped`로 닫고 Leave 확인은 기다리지 않는다.
- **기록:** 전환마다 `<회차>_zaps.jsonl` 한 줄(02 7-2, 수신 회차 폴더 `raw/<장비>/`). 시각은 수신기 `e` 시계의 초이고 Controller가 timeline 차이로 `run_s`로 바꾼다(02 7-2). `t_normal_play` = 새 채널에서 재생기가 처음 `ok`를 알린 초, 재생을 끄면 `null`이고 성공은 첫 패킷 기준(`basis: "first_packet"`). 전환이 끝난 값은 그 뒤 첫 1초 줄의 전환 키(02 7)로도 가서 5분 요약 `channel`이 된다. 전환 기록은 한 줄씩 쓰므로 비정상 종료 때는 마지막 줄만 깨질 수 있고, 읽는 쪽이 그 줄을 건너뛴다(마감 줄 없음, 20장 GAP-90 ⑨).
- **판정:** 첫 패킷이 5초 안에 없으면 **NET-003**(가입 실패, 그 구간의 칸 빨강 — 05 5.3). Leave 뒤 3초 넘게 이전 그룹이 오면 **NET-005**(노랑, 그 구간의 칸) — Leave 뒤 4초 동안 원시 소켓(AF_PACKET, CAP_NET_RAW, 설치 서비스는 가짐; NIC가 안 받는 그룹도 보이게 ALLMULTI)으로 이전 그룹:포트 패킷을 본다. 권한이 없거나 같은 노드의 다른 수신기가 그 그룹을 아직 받고 있으면 `leave_check: "not_checked"`로 남기고 노랑으로 하지 않는다. S-47(반응 성공 시간)은 성공률에만, 색과 무관. 가입 실패(NET-003)에서 송신·링크 문제 구간이 설명하면 보라(05 5.3).
- **가입 방식 A/B(RFC 3918 6.1·6.2):** Controller가 명령 때 다른 수신기가 새 채널을 보고 있는지로 정해 보낸다(`A` = 아무도 없음, `B` = 이미 누가 봄).
- **자동(S-21·S-22):** Controller가 N분마다 수신기마다 계획의 다음 채널(CH1 → CH2 → CH3 → CH1 …)로 바꾼다. S-22 켬이면 수신기 사이를 10초(설정값)씩 어긋나게, 끔이면 동시에. 시험이 RUNNING일 때만, 멈추면 타이머도 멈춤.
- **5분 요약 `channel`(02 6):** 그 칸에 끝난 전환의 수·성공·평균/최대 전환 시간. 보고서 `channel_change`(02 10): 회차 전체.

### 완료 기준
- [ ] Controller에서 태블릿 채널 변경 → 1~5초 안에 새 채널 재생, 전환 시간 기록
- [ ] 자동 전환 10분 간격으로 24시간 → 전환마다 기록, 전환 공백이 손실로 잡히지 않음
- [ ] 패킷 캡처로 전환마다 IGMP Leave·Join이 실제로 나가는지 확인

## F20. 송신·수신 PC의 작은 상태 창 (Agent Desktop)

### 용어
- **재생기** = 수신단에서 영상·소리를 실제로 틀어 주는 프로그램(PC: VLC 기본, mpv 옵션 S-26, 태블릿: 앱 안의 재생 화면).
- **상태 창** = 송신·수신 PC 화면 구석에 뜨는 **작은 창**. 그 PC에서 무엇이 돌고 있고 정상인지 한눈에 보여준다.

### 원칙
- 조작과 자세한 모니터링은 **Controller**에서 한다(F12). 송신·수신 PC의 상태 창은 **현장에서 "지금 돌고 있나, 정상인가"만 확인**하는 용도다(보기 전용).
- 작게, 항상 위(always on top, 끌 수 있음), 화면 구석. 재생 화면을 가리지 않는다.
- 상태 색: 🟢 정상 / 🟡 주의 / 🔴 문제 / ⚪ 대기.

### 송신 PC 상태 창
```
┌ ZeroLoss Sender ───────── 🟢 ┐
│ Sending 3 channels           │
│ CH1 239.1.1.1  35.0 Mbps  🟢 │
│ CH2 239.1.1.2  35.0 Mbps  🟢 │
│ CH3 239.1.1.3  35.0 Mbps  🟢 │
│ Controller: Connected        │
│ My IP: 10.0.0.1 (enp37s0, router WAN)  │
│ ISP role: ready on enp37s0             │
└──────────────────────────────┘
```
- 보여주는 것: 역할, 상태(Idle / Sending / Broadcast ON / Error), 채널별 주소·실제 송출 속도·정상 여부, Controller 연결, **My IP**(주소가 있는 NIC마다 한 줄 `주소 (NIC 이름[, Wi-Fi][, router WAN])` — 자동 시도·다시 찾기로도 못 찾을 때 Controller에 입력할 주소, 07-network 5장), **ISP role**(20장 W-4, 2026-09-26 사용자: 통신사 역할이 `ready`면 "ISP role: ready on <NIC> (router WAN gets its address here)"이고 그 NIC의 My IP에 `router WAN`, 기다림·충돌·오류면 "ISP role: waiting|conflict|error — <이유>", 역할이 없는 PC는 줄 없음 — 송신 PC가 공유기 WAN에 붙었는지 화면만 보고 알게)
- 🔴 예: 송출 속도가 목표와 다름, 송출 프로세스 멈춤, Controller 연결 끊김

### 수신 PC 상태 창
```
┌ ZeroLoss Receiver ─────── 🟢 ┐
│ Receiving CH2 (wired)        │
│ Jitter   2.1 ms              │
│ Loss     0                   │
│ Bitrate  35.0 Mbps           │
│ Player   Playing 🟢          │
│ Tablets  3 connected (USB)   │
│ Controller: Connected        │
│ [Details ▾]                  │
└──────────────────────────────┘
```
- 보여주는 것: 상태(Idle / Receiving / Relaying tablets / Error), 채널과 유선·무선, **Jitter·Packet Loss(맨 위, 크게)**, 비트레이트, 재생기 상태, USB로 연결된 태블릿 수, Controller 연결
- 태블릿 시험 중(영상 수신 안 함)에는 "Relaying 3 tablets"와 태블릿별 연결 상태만 보여준다.
- **[Details ▾]**를 펼치면 1초 값 목록(최근 1,000줄, F12)이 보인다. 기본은 접힘.

### 태블릿
- 재생 화면 위에 같은 형식의 작은 상태 표시(접을 수 있음): 채널, Jitter, Loss, 상태 색.

### 구현 규칙 (2026-09-26 사용자 결정, 20장 GAP-65)
- **재생기는 Desktop이 띄운다:** 노드(서비스)는 화면이 없으므로(D38) 재생 켬(S-49 On) 수신이면 노드가 "원하는 화면 작업" 목록에 재생기 작업을 올리고, Desktop이 노드의 127.0.0.1:10994를 1초마다 보며 목록대로 켜고 끈다(목록 방식: 메시지를 놓쳐도·다시 켜도 같은 결과). Desktop은 재생기의 1초 값·사건을 노드에 돌려주고, 노드는 그것을 지금처럼 1초 기록·재생 이상 판정에 쓴다(재생기 부품 자체는 P2 것 그대로, GAP-39). Windows·Linux 같은 방식.
  - 작업 id = `<run_id>/<receiver id>/ch<n>/player`: 다른 시험·옛 세대의 보고는 버린다(G-13).
  - **서로 묶임:** Desktop은 노드가 3초 답이 없으면 자기가 띄운 재생기를 모두 끈다(재생기는 노드와 함께 끝남, 절대 원칙). 노드는 Desktop 보고가 3초 없으면 그 재생기를 "재생 안 함"(RCV-020)으로 본다.
  - 시작 때 Desktop이 연결되어 있지 않으면(5초 기다림) RCV-010으로 시작 실패 + Action Required `human.os.check_auto_login`(Desktop이 붙으면 자동 완료). Desktop은 붙었는데 재생기가 안 켜지면 지금처럼 RCV-019.
  - 노드가 스스로 재생기를 띄우는 방식(P2, `--player-host self`)은 개발·시험용으로 남긴다. 설치본 서비스는 `--player-host desktop`.
- **상태 창은 보기 전용:** 노드의 `GET /v1/desktop/status`(02 2-12)만 보고 그린다. 모듈별 줄은 모듈의 `desktop_entry`(12 2)가 만든다(Core·Desktop에 "IPTV면…" 분기 없음).
- **닫기 = 숨김:** 창을 닫으면 숨기기만 하고 Desktop(재생기 포함)은 계속 돈다. 트레이 아이콘(없으면 작업 표시줄)에서 다시 연다. 트레이 메뉴 **Quit**만 Desktop을 끝내며, 시험 중이면 재생기 죽음(RCV-020, 수신단 원인 = 보라)으로 처리된다. 시험 중 Quit는 확인을 한 번 묻는다.
- 항상 위: 기본 켬, 창에서 끌 수 있음(그 PC에만 저장, 16 S-53). 위치: 오른쪽 아래(11-ui 1.x).
- 자동 시작: Linux `/etc/xdg/autostart/zeroloss-agent-desktop.desktop`(.deb가 설치·제거), Windows는 시작 항목(V18). 자동 로그인은 SSH 설치 때 `--auto-login`으로 켠다(06 11.3 4-2, 실제 화면 확인은 실기).
- 같은 PC에서 Desktop은 하나만(두 번째는 첫 창을 앞으로 가져오고 끝남).
- 화면 꺼짐·잠금 막기(RCV-006): 재생 작업이 있는 동안 세션 D-Bus `org.freedesktop.ScreenSaver.Inhibit`, 작업이 없으면 `UnInhibit`. 2초마다 `GetActive`로 잠김을 보고 사건으로 보냄.

## F21. 문제 알림 창 (Problems)

### 목적
예외가 많아도 **사용자가 무엇이 문제인지 알아야 고칠 수 있다.** 예외는 기록만 하고 끝내지 않고, 모두 한곳에 모아 사용자에게 보여준다.

### 동작
- Controller 메인 화면 상단에 **문제 개수 배지**: `⚠ 2 problems` (🔴 오류 / 🟡 주의 개수). 누르면 Problems 창.
- Problems 창의 한 줄 = 문제 하나:
  | 시각 | 장비 | 코드 | 무엇이 (What) | 왜 (Why) | 어떻게 고치나 (Fix) | 버튼 |
  |------|------|------|---------------|----------|---------------------|------|
  | 14:32:10 | Tablet-2 | ZL-TAB-005 | Wi-Fi disconnected | Joined "Office_5G" | Connect to "DUT_5G" | [Retry] [Manual ▸] |
- **지금 진행 중인 문제**가 위, 해결된 문제는 아래로(회색, 해결 시각 표시). 같은 문제가 반복되면 한 줄로 묶고 횟수 표시.
- 새 🔴 문제가 생기면: 배지 깜빡임 + 해당 장비 칸 빨간 테두리 + (설정 시) 소리. 시험 중에도 **팝업으로 작업을 막지 않는다**(판단이 필요한 경우만 팝업).
- [Manual ▸]은 설명서의 해당 문제 해결 항목을 연다(오류 코드로 연결).
- 모든 문제는 보고서의 "Problems during the test" 표에도 그대로 들어간다.
- 문구 규칙: 전문 용어 없이, **고칠 수 있는 행동**으로 끝난다. 원인을 모르면 "Unknown cause"라고 쓰고 [Export diagnostics](진단 파일)를 제공한다. [Export diagnostics]는 Problems 창 오른쪽 아래에 **항상** 있다(2026-09-27, 20장 GAP-82): 누르면 만드는 동안 `Exporting…` 회색, 끝나면 파일 경로 + [Open folder], 실패하면 이유(02 2-13 `diagnostics`와 같음).
- **알림 폭주 막기 (ISA-18.2 / EEMUA 191, 2026-09-24 결정):**
  - 우선순위 3단계(🔴 오류 / 🟡 주의 / 정보). 목표 분포는 대략 높음 5%·중간 15%·낮음 80%.
  - **폭주:** 10분 안에 새 문제가 10개를 넘으면 맨 위에 "Many problems at once (n in 10 min)" 요약 한 줄을 두고 🔴만 펼쳐 보인다. 폭주가 끝나면 자동으로 원래 보기.
  - **깜빡이는 문제(chattering):** 같은 코드·같은 장비가 켜졌다 꺼졌다 하면 한 줄로 묶고 횟수·처음·마지막 시각을 보인다. 짧은 반복(기본 10초 안에 다시 켜짐)은 새 알림으로 세지 않는다.
  - **오래 남은 문제(stale):** 24시간 넘게 진행 중인 문제는 따로 표시.
  - 보고서 "Problems during the test"에 알림 수(10분당 평균·최대, 폭주 시간 비율, 가장 잦은 10개)를 적는다. 목표는 10분당 평균 1개 이하. **판정·색과는 무관**하다.

### 구현 메모 (2026-09-25)
- 문제 목록은 **Controller 서비스 한 곳**(11-ui 1.1): 자기 사건 + 노드가 보낸 경고·오류(02 5 `events`) → 문제 저장소 → 10994 `GET /v1/controller/problems`(02 2-2) → 화면·CLI.

## F22. 사람 할 일 창 (Action Required)

### 목적
사람 손을 최소화하되, **꼭 사람이 해야 하는 일은 별도 창으로 반드시 알려준다.** 문제 알림(F21)과 섞지 않는다. 문제는 "무엇이 잘못됐나", 이 창은 "**사람이 무엇을 해야 하나**"다.

### 동작
- 사람이 해야 할 일이 생기면 **Action Required 창**이 뜬다(별도 창, ZeroLoss 창 위 — 다른 프로그램 위는 아님: 2026-10-17 사용자 "화면 가운데 가려버리고", 끌어서 옮길 수 있음). 메인 화면에도 `🖐 1 action needed` 배지.
- 한 줄 = 할 일 하나:
  | 어디서 | 무엇을 | 방법(그림 포함) | 상태 |
  |--------|--------|-----------------|------|
  | Tablet-2 (USB) | Allow USB debugging | 태블릿 화면의 "Allow" 누르기 [그림] | ⏳ Waiting… |
- **완료는 가능하면 자동 감지:** 태블릿 허용 → adb 상태로, 케이블 연결 → 링크로, 설정 변경 → 재점검으로 확인하고 자동으로 ✔. 감지할 수 없는 일은 사람이 [Done]을 누른다. **자동으로 닫히는 일도 사람이 [Done]으로 닫을 수 있다(2026-10-04 GAP-116):** 장비 이름이 빈 "Restart the PC" 줄이 자동으로도, 사람으로도 닫히지 않아 사용자가 막힘 — [Done]은 기다리는 줄 모두에 되고, 고른 줄이 없으면 맨 위 기다리는 줄에. Start 실패로 열리는 줄은 그 PC 이름을 단다(시작 단계의 오류는 모두 장비 이름을 가짐).
- 할 일이 끝날 때까지 그 일이 필요한 단계만 기다리고(상태창 F17에 "Waiting for human action"), 관계없는 준비는 계속 진행한다.
- **원격에서도 보인다:** CLI(`zeroloss actions --json`), 원격 웹·Claude 세션(13-ai-loop), 알림(00-vision 원칙 10). 현장에 사람이 없을 수 있으므로, 누가 언제 해야 하는지 알 수 있게.
- 할 일마다 **처음 한 번인지, 매번인지** 표시. "매번"인 할 일이 생기면 자동화 대상으로 기록(00-vision 3차 목록 갱신 근거).
- 모든 사람 할 일은 보고서의 "Human actions" 표에 남는다(무엇을, 언제 요청, 언제 완료, 누가).

### 구현 메모 (2026-09-25)
- 할 일 목록은 Controller 서비스 한 곳(F21 문제 목록 옆). **할 일은 문제 코드로 열린다**: 목록(`controller/actions/catalog.json`)에 할 일마다 `action_id`, 문구(what·how), 여는 코드, 자동 완료 여부, once/every를 적는다. 여는 문제가 `clears`로 풀리면 자동 ✔(`done_by` auto), 감지할 수 없는 일은 [Done].
- 새 할 일이 생기면 창이 앞으로 뜬다(ZeroLoss 창 위, 작업을 막지 않음 — 모달 아님). 배지 `🖐 n action needed`.
- **고르기 버튼(2026-09-26 사용자 결정, 20장 W-1):** 사람이 여러 후보 중 하나를 골라야 하는 할 일(예: 공유기 WAN 카드)은 그 줄을 고르면 표 아래 "Choose:" 줄에 **후보마다 버튼**이 나온다. 누르면 그 할 일이 내놓은 후보만 받아 실행한다(명령어 입력 없음, CLI `zeroloss actions choose <key> <후보>`와 같음). 받아들여지면 ✔, 안 되면(다른 DHCP 서버 등) 할 일은 그대로 남고 이유는 Problems에.
- 끝난 일은 경험 DB(14장)에 행동으로 남는다.
- **잠깐 기다렸다 보인다(2026-10-09 사용자 "done이 클릭되지 않아", GAP-135):** 할 일마다 `grace_s`(재시작 60초, 케이블·Wi-Fi 15초) 동안 기다리는 줄은 보이지 않고 창도 뜨지 않는다. 그 안에 저절로 풀리면 아무에게도 묻지 않은 것으로 하고(보고서 Human actions에도 없음), 넘으면 그때 창이 뜬다. 무선 카드의 링크 끊김(NET-015)은 "케이블 확인"이 아니라 "공유기 Wi-Fi 확인"(`human.wifi.check`).
- **기다리는 일이 없으면 [Done] 대신 [Close]:** 아래에 "✔ All done — nothing to do now."와 누를 수 있는 [Close]. 회색 [Done]을 남기지 않는다(사용자 "무슨 의도로 버튼처럼 하단에 done을 찍어?").

## F23. 재생 이상 증거 자동 수집 (화면·소리 캡처)

### 목적
화면 깨짐(글리치)·멈춤(스톨)·소리 끊김이 생기면 **그 순간을 자동으로 저장**해서, "언제, 어느 장비에서, 화면이 어떻게 깨졌는지"를 나중에 누구나 확인할 수 있게 한다. 패킷 원본까지 함께 저장해 **다시 재생해 재현**할 수 있게 한다.

### 무엇이 계기가 되나 (자동)
| 계기 | 감지 방법 |
|------|-----------|
| 화면 멈춤(스톨) | 재생기의 프레임 수가 늘지 않음, 같은 화면이 계속됨(정지 화면 감지) |
