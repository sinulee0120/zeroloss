# 14. 경험 기록과 자동 대응 (Autonomy)

> 목표: "이런 경우엔 이렇게 했더니 해결됐다"는 경험을 **DB에 가중치와 함께 쌓아서**, 비슷한 상황이 오면 Controller가 **스스로 대응**하거나 **추천**하고, 권한 있는 관리자에게 **메신저·이메일로 보고하고 다음 지시를 받는다.**
> 단계: 1차는 **기록의 틀만** 만든다(데이터가 쌓여야 학습할 수 있으므로). 추천·자동 대응·양방향 메신저는 2차 이후.

## 1. 경험 기록 (1차부터 쌓는다)
모든 사건과 그에 대한 대응을 **같은 형식**으로 Controller의 경험 DB(SQLite, `experience.db`)에 남긴다.

| 필드 | 내용 | 예 |
|------|------|----|
| `situation` | 상황 특징: 오류 코드, 장비 종류·역할, 모듈, 시험 단계, 관련 값 | `ZL-TAB-005`, tablet, iptv, RUNNING, rssi=-71 |
| `action_id` | 한 대응 행동의 **표준 이름** | `tablet.wifi.reconnect`, `agent.restart`, `run.reset_all` |
| `actor` | 누가 했나 | auto / human(이름) / claude / remote(admin 이름) |
| `outcome` | 결과 | resolved / not_resolved / made_worse / pending(진행 중) / unknown(결과 전에 프로그램이 꺼짐 — 다음 시작 때 표시), 해결까지 걸린 시간 |
| `context` | 빌드, DUT 모델·펌웨어, 시각(UTC) | |

- **모든 해결 버튼·자동 처리·사람 할 일(F22)·CLI 명령은 `action_id`를 가진다.** 같은 행동은 어디서 하든 같은 이름 → 기록이 모인다.
- 사람이 직접 한 일도 [Done] 때 "무엇을 했나"를 목록에서 고르거나 한 줄 메모로 남긴다.
- `action_id` 형식: 소문자 점 구분 두 단계 이상(`^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$`). 모든 사건은 사건 흐름에서 자동으로 `situation`으로 쌓인다(Controller). 1차 형식: `situations`(사건)·`actions`(대응, 사건에 연결) 두 표, `PRAGMA user_version` = 1.

## 2. 가중치 (2차)
상황 특징이 비슷한 과거 기록을 찾아, 행동마다 점수를 매긴다.
- **점수 = 성공률 × 기록 수 반영 × 최근성(오래된 기록은 가중치 감소) × 같은 DUT·빌드 가산**
- 결과가 나쁘면(made_worse) 크게 감점. 관리자가 "이 대응은 틀렸다"고 표시하면 즉시 반영.
- 처음에는 규칙·통계 방식으로 시작하고, 데이터가 쌓이면 Claude가 DB와 문서를 읽고 추천 이유를 문장으로 설명하게 한다.

## 2-1. 학습 모델: 예측과 제어 (2~3차)
> 가중치를 **경사 하강(gradient)으로 계속 조정**하면서 ① 앞으로 일어날 일을 **예측**하고 ② 어떤 행동을 할지 **제어**한다. 이것이 "스스로 일을 정리하는" 자동화의 핵심이다.

### 예측 (무엇이 곧 일어날까)
| 예측 대상 | 입력 특징(예) | 쓰임 |
|-----------|---------------|------|
| 곧 손실·장애가 날 확률 | Jitter 추세, RSSI 하락, 버퍼 사용률, 메모리 증가, 온도, 과거 같은 DUT·빌드 이력 | 문제가 나기 전에 경고·예방 조치 |
| 사전 점검 실패 가능성 | 장비 상태, 최근 사건 | 시작 전에 미리 준비 행동 |
| 시험 결과(PASS/FAIL) 조기 예측 | 초반 몇 시간의 5분 칸 패턴 | 100시간을 다 기다리지 않고 관리자에게 조기 보고(판정은 끝까지 규칙대로) |
| 문제 원인 | 사건 순서·패턴 | 원인 분석 문장 보강 |

### 제어 (무엇을 할까)
- 상황 특징 → 행동별 "성공 확률" 모델. 가장 높은 행동을 고르되, 가끔은 덜 시도된 행동도 시험해 본다(탐색). 탐색은 **안전한 행동 목록 안에서만.**
- 대기 시간·재시도 간격·경고 기준(노랑) 같은 **운영 값**도 결과에 따라 조정할 수 있다.

### 학습 방식
- 처음(데이터 적음): 2장의 통계 가중치.
- 데이터가 쌓이면: **온라인 학습 모델**(새 기록이 올 때마다 경사 하강으로 가중치 갱신). 학습률(경사 크기)은 처음엔 크게, 안정되면 작게 줄이고, 새 DUT·새 펌웨어처럼 **환경이 바뀌면 다시 키운다**(변화 감지).
- 더 쌓이면: 모델을 키운다(여러 층 신경망 등). 모델 구조는 모듈(`modules/learner/`)로 교체 가능하게.

### 안전장치 (반드시)
1. **판정 기준은 학습 대상이 아니다.** 손실 0%, 지터 150 ms 등 고정 판정 기준(05-standards 5.3~5.4)은 모델이 절대 바꾸지 못한다. 모델은 **운영(언제·무엇을 할지)**만 다룬다.
2. **그림자 모드부터:** 새 모델은 먼저 "예측만 하고 행동은 안 함" 상태로 돌려, 실제 결과·사람의 판단과 비교해 정확도를 잰다. 기준(예: 정확도 90%, 위험 행동 오판 0)을 넘어야 추천·자동 단계로 올린다.
3. **모델 버전 관리와 되돌리기:** 모델마다 버전·학습 데이터 범위·성능 기록. 성능이 떨어지면 자동으로 이전 모델로.
4. **설명 가능:** 추천·자동 행동마다 "왜"(주요 특징, 비슷한 과거 사례)를 함께 보여준다.
5. 위험한 행동은 모델 점수와 상관없이 항상 승인(3장).

## 3. 자동 대응 단계 (행동마다 관리자가 정함)
| 단계 | 동작 |
|------|------|
| 0. 기록만 | 기록만 남김(1차 기본) |
| 1. 추천 | Problems·Action Required 창과 메신저에 "추천: X (과거 9/10 성공)" 표시, 사람이 선택 |
| 2. 자동 후 보고 | 점수가 기준 이상이면 자동 실행하고 결과를 관리자에게 보고 |
| 3. 승인 후 자동 | 관리자에게 물어보고 승인(메신저 답장)되면 실행 |
- **위험한 행동은 절대 2단계(자동)로 두지 않는다:** 제거, Reset All, 장시간 시험 시작, 지휘 넘겨받기, DUT 설정 변경 → 항상 3단계(승인) 이상.
- 자동 대응도 09-exceptions의 재시도 제한을 따른다(같은 자동 대응을 무한 반복 금지).

## 4. 관리자와 메신저·이메일 (2차, 알림 모듈)
- 알림 모듈(L2, `modules/notify/`)로 만든다: 이메일, 메신저(예: Slack, Teams, Telegram 등 — 쓰는 곳에 맞춰 연결부만 추가).
- **보내는 것:** 시험 시작·완료·FAIL·장애, 사람 할 일(F22), 추천·승인 요청, 일일 요약.
- **받는 것(다음 지시):** 관리자 답장으로 명령. 예: `approve 1234`, `reset all`, `run plan-A`, `status`.
  - 명령은 CLI(13-ai-loop 2장)와 **같은 명령 목록**만 허용.
  - **등록된 관리자 계정에서 온 것만**, 승인 요청에는 1회용 확인 번호. 위험 명령은 확인 번호 필수.
  - 모든 원격 명령은 감사 기록 + 경험 DB 기록.
- Claude 원격 세션을 통한 지시(13-ai-loop 4장 A)와 함께 쓸 수 있다.
