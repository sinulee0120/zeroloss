# 12. 전체 구조: 오케스트레이션 + 시험 모듈

> **왜 Controller–Agent 구조인가:** ZeroLoss는 IPTV 시험 하나만 하는 도구가 아니라, **여러 PC·태블릿을 한 곳에서 지휘하는 시험 플랫폼**이다.
> IPTV 품질 시험은 **첫 번째 모듈**이고, 2차의 throughput(처리량) 시험, YouTube/Netflix형 시험 등은 **모듈을 추가하는 방식**으로 개발한다.
> 새 모듈을 추가할 때 **공통 틀(Core)을 고치지 않는 것**이 목표다.

## 1. 두 층으로 나눈다

```
┌──────────────────────── Controller ────────────────────────┐
│  Core (공통 틀)                                             │
│  발견·페어링·배포 · heartbeat·장애 처리 · 시험 생명주기      │
│  (Start/안정화/Stop/원복) · 상태 저장소 · Problems · 5분 칸  │
│  · 보고서 틀 · 화면 틀 · 설정 · 로그 · 버전                  │
│  ┌───────────── 모듈 ─────────────┐                         │
│  │ iptv (1차) │ throughput(2차)│ …   │ ← 모듈만 추가           │
│  └────────────────────────────────┘                         │
└────────────────────────────────────────────────────────────┘
              │ 제어 (10992) / 배포 (10991)
┌──────────────────────── Agent ─────────────────────────────┐
│  Core: API 서버, heartbeat, 프로세스 관리(Job Object 등),    │
│        파일 기록, 원복, 자원 감시, adb 중계, Deployer 연동   │
│  ┌──── 역할 모듈 ─────────────────────────┐                  │
│  │ iptv.sender │ iptv.receiver │ throughput.* │                  │
│  └────────────────────────────────────────┘                  │
└────────────────────────────────────────────────────────────┘
태블릿 앱도 같은 구조: Core(서비스·heartbeat·기록·USB 통신) + 모듈(iptv.tablet_receiver …)
```

| 층 | 하는 일 | 모듈이 바뀌어도 |
|----|---------|-----------------|
| **Core** | 장비 지휘, 시험 시작·정지·원복 순서, 장애 처리, 기록, 판정 틀, 화면 틀, 보고서 틀, 설치·업데이트 | **그대로** |
| **모듈** | 그 시험만의 송수신 방법, 지표 계산, 색·판정 규칙, 설정 항목, 사전 점검, 보고서 내용, 원인 분석 규칙 | 모듈 폴더만 추가·수정 |

## 1-0. 모든 PC는 같은 "노드", Controller도 역할 모듈 하나
> Controller도 **하나의 Agent(노드)**이고, **지휘(orchestrator)**는 그 노드에 올린 **메인 역할 모듈**이다.

```
모든 PC = ZeroLoss 노드
 ├─ L0 Deployer (10991)            ← 모든 노드 동일
 ├─ L1 노드 Core (10992)           ← 모든 노드 동일
 └─ L2 역할 모듈 (필요한 것만)
     ├─ controller  ← 지휘: 장비 관리, 시험 진행, 판정, 화면, 보고서  (지휘 PC 한 대에만 활성)
     ├─ iptv.sender / iptv.receiver / (2차) throughput.server / throughput.client …
```
- **최소 구성이 자연스럽게 된다:** 지휘 PC 한 대에 `controller` + `iptv.sender` 역할을 함께 켜면 끝(한 노드, 두 역할).
- **설치 파일 하나(노드):** 모든 PC에 같은 노드를 설치하고, 역할은 Controller 화면에서 켠다. Windows 설치 파일은 `controller` 모듈을 기본 포함하되, **지휘 PC 한 대에서만 활성**한다(06-install 2장의 Controller/Agent 설치 파일 구분은 이 구조로 대체).
- **지휘는 화면 없는 서비스에서 돈다(결정 2026-09-23):** `controller` 역할 모듈은 Controller PC의 **노드 서비스 안**에서 돈다(시험 진행, 판정, 상태 저장소, 보고서, 경험 DB). 화면 앱(**Controller Desktop**, PySide6)과 CLI는 둘 다 127.0.0.1:10994로 붙는 **창구**일 뿐이다(Agent Service/Agent Desktop과 같은 구조).
  - 화면을 닫거나 화면 앱이 죽어도 **시험은 계속**된다. 다시 열면 서비스의 현재 상태를 받아 그대로 그린다.
  - Windows에 로그인하지 않아도 CLI·원격(2차)으로 시험할 수 있다(노마드 목표). 화면 앱은 여러 개 떠도 같은 상태를 보여 주고, 명령은 서비스의 대기열 하나로 처리된다(11-ui 1.12).
- **Controller 자신도 Deployer로 업데이트:** 지휘 PC의 Deployer가 controller 모듈을 교체한다(다른 노드와 같은 방식).
- **지휘 역할은 한 네트워크에 하나:** 다른 노드에서 `controller`를 켜려 하면 기존 지휘 노드를 알려주고 넘겨받을지 묻는다(DSC-003과 같은 흐름).
- 원칙은 그대로: 지휘 역할은 **명령과 판정만** 하고 영상 데이터는 지휘 역할을 거치지 않는다(같은 PC에서 송신 역할을 함께 돌려도, 지휘 역할의 코드는 영상 데이터를 다루지 않는다).

## 1-1. 레이어와 포트 (포트 두 개로 나눈 이유)
| 레이어 | 구성 | 포트 | 바뀌는 빈도 |
|--------|------|------|-------------|
| **L0 기반(배포) 레이어** | Deployer: 설치·업데이트·복구·버전 조회·**같은 PC의 Agent 감시**(멈춤 감지 시 강제 재시작, `06-install.md`) | **TCP 10991** | 거의 안 바뀜. 항상 살아 있음 |
| **L1 노드 Core** (모든 PC 공통) | 발견·연결·heartbeat·시험 생명주기·기록·장애 처리·화면 틀 | **TCP/UDP 10992** | 가끔 |
| **L2 역할 모듈 레이어** | **controller(지휘, 메인)**, IPTV 송신·수신(1차), throughput(2차), … | 10992 위의 `/v1/modules/<id>/…` | 자주 (모듈 추가·수정) |

- **포트를 둘로 나눈 이유:** 설치·업데이트 통로(10991, L0)와 실제 동작 통로(10992, L1·L2)를 분리해서, **L1·L2가 죽거나 새 모듈을 올리는 중에도 L0로 언제든 고치고 올릴 수 있게** 하기 위해서다. 모듈이 늘어나도 포트는 늘리지 않는다(모듈은 10992의 경로로 구분).
- **의존 방향은 아래로만:** L2 → L1 → L0. 아래 레이어는 위 레이어를 모른다.
  - Core(L1)는 모듈(L2)을 **이름으로 가져다 쓰지 않는다.** 시작할 때 `modules/` 폴더에서 `module.json`을 찾아 **등록**하고, 모듈 계약(2장)의 함수로만 부른다.
  - Deployer(L0)는 Core·모듈의 코드를 쓰지 않는다. 패키지를 받아 설치할 뿐이다.
  - Deployer는 같은 PC의 Agent(L1)를 감시한다: Agent가 응답하지 않으면(멈춤) 강제 종료 후 재시작하고 사건을 기록한다. 재시작된 Agent는 이전 시험을 이어 하지 않는다(절대 원칙). Deployer 자신은 OS 서비스 자동 재시작으로 보호한다.
- **개발도 레이어별로 따로:** 레이어마다 폴더, 시험, 변경 이력을 분리한다. L2 작업이 L1·L0 파일을 고쳐야 한다면 먼저 모듈 계약에 항목을 추가하는 설계 변경으로 다룬다.
- 자동 검사: `core/`, `controller/`, `agent/` 코드가 `modules/`를 직접 import하면 빌드 실패.
- **HTTP 서버는 Python 표준 기능만**(`http.server` + 스레드, 2026-09-24 결정): 외부 의존 0개, 라이선스·PyInstaller 부담 없음. 요청이 초당 몇 개뿐이라 충분하다. 10994의 실시간 갱신(SSE)도 같은 방식. 경로 등록·요청 검사는 `core/protocol/`에 한 번만 만든다.

## 1-2. 기능 블록: 작게 나누고 한 번만 만든다
> 원칙: **모든 모듈은 기능별로 최소화**한다. 여러 모듈이 쓸 수 있는 기능은 모듈 안에 만들지 않고 **공용 기능 블록**으로 한 번만 만들어, 모듈은 블록을 **조립**만 한다. 중복 작업을 줄이는 핵심이다.

**공용 기능 블록 (Core 안 `core/blocks/`, 한 블록 = 한 가지 일)**
| 블록 | 하는 일 (한 가지) | 쓰는 곳 |
|------|------------------|---------|
| `process_runner` | 외부 프로그램 실행·감시·종료 확인·자식 프로세스 묶기 | tsp, ffmpeg, VLC·mpv, iperf3 … 모든 모듈 |
| `tool_locator` | 외부 도구 찾기·버전 확인 | 모든 모듈 |

| `adb_bridge` | adb 연결·명령·포트 연결·앱 설치 | 태블릿 쓰는 모든 모듈 |
| `recorder` | 1초 기록 파일(1시간 분할, 마감, 복구) | 모든 모듈 |

| `warmup_gate` | 시작·전환 안정화 판정 틀(조건은 모듈이 제공) | 모든 모듈 |
| `resource_monitor` | CPU·메모리·디스크 감시·경고 | 모든 구성 요소 |

**모듈에 남는 것 = 그 시험만의 것**
- IPTV 모듈: 송출 파이프라인 조립(ffmpeg + TSDuck), RTP/TS 규칙, 채널·전환, 재생기 연동, IPTV 판정 규칙표, IGMP·M2U 원인 분석 규칙
- throughput 모듈(2차): iperf3 실행 인자 조립, 처리량 판정 규칙표, 처리량 원인 분석 규칙

**규칙**
1. **한 블록·한 모듈은 한 가지 일만.** 이름으로 하는 일을 한 줄에 설명할 수 없으면 나눈다.
2. **두 번째로 필요해지면 블록으로:** 같은 로직이 두 번째 모듈(또는 두 번째 장소)에 필요해지는 순간 복사하지 말고 블록으로 옮긴다. 복사·붙여넣기 금지.
3. **블록은 모듈을 모른다:** 블록은 설정값을 받아 일만 한다. "IPTV면…" 분기 금지(4장 규칙 1과 같음).
4. **블록마다 자체 시험:** 블록 단위 자동 시험(10-verification 1.1의 합성 패킷 시험은 `seq_tracker`·`jitter_calc`·`ts_analyzer` 블록 시험이 된다). 모듈 시험은 조립이 맞는지만 본다.
5. **작은 입출력:** 블록 사이는 단순한 값(설정 → 결과)으로 주고받는다. 블록끼리 서로의 내부를 건드리지 않는다.
6. 새 기능 설계 순서: **① 기존 블록으로 조립 가능한가 → ② 안 되면 필요한 최소 블록 추가 → ③ 모듈에는 그 시험만의 규칙만.**

## 1-3. 모듈은 따로 설치·제거한다
> 기능을 작게 나누는 이유: **모듈 하나를 제거하고 다시 설치해도 Core와 다른 모듈에 아무 문제가 없어야** 한다.

- **모듈 = 독립 패키지:** `zeroloss-module-<id>-<빌드>.zlm` (모듈 코드 + `module.json` + 설치 목록 + SHA-256 목록). Controller·Agent·태블릿 앱에 **각각 따로** 올리고 내린다(Deployer 10991).
- **모듈 설치 목록:** 모듈이 만든 것(파일, 모듈 전용 외부 도구, 설정)은 **모듈 자기 설치 목록**에 기록하고, 제거할 때 그것만 지운다(06-install 원칙 그대로, 모듈 단위로). 형식은 02 13·14장, 위치와 순서는 06 12장(코드 폴더·설정·캐시).
- **공유 자원은 Core 소유:** 공용 블록, 포트, 방화벽 규칙, 서비스는 Core 것이다. 모듈 제거가 이것들을 건드리지 않는다. 여러 모듈이 쓰는 외부 도구(예: adb)는 **사용하는 모듈이 하나라도 남아 있으면 지우지 않는다**(사용 모듈 수 기록).
- **모듈 데이터 분리:** 모듈 설정은 `modules/<id>/` 설정 파일에만. 제거 시 설정 삭제 여부를 묻는다(기본: 보존 → 다시 설치하면 그대로 복원).
- **보고서는 모듈 없이도 열린다:** 보고서(report.html)는 필요한 내용을 모두 안에 담으므로, 모듈을 지워도 지난 보고서는 그대로 열린다.
- **호환 확인:** `module.json`에 필요한 Core 버전 범위(`core_api_min`, `core_api_max`)를 적는다. 맞지 않으면 그 모듈만 비활성(목록에 이유 표시), Core와 다른 모듈은 정상.
- **실행 중 추가·제거:** 시험 중에는 거부. 대기 상태에서는 Deployer가 그 PC의 노드 서비스만 다시 시작해 반영한다(몇 초, 사람 일 없음 — 2026-09-25, 06 12장. 이미 불러온 파이썬 모듈은 제자리에서 안전하게 바꿀 수 없어서). 제자리 다시 읽기는 2차 후보.
- **Controller 화면:** 장비 관리(S10)에 **Modules** 목록: 모듈별 설치 여부·빌드·장비별 설치 상태, [Install] [Remove] [Update].

## 2. 모듈이 Core에 알려주는 것 (모듈 계약)
모듈은 폴더 하나 + **모듈 정의 파일**(`module.json`) + 정해진 함수들로 구성된다.

| 항목 | 내용 | IPTV 예 | throughput 예(2차) |
|------|------|---------|---------------|
| `id`, `name`, `protocol_version` | 모듈 이름·통신 형식 번호 | `iptv` | `throughput` |
| **필요한 역할** | 어떤 장비가 무슨 역할로 필요한가 | sender 1, receiver_pc 0~1, tablet 0~3 | server 1, client 1~N |
| **설정 목록(스키마)** | 메인 설정(최대 10개, 2026-10-04) / Advanced 설정, 기본값, 범위, 도움말 문구, 연동 규칙 | Quality, Duration, 전송 방식… | 프로토콜 TCP/UDP, 방향, 스트림 수… |
| **사전 점검 단계** | 상태창(F17)에 보일 단계들 | 멀티캐스트 시험 송출… | 포트·도달 확인… |
| **시작·정지 순서** | 역할별 시작 순서, 안정화 조건, 정지 순서 | 송출 안정 → 수신 가입 → 안정화 | 서버 → 클라이언트 |
| **1초 기록·5분 요약 필드** | 기록할 값과 이름 | 손실, Jitter… | 처리량, 재전송… |
| **색·판정 규칙** | 5분 칸 색 계산, 최종 판정 | 05-standards 5.3~5.4 | (2차 정의) |
| **핵심 표시값** | 화면 맨 앞에 크게 보일 값 | Jitter, Packet Loss | Throughput, Retransmits |
| **원인 분석 규칙** | 결과 패턴 → 원인 후보 문장 | IGMP·M2U 규칙 | (2차) |
| **오류 코드** | 모듈이 내는 예외 | 09장 영역 코드(SND·RCV·NET·TAB …)를 그대로 쓴다 | 같음(새 상황은 09장에 먼저 추가) |
| **보고서 부분** | 보고서에 들어갈 모듈 전용 표·그래프 | TR 101 290 표 | 처리량 그래프 |
| **필요한 외부 도구** | 버전 정책 포함 | ffmpeg, TSDuck, VLC(기본)·mpv(옵션), adb | iperf3 |
| **검증 시험** | 10-verification 형식의 모듈 시험 | 합성 패킷·netem | 알려진 대역폭 제한 |

**`module.json` 필수 필드 (1차, 2026-09-24):**
```json
{ "id": "iptv", "name": "IPTV streaming", "protocol_version": 1,
  "core_api_min": 1, "core_api_max": 1,
  "entry": "modules.iptv.module:create",
  "run_entry": "modules.iptv.run:create",
  "roles": ["sender", "receiver"],
  "tools": { "sender": ["ffmpeg", "ffprobe", "tsp"], "receiver": ["vlc"] } }
```
- `tools`(선택): 역할마다 필요한 외부 도구 이름(15장). 노드는 켜진 모듈들의 도구를 찾아 `/v1/info` `tools`로 알리고(`core/blocks/tool_locator.py`), Controller는 `run_entry.required_tools(plan, device)`로 이번 계획에 실제로 필요한 것만 본다(예: 재생 끔이면 VLC 불필요). F17 2단계(2026-09-25).
- `id`는 폴더 이름과 같아야 한다(소문자·숫자·`_`). `entry`는 Core가 문자열로만 불러오는 진입점(`모듈경로:함수`) — Core 코드에 모듈 이름을 쓰지 않기 위해서다.
- `media_import`(선택, 2026-10-03, 20장 GAP-109): `{"from": "Videos", "into": "media", "ext": ["mp4", …]}` — 데스크톱 사용자 폴더(`/home/<사용자>/<from>`, 맨 위 파일만)의 그 확장자 파일을 노드 데이터 폴더의 `<into>`로 **Deployer(L0, root)가** 가져온다. Deployer는 시험 종류를 모르고 설치된 모듈이 적은 대로만 한다(모듈이 없으면 아무것도 안 함). 규칙: ① 노드가 IDLE일 때만(Deployer가 1초마다 보는 health 상태), 60초마다 ② 다른 사람도 읽을 수 있는 파일은 **하드 링크**(복사 없음, 원본의 주인·권한은 절대 안 바꿈), 아니면 여유(파일 크기 + 1 GB)가 있을 때만 **복사**(주인 `zeroloss`) ③ 원본이 바뀌면(inode·크기·수정 시각) 다시, 원본이 없어지면 가져온 것을 지움 ④ `<into>`에 사람이 넣은 같은 이름 파일은 건드리지 않음 ⑤ 가져온 것은 `<into>/.imported.json`에만 적고, 노드 제거·그 모듈 제거 때 정확히 그것만 지움(G-11, 1-3).
- `desktop_entry`(선택, 2026-09-26, 03 F20): Agent Desktop 쪽 진입점. `jobs` = 화면 작업 종류별 만들기 함수(IPTV: `player` → 재생기 부품), `status_rows(module_data)` = 상태 창에 그릴 줄(제목·상태 색·큰 값·줄). Desktop은 이것으로만 모듈별 화면 일을 한다.
- `run_entry`(선택): Controller 쪽 진입점. 시험 계획 검사, 역할별 시작·정지 명령, 5분 요약 → 칸 입력 변환(판정 규칙)을 준다. Controller는 이것으로만 시험 종류별 규칙을 쓴다(2026-09-24).
  - 프라임 방식(2026-09-25, iptv 4.5, 선택): `probe_fallback(plan)` → 멀티캐스트 시험 송출이 NAT 뒤에서 아무에게도 안 갔을 때 다음에 시험할 계획(없으면 `None`), `path_note(plan)` → `{"path", "note"}`(보고서 `dut.multicast_path`·체크리스트). Controller는 계획의 뜻을 모르고 이 둘만 부른다. 계획에는 Controller가 `hosts`(02 11-1)를 채워 준다.
  - 원본 영상 목록(2026-09-26, 선택): `sources_step(device)` → 그 장비에 물을 노드 경로(S-48 목록, 02 2-10).
  - F17 4단계 PC 성능(2026-09-26, 선택): `device_checks(plan, light)` → 장비별 점검 단계 목록(가벼운 점검이면 `light=True` — 저장된 결과만). 답에 `warn`(`{code, what, why, fix}`)이 있으면 Controller가 ⚠로 적는다.
  - F17(2026-09-25): `required_tools(plan, device)` → 도구 이름 목록, `disk_need_mb(plan, device)` → 이번 시험에 그 장비가 쓸 디스크(MB), `probe_steps(plan)` → 시험 송출 단계(수신 듣기 → 송신 → 결과).
  - `link_need(plan, device)` → `{"bps": 필요 대역, "label": "WAN"|"LAN"}`: 그 장비의 시험 NIC가 실어야 하는 양(05 1.8). Controller는 이것으로 NET-012(시작 전)·NET-013/014(시험 중)를 판단한다(2026-09-24).
  - `trouble_of(plan, device, code, data)` → `"sender"` / `"sender_slow"` / `"receiver_link"` / `None`: 이 사건이 어느 문제 구간을 여는지(05 5.3, 2026-09-26). 구간을 닫는 것은 그 코드를 `clears`에 가진 사건. `second_records(plan, device, module_data)` → 수신기별 `(key, 1초 기록)`: Controller가 받은 시각과 함께 보관해 칸을 나눈다. `cell_color(summary, jitter_warn_ms)`는 줄의 `trouble`을 읽는다.
  - `live_row(plan, module_data, memo)` → 장비 줄(`memo`는 Controller가 장비마다 들고 있는 모듈 몫의 빈 dict, 이번 칸의 나쁜 색 유지용)(핵심 표시값, 02 2-1 `row`). 화면은 `row`의 글자·색만 그리고 모듈 필드를 읽지 않는다. 줄 내용·아이콘 규칙은 11-ui 3장(2026-09-24, 20장 GAP-35).
  - 자체 검사(2026-09-27, 선택, 20장 GAP-81): `self_checks()` → `[(suite, name, fn)]` — `zeroloss verify`가 Core 검사와 함께 돌린다. `suite`는 `accuracy`(10장 1.1: 답을 아는 합성 패킷을 실제 분석기에) / `judgement`(05 5.3·5.4 표의 모든 줄). `fn()`은 통과면 짧은 설명을 돌려주고, 틀리면 이유와 함께 예외. 장비·네트워크·외부 도구 없이 몇 초 안에 끝나야 한다.
  - 원인 분석(2026-09-27, 선택, iptv 2.4, 20장 GAP-85): `analysis(plan, data)` → `{"findings": [...], "missing": [{"rule", "why"}]}` — `data`는 `summaries`(5분 요약), `events`(회차 사건, `run_s`), `seconds`(장비·채널 → 1초 기록, 없으면 `None`), `offsets`(timeline.json). 판정·색을 바꾸지 않는다.
- 진입 함수가 돌려주는 객체는 `attach(node)`(경로·heartbeat 값 등록)와 `safe_stop(reason)`(송출·수신·재생·동반 작업을 멈추고 확인)을 갖는다. `safe_stop`은 **노드가 IDLE이어도 불린다** — 노드를 활성으로 만들지 않는 모듈 작업(IPTV 영상 만들기, iptv 1-1-2)도 새 Controller·노드 종료 때 멈추게(2026-09-25, 20장 GAP-50). 나머지 계약 항목(설정 스키마, 사전 점검 단계 …)은 해당 기능을 만들 때 필드를 추가한다.
- 검사 실패(파일 없음·JSON 오류·필드 누락·`core_api` 범위 밖·진입점 오류)는 **그 모듈만 비활성**으로 두고 이유를 기록한다(1-3 호환 확인).

## 3. Core가 모듈에 주는 것 (모듈이 다시 만들지 않는 것)
- 장비 발견·선택·페어링, 설치·업데이트(모듈의 도구·파일도 Deployer로 배포)
- 시험 생명주기: 상태 흐름(IDLE → STARTING → RUNNING → STOPPING → IDLE, FAULT), Start/Stop 버튼, 연타 방지, 정리 중 잠금, 원복, 결과 팝업
- heartbeat·장애 처리 정책(F11), 부분 보고서(F10), 복구
- 1초 기록 파일(1시간 단위·정상 마감·복구), 5분 요약 수집, 5분 칸 그리드 틀(색은 모듈이 계산)
- Problems 창, 오류 표시 부품(What/Why/Fix), 문구 파일, 디자인 값
- **모듈 폴더:** `node.module_dir(<id>, "settings")`(제거 때 남음)·`node.module_dir(<id>, "cache")`(제거 때 지움) — 모듈은 데이터 폴더 구조를 직접 조립하지 않는다(06 12장, 2026-09-25)
- **설정 화면 자동 생성:** 모듈의 설정 스키마로 메인 설정·Advanced 화면을 Core가 만든다 → 모든 모듈 화면이 같은 모양·같은 규칙(11-ui 1.10~1.11)을 자동으로 따른다
- 보고서 틀(표지, 판정, 5분 칸, 구간 보기, 문제 목록) + 모듈 부분 끼워 넣기
- 조작 상태표(11-ui 1.10)의 공통 부분

## 4. 규칙
1. **Core에 시험 종류별 코드를 넣지 않는다.** "IPTV면 이렇게" 같은 분기는 Core에 없어야 한다. 필요하면 모듈 계약에 항목을 추가한다.
2. **모듈끼리 직접 부르지 않는다.** 모듈은 Core를 통해서만 통신한다.
3. **모듈 추가 = 폴더 추가:** `modules/<id>/`(Controller·Agent 공통 Python), 필요하면 `android/modules/<id>/`. Core 코드 수정 없이 목록에 나타나야 한다.
4. **통신 경로:** 공통 API는 `/v1/...`, 모듈 API는 `/v1/modules/<id>/...`. 데이터 형식은 공통 봉투(02-data 3장) + 모듈 전용 내용(`module_data`).
5. **한 번에 한 시험:** 1차는 Controller 하나가 한 번에 모듈 하나의 시험만 돌린다(동시 여러 모듈 시험은 범위 밖).
6. **모듈별 버전 호환:** 모듈 `protocol_version`이 Controller와 Agent에서 다르면 그 모듈 시험만 막고, 다른 모듈은 사용 가능.
7. 1차 개발에서도 IPTV를 **모듈로** 만든다. Core와 IPTV 모듈의 경계가 흐려지면 2차에서 다시 뜯어고치게 된다.

## 4-1. 이벤트 내보내기: 외부 로깅 장비 연동 (2차, 모듈)
> 문제가 되는 순간 **별도의 외부 장비**(패킷 캡처 장비, 네트워크 분석기, 로그 서버, 계측기 트리거 등)가 이벤트를 받아 **자기 쪽 기록·캡처를 시작**할 수 있게 한다.

- **1차에서 할 일(틀만):** 모든 사건은 이미 표준 형식(02-data 8장 `events.log`, 오류 코드, UTC 시각, 장비, 경과 시각)으로 Core의 **사건 흐름(event bus)** 하나를 지나가게 만든다. 나중에 내보내기 모듈이 여기에 붙기만 하면 되게.
- **2차: `modules/event_out/`(L2 모듈)** — 사건 흐름을 구독해 외부로 보낸다. 출력 방식은 연결부만 추가:
  | 방식 | 용도 예 |
  |------|---------|
  | Syslog (RFC 5424) | 사내 로그 서버·SIEM |
  | HTTP 웹훅(JSON) | 사내 시스템, 알림 |
  | MQTT | 여러 장비가 구독하는 이벤트 버스 |
  | SNMP Trap | 네트워크 관리 시스템 |
  | 트리거 신호(시리얼·GPIO·USB 릴레이) | 외부 패킷 캡처 장비·계측기 녹화 시작 |
- **규칙:**
  - 보낼 사건 종류·등급을 고른다(예: 빨강·재생 이상·장애만). 너무 잦으면 묶어서 보냄.
  - 이벤트에 **앞뒤 몇 초를 기록하라는 요청 창**(예: −10 s ~ +5 s, F23 증거와 같은 구간)을 함께 넣어, 외부 장비가 순환 버퍼에서 같은 구간을 잘라 저장할 수 있게 한다.
  - **시각이 생명:** 외부 장비와 시각을 맞춰야 서로 대조할 수 있다. Controller 기준 시각 + 추정 오차를 싣고, 장비가 PTP/NTP를 지원하면 Controller를 시각 기준으로 제공하는 방안을 함께 검토.
  - 내보내기 트래픽은 **시험망(DUT)으로 보내지 않는다.** Controller의 외부용 NIC(13-ai-loop 1장) 또는 별도 관리망으로만.
  - 외부 장비가 응답 없어도 시험은 영향 없음(보내기 실패는 기록·재시도만, 무한 재시도 금지).
  - 외부 장비의 캡처 결과(파일 위치·ID)를 받아 보고서의 해당 사건에 링크할 수 있게 응답 형식을 열어 둔다.

## 4-2. 공유기(DUT) 쪽 동시 실행: DUT 모듈 (2차부터, 명시적으로 켤 때만)
> 시험하는 동안 **공유기 쪽에서도 동시에 읽어야** 할 수 있다: 공유기 로그 기록, 문제 순간 공유기 내부 상태 확인. 공유기 설정을 바꾸는 일은 없다.
> 설계 원칙 5(도구는 DUT에 로그인하지 않음)의 **유일한 예외**로, `modules/dut/` 모듈을 **DUT별로 명시적으로 허용했을 때만, 읽기 전용으로** 동작한다. 기본은 꺼짐.

**DUT 접근 규칙(한 곳, 2026-10-02 변경):** ① 기본: 도구는 DUT에 로그인하지 않는다(IPTV·throughput을 포함한 모든 모듈). ② 유일한 예외: 본인 공유기에 **명시적으로 켠 DUT 모듈**(`modules/dut/`, 2차)이 **읽기 전용**(로그 기록·상태 떠 오기)만 한다. ③ **어떤 모듈도 공유기 설정을 바꾸지 않는다** — 무선·WAN 설정, 펌웨어 올리기 모두 없음(사용자 2026-10-02, 20장 GAP-93). 처리량 시험은 측정 PC의 NIC 설정만 바꾼다(throughput.md 1장). ④ 다른 문서는 이 규칙을 되풀이하지 않고 여기를 가리킨다.

| 기능 | 방식 | DUT 접속 | 단계 |
|------|------|----------|------|
| **공유기 로그 동시 기록** | ① 시리얼 콘솔(USB-시리얼)을 Controller나 가까운 노드에 연결해 **읽기만** ② 공유기가 보내는 syslog를 받음 | 읽기 전용(로그인 불필요한 경우 우선) | 2차 |
| **문제 순간 공유기 상태 떠 오기** | 사건(빨강·재생 이상) 때 미리 정한 **읽기 전용 명령**만 실행: IGMP 스누핑·멤버십 표, 멀티캐스트 전달 표, M2U 상태, CPU·메모리, 무선 클라이언트 목록·전송 속도 | 로그인 필요 → 허용 시에만 | 2차 |

**규칙**
- DUT 접속 정보는 DUT별로 암호화해 Controller에만 저장, 화면·로그·보고서에 남기지 않음.
- 실행 가능한 명령은 **DUT 종류별 허용 목록**에 있는 것만(임의 명령 금지). **읽기 명령만** 허용한다(쓰기 명령은 허용 목록에 둘 수 없음, 2026-10-02).
- **측정 오염 방지:** DUT 로그·명령 트래픽은 가능하면 **시리얼 콘솔**로(시험 네트워크를 안 탐). 네트워크로 해야 하면 유선 LAN 쪽, 양을 기록하고 보고서에 표시. 상태 떠 오기는 공유기 CPU에 부담이 될 수 있어 **사건당 1회, 최소 간격(기본 60초)** 제한.
- 공유기 로그와 ZeroLoss 사건을 **같은 시각 축**에 맞춰 보고서에 나란히 표시(공유기 시각과 Controller 시각 차이를 로그 시작 때 기록해 보정).
- 공유기 쪽 동작이 실패해도 시험은 계속(기록만).
- 보고서: "Router logs" 구간 보기, 사건마다 "Router state at that moment" 첨부.

## 4-3. 동반 작업(Companion task)의 실행과 멈춤
> 패킷 캡처(4.7), 외부 로깅 장비 트리거(4-1), 공유기 로그·공유기 쪽 프로그램(4-2)처럼 **시험과 함께 돌아가는 작업**은 모두 같은 틀로 **켜고 끄는 것까지** 관리한다. 켜 놓고 안 끄거나, 끄다 멈춰서 남는 일이 없게.

**모든 동반 작업이 갖는 것(Core 틀, 모듈은 내용만 채움)**
| 항목 | 내용 |
|------|------|
| 필수 여부 | **필수**(없으면 시험 시작 안 함) / **선택**(실패해도 시험 계속, 기록만) |
| 시작 | 시작 명령 → **준비 확인**(예: 캡처 파일이 생기기 시작함, 공유기 로그 첫 줄 도착) → 제한 시간(기본 10초) |
| 상태 감시 | 살아 있는지 1초마다(heartbeat와 함께), 멈춤 감지(할 일을 안 하고 있음) |
| 멈춤 | 정상 멈춤 명령 → **멈춤 확인** → 제한 시간(기본 15초) 넘으면 강제 종료 → 강제 종료 확인 |
| 정리 | 만든 파일 마감, 임시 설정 원복(예: 공유기 쪽에서 켠 디버그 기능 끄기), 남은 프로세스 없음 확인 |
| 결과 | 보고서에 시작·멈춤 시각, 실패·강제 종료 여부 |

**시험 순서 안에서의 자리**
```
Start:  사전 점검 → [동반 작업 시작·준비 확인] → 송출 → 수신·안정화 → 측정
Stop:   측정 마감 → 재생·가입 해제 → 송출 정지 → [동반 작업 멈춤·확인·정리] → 원복 → 보고서
```
- 동반 작업은 **측정보다 먼저 켜고, 측정이 끝난 뒤 끈다** → 측정 구간 전체가 캡처·로그에 들어감.
- **남는 프로세스 막기(2026-09-25, 20장 GAP-48):** ① ZeroLoss가 띄우는 모든 외부 프로그램은 Core 블록 `process_runner` 하나로만 띄운다(부모가 죽으면 같이 죽게 묶음: Linux 새 세션 + 부모 사망 신호, Windows Job Object). 예외: 제한 시간이 있는 짧은 호출(`iw` 조회), 그리고 Core 코드를 쓰지 않는 Deployer(L0)의 OS 명령(서비스 `systemctl`·`sc`·`taskkill`, 설치 스크립트 `adduser`·`sysctl`·`ufw` — 06 4.3-1, 제한 시간 필수, 2026-09-25) — 둘 다 검사 시험의 허용 목록에만. ② 실행 기록(이름·PID·실행 토큰)은 **노드 한 폴더 `<데이터>/procs`**에 둔다. ③ **노드가 시작할 때 그 폴더를 보고, 토큰이 맞는 남은 프로세스를 모두 끈다**(SYS-007, Problems ⚠). ④ 자동 시험: 노드를 별도 프로세스로 띄워 송출·재생 중에 강제 종료(kill -9)해 남은 것이 없는지, 다시 켰을 때 기록이 정리되는지 확인.
- **누가 언제 멈추나(20장 G-12):** 새 스레드·외부 프로세스를 만들면 여기에 한 줄 더한다.

  | 작업 | 만드는 곳 | 멈추는 길 |

- 멈춤이 끝나지 않으면 버튼은 Stopping…에 머물고 상태창에 어느 작업이 멈추는 중인지 표시(F13). 강제 종료까지 실패하면 FAULT로 가서 사람 할 일(F22) 안내.
- 장애 정지·Reset All·Shut Down All(F11)·Controller 끊김으로 인한 Agent 안전 정지 때도 **동반 작업까지 모두 멈춘다.** 공유기 쪽에서 켠 것(디버그 로그 등)도 되돌린다.
- 재시작된 Agent·Controller는 **이전 시험의 동반 작업이 남아 있는지 먼저 찾아 정리**한다(ZeroLoss가 만든 것만, 이름·ID 기록으로 식별).
- 몽키·장애 주입 시험(10-verification 4-2)에 동반 작업 켜고 끄기, 멈추는 중 강제 종료, 멈춤 확인 실패를 포함한다.

## 4-4. 장애 복구 구조: 감독과 지휘 이어받기 (2026-09-24, 근거 18장 6절)
> 질문: Controller가 죽으면 Agent가 이어받을 수 있나? Agent가 망가지면 Controller가 고쳐 주나? 분산 시스템 연구의 답을 단계별로 적용한다. **절대 원칙(주인 없는 시험은 안전 정지, 재시작된 장비는 이전 시험을 이어 하지 않음, 지휘 넘겨받기는 사람 확인)은 바꾸지 않는다.**

**1차 (지금 구조, 이미 구현·설계됨)**
| 생각 | 근거 | ZeroLoss |
|------|------|----------|
| 감독자가 죽은 부품을 정해진 방법으로 다시 켠다(감독 트리) | Armstrong 2003 (Erlang/OTP supervisor) | Deployer(L0)가 Agent를 감시·강제 재시작(SND-018), Agent가 tsp를 한 번 재시작(SND-005), `process_runner`가 자식까지 정리 |
| 복구는 "끄고 다시 켜기" 하나로, 재시작하면 알려진 처음 상태 | Candea·Fox, Crash-Only Software 2003 | 재시작된 Agent·Controller는 이전 시험을 이어 하지 않음(boot_id), 남은 프로세스는 표식으로 정리(SYS-007) |
| 죽었다고 단정하기 전에 "의심" 단계 | SWIM 2002 (suspicion) | heartbeat 3 s 의심 → 10 s 사망(F11) |
| 지휘권마다 늘어나는 번호를 명령에 붙이고, 받는 쪽은 옛 번호를 거부 | Chubby 2006 (lock acquisition count), 리스 Gray·Cheriton 1989 | `generation` + `X-ZL-Controller-Boot`(DSC-011, CTL-008): 옛 지휘자·늦게 온 명령은 실행 안 됨 |
| 원하는 상태와 실제 상태를 계속 비교해 맞춤(조정 루프) | Kubernetes 컨트롤러 패턴 | Reset All·원복 확인(F11), 깨끗한 상태 점검 |

**2차 후보 — 더 정확한 사망 판단**
- 고정 10 s 대신 heartbeat 도착 간격 분포로 "의심 정도"를 계산(φ accrual, Hayashibara 외 2004). 무선·느린 PC에서 헛사망을 줄인다.
- 1차에서 할 일: heartbeat 왕복 시간을 장비별로 기록해 둔다(분포 자료). 판단 방식 변경은 그림자 모드부터(14장).

**3차 후보 — 대기 Controller의 지휘 이어받기**
- 조건: ① 리스(지휘권 유효 시간)를 가진 지휘자 한 명 ② 이어받을 때 `generation`을 올려 옛 지휘자를 막음(펜싱) ③ **두 지휘자 동시 지휘(split-brain) 금지**.
- 합의 알고리즘(Raft, Ongaro·Ousterhout 2014)은 **과반수**가 필요해 3대 이상에서만 안전하다. PC 2~3대 시험실에서는 Chubby처럼 **외부 심판**(예: 항상 켜진 Deployer 한 곳의 잠금)을 쓰거나 사람 확인을 유지한다.
- 이어받아도 **끊긴 시험은 이어 하지 않는다.** 새 지휘자는 남은 자료를 회수하고 보고서(INCOMPLETE)를 만든 뒤, 사람이 새 시험을 시작한다.
- 기본은 꺼짐. 켜려면 관리자 설정 + 이어받기 때마다 기록(경험 DB).
