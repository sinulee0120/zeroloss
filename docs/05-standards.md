# 05. 송수신 표준 (반드시 적용)

> 목적: **송신과 수신 도구 자체가 공유기(DUT) 검증 결과에 영향을 주지 않게** 한다.
> 측정값에 문제가 보이면 그 원인이 DUT에 있다고 말할 수 있어야 한다. 그러려면 송신·수신 쪽은 표준을 지키고, 스스로 만든 손실과 지연을 따로 세어 증명해야 한다.
> 이 문서의 규칙은 코드 구현 시 **예외 없이** 따른다. 옵션 이름 등 구체 값은 구현 단계에서 사용하는 도구 버전으로 다시 확인한다.

## 1. 적용 표준 목록

> **필수** = 요구사항. 구현이 반드시 따르고, 준수 여부를 시험으로 확인한다.
> **참고** = 설계·해석에 참고. 구현 의무는 없다.

### 1.4 품질 지표 계산 (필수)
| 표준 | 제목 | 적용 |
|------|------|------|
| **ETSI TR 101 290 V1.4.1**(2020-06, 전엔 V1.2.1 인용) | DVB Measurement Guidelines | Priority 1(TS sync loss, Sync byte, **PAT_error_2(1.3.a)**, CC, **PMT_error_2(1.5.a)**, PID 오류), Priority 2 중 **TEI(2.1)·CRC(2.2)는 세기만**(2026-09-25), PCR 반복·정확도·PTS는 2차 |
| **RFC 4445** | A Proposed Media Delivery Index (MDI) | **DF**(Delay Factor, ms), **MLR**(Media Loss Rate, 패킷/초) |
| **RFC 3393** | IP Packet Delay Variation Metric (IPDV) | 도착 간격 변동. RTP가 없을 때 Jitter 대체 |
| **RFC 5481** | Packet Delay Variation Applicability Statement | 지연 변동 지표 선택·표시 방법 |
| **RFC 3357** | One-way Loss Pattern Sample Metrics | 연속 손실(버스트) 길이와 간격 |
| **RFC 7680** | A One-Way Loss Metric for IPPM | 단방향 손실 정의 |

- **TR 101 290 시간 기준 (원문 V1.4.1 근거, 2026-09-25 사용자 결정 20장 GAP-42 ①):**
  - **PAT·PMT는 1.3.a·1.5.a(V1.4.1이 1.3·1.5의 대체로 권고):** 시간은 PID 패킷이 아니라 **완전한 구간(section)** 기준 — PID 0에서 table_id 0x00 구간이, **PAT에 적힌 각 program_map_PID**에서 table_id 0x02 구간이 0.5초 넘게 없으면 오류. PID 0에 table_id 0x00이 아닌 구간, 스크램블 비트가 00이 아닌 패킷도 오류(NOTE 3: 100 ms 권장, 0.5 s 확인으로 충분). 구간이 패킷 여러 개에 걸치면 모아서 본다.
  - **TEI(2.1)·CRC(2.2):** TS 헤더의 transport_error_indicator = 1인 패킷 수, PAT·PMT 구간의 CRC-32가 틀린 수를 **세기만** 한다(1초 `tei`·`crc`, 5분 `ts.tei_err`·`crc_err`). 우선순위 1 합계(`p1`)·칸 색·판정에는 넣지 않고 원인 분석 참고로 쓴다. CRC가 틀린 PAT·PMT 구간은 내용도 쓰지 않는다(없는 것으로 봄 → 1.3.a·1.5.a 시간에 반영).
  - PID 오류(1.6): **영상·소리 PID 5초**(원문: "should not exceed 5 s for video or audio PIDs", 상한이므로 늘리지 않음). 자막·데이터 PID와 ISO 639 audio_type > 0인 소리는 원문대로 **검사 제외**. 설정 항목 아님(고정).
  - 기준 시간은 첫 PAT·첫 PMT·PMT에 처음 적힌 시각부터 센다(2.1-2 경계 규칙).

### 1.6-1 통신사가 공개한 공유기 요구사항 예시 (2차: 해외 통신사 프로파일의 근거)
> 대부분의 통신사 요구사항서(RFP·장비 규격)는 **비공개(NDA)**다. 다만 규제(유럽 "공유기 선택 자유" 등)나 도매 개방 때문에 **공개하는 곳**이 있다(Exa로 확인, 2026-09-23).

| 문서 | 공개 주체 | 공유기·IPTV 관련 핵심(요약) |
|------|-----------|-----------------------------|
| **SIN 511** (TV Connect) | BT Wholesale (영국) | 공유기는 **IGMP Proxy + Snooping**, **IGMPv3 필수**(ASM만), 가입 요청 2회(Robustness 2), 요청 간격 1초, IGMP에 우선순위(802.1p ≥3), 채널당 최대 30 Mbps, 재전송(RET) 선택 |
| **SIN 503** (Multicast for GEA) | Openreach (영국) | 빠른 탈퇴(fast leave), 질의 출발 주소 0.0.0.0에도 응답, 동시 가입 16개 제한, **23비트 MAC 겹침 금지**, RFC 4605 Proxy 권장, TR-101·TR-156 참조 |
| **SIN 498** (GEA FTTC 모뎀) | Openreach | VLAN 101, IGMPv2/v3, 멀티캐스트 처리 적합성 시험 항목 |
| **1TR112** | Deutsche Telekom (독일) | 고객 장비 기술 규격(공개). 실제 서비스는 **IGMPv3 + SSM(232.0.0.0/8, 출발지 지정)**, 멀티캐스트 전용 VLAN 사용 |

- **1차 IGMP 방식:** 수신기는 OS 기본 방식(보통 IGMPv3 보고, 출발지 지정 없는 ASM 가입)을 그대로 쓰고 바꾸지 않는다. 대신 **실제로 쓰인 IGMP 버전을 수신기마다 기록**해 보고서 "Test setup"에 적는다(Linux `/proc/net/igmp`, Windows `netsh interface ipv4 show joins`·인터페이스 IGMP 설정, Android는 알 수 없으면 "OS default (unknown)", Linux PC 캡처가 켜져 있으면 캡처로 확인). 공유기가 v2로 낮추는 경우(질의 버전 변화)도 사건으로 기록한다.
- **ZeroLoss에 주는 시사점:** 1차(한국, VLAN 없음·239 대역)는 그대로 두되, 2차 해외 확장 때 **통신사 프로파일**(IGMP 버전, ASM/SSM, VLAN, 가입 요청 횟수·간격, 동시 가입 수)을 설정 묶음으로 추가할 수 있게 한다(16-settings에 항목 추가 예정). 위 공개 문서의 요구사항은 그대로 **시험 항목 목록**으로 바꿀 수 있다.
- 한국 통신 3사의 공유기·IPTV 요구사항서는 공개 자료를 찾지 못했다(일반적으로 비공개). 국내 표준은 1.6-2 참고.

| 부트 | 웜 부트 시간 | 절전 대기에서 전원 버튼 → 메인 메뉴 표시 또는 실시간 방송 재생 |

| 기능 | 기능 진입 시간 | 버튼 입력 → 해당 기능 주 메뉴 표시 완료 (전용 버튼 / 홈메뉴 경로 따로 관리 가능) |

| 전환효과 | FPS / 프레임 균일도 / Jerkness | 초당 화면 갱신 수 / **프레임 간격의 표준편차** / 프레임별 이동량의 2차 미분 |
| 성공률 | 반응 성공률 | 같은 조작을 반복했을 때 정해진 시간 안에 정상 반응한 비율. 조작 종류·간격·반복 수에 따라 달라짐 |
- **채널 전환 보조 지표:** 현재 채널 멈춤(정지 화면·검은 화면), 다음 채널 첫 프레임 표시, 다음 채널 낮은 FPS 재생 시점. **다음 채널 멀티캐스트 Join 같은 네트워크 사건 시각도 보조 지표로 관리할 수 있다**고 명시.
- **입력 시점:** 명령 단위의 마지막 버튼 Press 시점. 측정 시스템이 신호를 직접 만들면 시스템 시각을 쓴다. 입력 간격은 입력 타임아웃의 80% 미만, 필터링 간격의 120% 이상.
- **영상 수집:** 카메라 촬영(출력 FPS의 2배 이상, 화면 비율 50% 이상, 자동 초점 끔, TV 화질 개선 끔) 또는 HDMI 캡처(캡처 지연 편차가 요구 정확도보다 작아야 함).
- **분석 제외 조건:** 화면 변화가 정지 화면 잡음의 5배 이하(안개·정적인 장면 등), 전환 전후 프로그램·광고가 바뀜, 잡음이 평소의 2배 이상, OSD가 화면을 덮음. 제외했으면 제외 기준을 함께 적는다. 알고리즘과 육안 판정 차이는 보통 1~2 프레임.

*TTAK.KO-01.0222 셋톱박스 UI 메뉴 구조 자동 탐색 (2019-12-11, 21쪽)*
- 캡처 장치 + IR 송신기로 화면을 읽어 메뉴 구조를 자동으로 파악하고, 목표 메뉴까지 리모컨 이동 조합을 찾는다.
- 화면마다 커서 위치(강조 표시·테두리) → 화면 이름·항목 이름(OCR, 기준 메뉴표와 편집 거리 비교) → 고유 ID "화면 > 항목"을 만든다. ID별 상/하/좌/우 이동 결과표를 빈칸이 없어질 때까지 채운다(같은 ID거나 깊이를 넘으면 막다른 곳). 경로 탐색 후 도착 ID를 다시 확인하고, 다르면 반복한다.

**ZeroLoss 적용**
- 1차 판정 기준(손실·지터)에는 넣지 않는다. 두 표준은 셋톱박스·수신기 반응 지표다.
- **채널 전환 시간(F19):** 끝점은 표준대로 "다음 채널 정상 재생(정상 FPS + 소리)"으로 한다. 보조 시각으로 IGMP Join 송신, 첫 패킷, 첫 프레임 표시를 함께 기록한다(표준이 네트워크 사건을 보조 지표로 허용). 공유기 몫(Join→첫 패킷)과 수신기 몫(첫 패킷→정상 재생)을 나눠 보고한다. 우리는 영상 속 프레임 번호 표식과 재생기 속성으로 판정하므로 카메라·분석 제외 조건 문제는 없다.
- **반응 성공률:** F19 자동 반복 전환에서 "정해진 시간(S-47, 기본 5초, 0.5~30초 조정) 안에 정상 재생된 전환 비율"을 기록 지표로 보여 준다(판정 아님).
- **프레임 균일도(프레임 간격 표준편차):** 재생 이상 감지(iptv 3장)의 수신단 원인 참고 지표 후보. 2차에서 검토.
- 01.0222는 3차 "사람 손 대체"(셋톱·태블릿 메뉴 자동 조작)에서 참고.
- 참고 값(공개 평가 보도, 표준 값 아님): 2022 유료방송 품질평가 채널 전환 평균 약 1.48초, IPTV 0.7~1.9초, UHD→UHD 최대 약 3.2초. 셋톱 웜 부트 평균 약 2.8초.

**국내 연구 (참고)**
- 김범준·김진철·박재성, "IPTV 서비스 품질의 사전 관리를 위한 서비스 이용자 중심의 상시 측정 방안 구현과 검증", 정보처리학회논문지 C, 2011 — **셋톱박스 안에서 품질을 상시 측정**(단방향 지연, 패킷 손실률(RTP 순번), 지터, MDI-DF, TS Sync Loss, CC 오류, 손상된 I/P/B 프레임)하고, **망 에뮬레이터로 손실 10⁻³·10⁻⁴를 넣어 상용 계측기 2종과 결과를 대조**해 검증. → ZeroLoss의 검증 방식(10-verification 1.3 netem 주입·1.5 교차 대조)과 같은 접근이며, 한국 사업자 환경에서 쓰인 지표 목록의 근거.

**스누핑 규칙 (RFC 4541 2.1)**
- 가입 보고(Report)는 **라우터 포트로만** 보낸다. IGMPv1·v2에서 다른 호스트로 퍼지면 그 호스트가 자기 보고를 생략(suppression)해, 스누핑 스위치가 그 호스트를 가입자로 모르게 된다(IGMPv3는 생략 없음).
- 데이터는 그룹별 포트 표대로 보내고, **라우터 포트로는 항상** 보낸다.
- **224.0.0.x**(링크 로컬)는 IGMP가 아니면 **모든 포트로** 보낸다 → 시험 그룹이 이 대역과 MAC이 겹치면 모든 포트로 퍼진다(3.3 금지 규칙의 근거).
- 가입 보고가 없는 그룹(unregistered)은 라우터 포트로 보내고, 모든 포트로 퍼뜨려도 된다(구현 선택) → **R-15 가입 안 한 채널 수신**의 해석: 스누핑 꺼짐 또는 unregistered 플러딩.
- IGMPv3를 모르는 스누핑 장비는 v3 가입을 못 알아봐 스트림을 끊을 수 있다 → 실제 쓰인 IGMP 버전을 수신기마다 기록(1.6-1)하는 이유.
- 조회 출발 주소 0.0.0.0(스누핑 장비의 대리 조회)은 라우터 포트로 보지 않는다. 가입 보고 출발 주소가 0.0.0.0이어도 버리면 안 된다(대리 보고 장비).

## 2. 핵심 지표 계산 (Jitter, Packet Loss)

> 화면과 보고서에서 **가장 중요한 두 값**이다. 계산 방식은 아래로 고정하고, 보고서에 계산 방식을 함께 적는다.

### 2.1 Packet Loss
- **RTP 모드(기본):** RFC 3550 부록 A.3 방식.
  - 확장 순번(16비트 순번 + 순환 횟수)으로 `예상 개수 = 최대 확장 순번 - 첫 순번 + 1`
  - `손실 = 예상 개수 - 실제 받은 개수`, `손실률 = 손실 / 예상 개수`
  - **중복**과 **순서 뒤바뀜**은 손실과 **따로** 센다.
  - **RFC 3550 A.1의 출처 재동기화(MAX_DROPOUT 3000·탐색 패킷 2개)는 쓰지 않는다**(2026-09-25): 같은 SSRC에서 큰 점프는 실제 손실로 센다. 우리 송신은 시작할 때마다 새 SSRC를 쓰므로(3.2) 재시작은 SSRC로 구분된다. 새 SSRC = 새 구간(손실 아님).
  - 버스트(연속 손실)는 **RFC 3357 손실 구간**(끊김 없이 이어진 손실) 정의를 쓴다. RFC 3611·6958의 Gmin(16) 방식 버스트는 쓰지 않는다.
  - **순서 뒤바뀜 처리 (정렬 창):** 순번이 비어도 바로 손실로 세지 않고, **정렬 창**(기본 = 재생 지터 버퍼와 같은 1,000 ms) 동안 기다린다.
    - 창 안에 빠진 패킷이 도착하면 → **정상 정리됨(reordered, recovered).** 오류 아님, 정보로만 기록. 색에 영향 없음.
    - 창이 지난 뒤 도착하면 → **너무 늦음(late).** 실제 셋톱박스라면 버렸을 패킷이므로 **손실로 센다**(RFC 7003 개념). 늦게 온 개수는 따로 기록.
    - 대응: 창 안에 온 것 + 창 뒤에 온 것 = RFC 4737의 순서 뒤바뀜 수(s < NextExp). 창 = ITU-T Y.1540·RFC 7680의 Tmax(손실 판정 시한).
    - 끝내 안 오면 → 손실.
  - 고정 기준의 "순번 오류 0"은 **정렬 창 안에서 정리되지 못한 순번 문제**(손실·너무 늦음)를 뜻한다.
  - 연속 손실 구간(버스트)의 시작 시각, 길이도 기록한다(RFC 3357).
  - **송신 재시작 구분:** SSRC가 바뀌면 새 구간으로 시작한다(손실로 세지 않고 `segment_restarts` 기록). SSRC가 같은데 순번이 크게 뛰면 **손실로 센다**(순번 점프만으로 재시작이라고 추정해 손실을 숨기지 않는다).
  - **긴 끊김(순번 한 바퀴 65,536개 이상 빠짐):** 16비트 순번만으로는 몇 바퀴 돌았는지 모르므로 RTP 타임스탬프 경과 시간 × 최근 패킷 속도로 빠진 바퀴 수를 추정해 손실에 더한다(예: 35 Mbps에서 약 20초 이상 끊김).
- **RTP 없는 모드(MPEG-TS over UDP):** TS 연속성 카운터(CC, 4비트)로 손실을 센다(TR 101 290 1.4).
  - CC는 0~15를 반복하므로 **16의 배수만큼 한꺼번에 빠지면 놓칠 수 있다.** 보고서에 "CC 기반 계측, 한계 있음"을 표시한다.
  - 데이터그램 도착 간격이 정상 간격보다 크게 벌어지면 "손실 의심"으로 추가 표시한다.
- 판정: 손실 0개. 최소 1,000 패킷, 최소 100 kbps 미만이면 FAIL(수신 자체가 안 된 것).
  - **적용 범위(2026-09-24 결정):** 최소 1,000 패킷은 **수신기별 시험 전체**와 **꽉 찬 5분 칸**에 적용한다. 부분 칸(시작·끝·채널 전환·끊김으로 5분 미만)은 **100 kbps 기준만** 본다(속도 기준이라 길이와 무관, 기준을 낮추지 않음). 짧은 시험(RUN-006)은 수신기별 전체 1,000 패킷 기준으로 FAIL을 가린다.
  - **계획 시간 뒤의 칸은 판정하지 않는다(2026-10-03 첫 실기, 20장 GAP-105 ③):** 정지 처리 중 수신기가 계획 시간을 조금 넘겨(예: 0.7초) 쓴 꼬리로 시작이 계획 시간 이상인 칸(예: 300초 계획의 300→301초)은 화면 칸·판정·보고서에서 뺀다. 요약 원본(`summaries.jsonl`)에는 그대로 남긴다.
- **채널 전환과 손실 계산:** 손실은 **채널 가입 구간(Join ~ Leave)마다 따로** 계산한다. 채널이 바뀌면 순번이 새로 시작하므로(채널별 SSRC가 다름) 이전 채널 순번과 이어 계산하지 않는다.
  - Leave 요청 ~ 새 채널 첫 패킷 사이의 공백은 **손실이 아니라 채널 전환 시간**으로 기록한다.
  - 새 채널에서 첫 패킷이 기준 시간(기본 5초) 안에 오지 않으면 "채널 가입 실패"로 빨강 처리한다.

### 2.1-1 재전송(RET)·FEC로 복구된 손실
통신사 IPTV에는 빠진 패킷을 나중에 채워 주는 장치가 있다.
- **RET (재전송):** 셋톱박스가 빠진 순번을 서버에 요청(RTCP NACK, **RFC 4585**)하면 서버가 그 패킷만 다시 보내 준다(**RFC 4588** RTP 재전송 형식, DVB-IPTV **ETSI TS 102 034** RET).
- **FEC (오류 정정):** 원래 패킷과 함께 복구용 패킷을 보내 수신기가 스스로 복구한다(**SMPTE 2022-1**, RFC 6363 계열 참고).

ZeroLoss의 처리 (D46):
- 손실을 **두 가지로 나눠** 항상 기록한다.
  - **원래 손실(raw loss):** DUT를 지나며 실제로 빠진 패킷. 공유기 품질 그 자체.
  - **복구 후 손실(residual loss):** RET·FEC로 채우고도 끝내 비거나, 정렬 창(1,000 ms)을 넘겨 늦게 채워진 패킷.
- **1차 (기본, RET·FEC 없음):** 송신은 RET·FEC를 하지 않는다. 판정은 **원래 손실** 기준(= 지금의 고정 기준). 공유기가 패킷을 하나라도 흘리면 드러난다.
- **2차 (옵션: Carrier RET/FEC mode):** 송신 Agent가 RET 서버·FEC 송출을 흉내 낸다.
  - 판정은 **복구 후 손실** 기준(통신사와 같은 관점). 복구로 정상 정리된 경우는 **오류가 아니다.**
  - 원래 손실은 숨기지 않고 **노랑**으로 표시하고 개수를 보고서에 적는다("Recovered by RET: 12 packets").
  - RET 요청(NACK)은 수신기가 DUT를 거쳐 송신으로 보내는 트래픽이므로 "수신 장비는 시험 경로로 트래픽을 보내지 않는다"(4.1)의 **예외**로 이 모드에서만 허용하고, 요청 수를 기록한다.
  - 재전송 패킷이 정렬 창 안에 오면 복구, 창을 넘기면 손실(늦음).

### 2.1-2 경계 구간 오판 방지 (시작·채널 전환·종료)
> 송수신을 동시에 시작하거나 채널을 바꾸는 순간에는 **정상인데도 오류처럼 보이는 값**이 나온다. 이것을 오류로 판정하지 않는다.

**오류처럼 보이지만 정상인 것들**
| 현상 | 이유 |
|------|------|
| 첫 패킷 순번이 0이 아님 | 이미 흐르던 스트림 중간에 가입했기 때문. 그 앞 순번은 "손실"이 아님 |
| 첫 몇 초 PAT·PMT 없음 | PAT는 주기적으로 오므로 가입 직후엔 아직 안 왔을 수 있음 |
| 첫 TS 패킷의 CC 오류 | 비교할 이전 값이 없음 |
| 첫 몇 초 Jitter 큼 | 송출 속도 안정화, IGMP 가입 처리, 수신 버퍼 채우는 중 |
| 첫 화면까지 멈춤 | 재생기가 첫 I-프레임을 기다림 |
| 종료 순간 손실 | 송출을 먼저 끄면 수신 쪽에는 "끊김"으로 보임 |

**규칙**
1. **시작 순서를 지킨다 (동시에 시작하지 않는다):** ① 송출 시작 → ② 송출 안정 확인(목표 속도 ±1% 이내 3초 연속) → ③ 수신기 가입 → ④ 수신 안정화 → ⑤ **측정 시작 시점(t=0)**. 상시 방송 모드는 ①②가 이미 끝난 상태.
2. **안정화 구간(warm-up):** 수신기마다 가입 후 다음이 모두 충족되면 측정을 시작한다.
   - 첫 패킷 도착 → **이 패킷을 순번·CC·타임스탬프 기준점**으로 삼는다(그 앞은 세지 않음)
   - 첫 PAT·PMT 도착
   - 연속 3초 동안 손실 0, Jitter가 기준 이내
   - 재생기 첫 화면 표시, 그 뒤 **재생이 자리 잡음**: `pb`가 **2초 연속 `ok`**, 늦어도 첫 화면 **5초 뒤**(2026-10-10 UHD mpv 실기, 20장 GAP-152 — 재생기 시작(스트림 살피기·하드웨어 디코더 준비·입력 버퍼)의 흔들림이 측정에 들어가 첫 칸이 멈춤·glitch로 나옴. 5초 상한: 깨끗이 못 트는 PC도 측정은 하고 재생 문제는 노랑 경고)
   - 최대 안정화 시간(기본 15초) 안에 충족 못 하면 → **"시작 실패"**(상태창 F17 4·6단계 실패). 오류를 숨기지 않는다.
3. **안정화 구간의 값은 판정에 넣지 않는다.** 대신 따로 기록해 보고서의 "Start-up" 항목에 보여준다(가입 → 첫 패킷 시간 등).
4. **채널 전환도 같은 규칙:** 전환 후 새 채널의 첫 패킷을 새 기준점으로, 짧은 안정화(기본 최대 5초) 후 다시 측정. 전환 공백은 손실이 아님(2.1). 첫 패킷이 5초 안에 없으면 Join 실패(빨강). 반응 성공 시간 S-47은 판정과 무관(03 F19 표).
5. **종료 순서는 반대로:** ① 수신기 측정 마감(마지막 1초까지 확정) → ② 재생·가입 해제 → ③ 송출 정지. 송출 정지로 생긴 끊김을 손실로 세지 않는다.
6. **송출 쪽 이벤트 시각과 대조:** 송신 재시작·반복 지점·일시 정지 등 송출 쪽 사건 시각에 생긴 수신 이상은 먼저 송출 원인(보라)인지 확인한다.
7. 안정화 구간 이후 생긴 문제는 **예외 없이** 정상 규칙대로 판정한다(안정화를 핑계로 숨기지 않음).

### 2.2 Jitter
- **RTP 모드(기본):** RFC 3550 6.4.1 Interarrival Jitter.
  - `D = (수신시각j - 수신시각i) - (RTP타임스탬프j - RTP타임스탬프i)`, `J = J + (|D| - J) / 16`
  - 단위는 ms로 변환해 표시. 1초마다 현재값, 최대값 기록.
  - 전제: 송신 측 RTP 타임스탬프가 **패킷이 도착해야 할 이론 시각(90 kHz)**을 나타내야 한다. TSDuck 문서 기준으로 RTP 타임스탬프는 "패킷이 도착하기로 되어 있는 이론 시각"이며, 수신 쪽은 이것과 **실제 도착 시각(커널 타임스탬프)**의 차이로 지터를 계산한다(Context7로 TSDuck 문서 확인, 2026-09-23).
  - **M 비트 = 타임스탬프 불연속(RFC 2250 2.1):** M = 1인 패킷에서는 그 전 패킷과의 `D`를 쓰지 않고 지터·도착 지연 기준을 새로 잡는다(SSRC가 바뀔 때와 같게). 송신 쪽 불연속이 망 지터로 잘못 보이지 않게 한다(2026-09-25, 20장 GAP-41).
  - **시계 기울기 보정(2026-09-25 사용자 결정, 20장 GAP-42 ③):** 송신·수신 PC 시계는 서로 맞춰져 있지 않아(시험망에 NTP 없음) 상대 전달 지연(`dlo`/`dhi`)에 직선 기울기가 섞인다(50 ppm이면 5분에 15 ms, RFC 5481 7장). **가입 구간마다** 매초 최소 지연(`dlo`)을 시간에 대해 최소 제곱 직선으로 맞춰 기울기 S를 추정하고(RFC 3393 5.2), 기록·5분 칸의 `dlo`/`dhi`에서 S·t를 뺀다. 조건: 자료 **120 s 이상**부터 쓰고, |S| > 200 ppm이면 시계가 아닌 다른 원인으로 보고 빼지 않는다(기록만). 구간 전체로 맞추므로 몇 분짜리 실제 지연 증가(대기열 증가)는 지워지지 않는다. S는 1초 `sk`, 5분 `jitter.skew_ppm`, 측정 신뢰도(F25)에 적는다. Interarrival Jitter(6.4.1)는 연속 패킷 사이 값이라 영향이 무시할 만하므로 보정하지 않는다.
- **RTP 없는 모드:** 도착 간격 변동(IPDV, RFC 3393/5481)과 MDI DF(RFC 4445)로 대신 표시한다. **입력 형식 자동 판별(TS 102 034 7.1.3, GAP-42 ④):** UDP 뒤 첫 바이트가 0x47이면 RTP 없는 MPEG-TS, 아니면 RTP. 판정은 설정(S-10)대로 하고, 실제 형식이 설정과 다르면 RCV-022로 알린다. **이 빌드의 S-10은 RTP만**(MPEG-TS/UDP는 RUN-013, 16장 3절).
- 보조 표시: MDI **DF**(ms), **MLR**(초당 잃은 **TS 패킷** 수 — RFC 4445 정의. 데이터그램 1개 손실 = TS 7개).
- 판정: Jitter 150 ms 이하.

## 3. 송신 규칙 (송신이 결과를 오염시키지 않게)

### 3.1 정속(CBR) 송출
- 송출 스트림은 **CBR MPEG-TS**로 만든다. 부족한 비트레이트는 널 패킷(PID 0x1FFF)으로 채운다.
  - 사전 준비 파일 모드: 미리 CBR TS로 변환해 둔다(예: ffmpeg의 muxrate 지정, 인코더 CBR/HRD 설정).
  - 실시간 인코딩 모드: 인코더를 CBR로 설정하고 muxrate를 고정한다.
- 송출 속도 조절은 **TSDuck(tsp)**으로 한다. 문서로 확인한 구성 요소(Context7, TSDuck 공식 문서):
  - 출력: `-O ip <그룹>:<포트> --rtp --packet-burst 7 --enforce-burst` (데이터그램당 TS 7개를 항상 채워 보냄)
  - 정속: `-P regulate` (필요 시 `--packet-burst`)
  - 파일 반복 이음새(SND-004): `-P continuity --fix`(연속성 카운터 이어 붙이기), `-P pcradjust`(PCR 보정)로 **확정**(2026-09-24 실측: 반복 3회 CC·P1 오류 0, PCR 연속. `tsfixcc`는 CC 규칙 위반으로 기각, iptv 4.2)
  - 정확한 옵션 조합(TTL, 송출 NIC 지정 등)은 `docs/modules/iptv.md` 4.4에 확정됨(2026-09-24 실측, TTL·출발 IP 캡처만 시험망에서 남음).
- **독립 교차 확인용 계측기:** TSDuck에는 도착 간격(IAT)을 재는 `iat` 플러그인이 있다. 수신 쪽 `-I ip --timestamp-priority kernel-tsp`(RTP 타임스탬프 대신 커널 수신 시각 사용)와 함께 쓰면 ZeroLoss 분석기의 지터 값과 **별도 도구로 비교**할 수 있다(10-verification 1.5 대조 시험에 추가). PCR 또는 지정 비트레이트 기준으로 일정하게 내보내며, 한 번에 몰아 보내는 버스트를 만들지 않는다.
- 데이터그램 간격이 일정해야 한다. 송신 쪽 간격 편차를 1초마다 기록하고, 기준을 넘으면 "송신 불안정"으로 표시한다(이 경우 그 구간은 5.3의 **보라(도구 원인)**로 분류).
- **송출 NIC 지정:** 송신 PC에 NIC가 여러 개일 수 있으므로(최소 구성 등) 멀티캐스트는 **선택한 WAN 쪽 NIC로만** 나가게 지정한다(`IP_MULTICAST_IF`, TSDuck의 로컬 주소 옵션). 발신 IP가 DUT WAN 대역인지 사전 점검한다.

### 3.2 패킷 형식
| 항목 | 값 | 이유 |
|------|----|------|
| 데이터그램당 TS 패킷 | **7개** (1316 바이트) | RFC 2250 / 업계 관행. RTP+UDP+IP 헤더 포함 1356 바이트 < MTU 1500 → **IP 단편화 없음** |
| RTP 헤더 | v2, PT 33, 순번 +1씩, SSRC = 채널 번호(위 8비트) + 송출 시작마다 새 난수(아래 24비트) (iptv 2장) | RFC 3550/3551 |
| RTP 타임스탬프 | 90 kHz, 이론 도착 시각(TSDuck `-O ip --rtp`) | Jitter 계산의 기준 |
| 목적지 | 239.x.x.x : 5004 (채널별 다른 그룹) | RFC 2365. 기본 포트 5004 |
| **혼잡 제어 대신 안전장치**(RFC 8085 3.6 통제된 환경) | 인터넷과 분리된 시험망(07), 정해진 속도로만 송출(S-11 상한 40 Mbps × 3), TTL 16 범위 제한(S-15), 받는 쪽·지휘가 끊기면 송출도 멈춤(heartbeat 안전 정지, F11) | UDP에 혼잡 제어가 없으므로 이 조건 밖(일반 망·인터넷)에서는 쓰지 않는다(2026-09-25) |
| 수신 PT 확인(RFC 3551) | PT ≠ 33인 RTP는 이 채널 계측에 넣지 않고 따로 센다 | 다른 흐름이 같은 그룹·포트로 섞였을 때 손실·지터를 오염시키지 않게(2026-09-25, GAP-41) |
| TTL | **16** (설정 가능, 최소 8) | 기본값 1이면 NAT 모드에서 공유기가 WAN→LAN으로 넘길 때 TTL이 0이 되어 버려진다 |
| DSCP | 0 (설정 가능) | 공유기 기본 동작 그대로 검증 |
| RTCP | 보내지 않음 | 시험 경로에 추가 트래픽 금지 |

### 3.3 멀티캐스트 그룹 주소 규칙
- 채널마다 다른 그룹 주소를 쓴다. 기본: 239.1.1.1, 239.1.1.2, 239.1.1.3.
- IP→MAC 매핑은 하위 23비트만 쓰므로(RFC 1112) 서로 다른 IP가 같은 MAC이 될 수 있다. **채널 주소끼리 MAC이 겹치지 않게** 검사한다.
- 224.0.0.x나 239.0.0.x, 239.128.0.x처럼 **예약 주소와 MAC이 겹치는 주소는 쓰지 않는다.** 스위치/공유기가 모든 포트로 뿌려 결과가 왜곡된다.

### 3.4-1 송신 문제 판별 (송신이 느리거나 갑자기 끊긴 경우)
> 수신 쪽에서 패킷이 줄거나 끊기면, 그것이 **공유기 탓인지 송신 PC 탓인지** 반드시 가려야 한다. 송신 탓을 공유기 탓(빨강)으로 판정하면 안 된다.

**송신 쪽에서 1초마다 재는 것**
| 값 | 어디서 | 뜻 |
|----|--------|----|
| 보낸 데이터그램 수·비트레이트 (채널별) | 송신 프로그램 | 프로그램이 내보낸 양 |
| 실제로 NIC로 나간 양 | NIC 전송 카운터(Linux `tx_packets`, Windows 어댑터 통계) | 선으로 실제로 나간 양 |
| 송신 NIC 드롭·오류 | NIC 카운터(`tx_dropped`, `tx_errors`), 소켓 송신 버퍼 가득 | 송신 PC 안에서 버려진 것 |
| 데이터그램 간격 편차, **최대 공백** | 송신 프로그램 | 정속인지, 멈칫했는지 |
| CPU, 메모리, 디스크 읽기 지연(사전 준비 파일) | OS | 느려진 원인 후보 |

**판정 기준 (기본값, 설정 가능)**
| 상황 | 조건 | 색·처리 |
|------|------|---------|
| 정상 | 목표 비트레이트 ±1% 이내, 최대 공백 < 50 ms | 영향 없음 |
| 송신 느려짐 | 1초 비트레이트가 목표보다 1% 넘게 낮음, 또는 최대 공백 ≥ 50 ms | 그 구간 **노랑**("Sender slow") |
| 송신 불안정 | 목표보다 5% 넘게 낮음, 또는 공백 ≥ 100 ms, 또는 송신 NIC 드롭 발생 | 그 구간 **보라**(도구 원인, 공유기 판정 불가). 사건 `ZL-SND-016`(매초), 구간은 5.3 "문제 구간으로 나누기" |
| 송신 멈춤 | 1초 이상 보낸 것 0 | **보라** + 사건 `ZL-SND-016 Sender stalled` + 원인 후보(CPU, 디스크, 프로세스) |

**수신 쪽 문제와 맞대 보기 (Controller가 시각을 맞춰서 비교)**
| 송신 쪽 | 수신 쪽 | 결론 |
|---------|---------|------|
| 정상 | 손실·끊김 | **공유기(DUT) 원인** → 빨강 |
| 느려짐·멈춤·NIC 드롭 | 같은 시각에 손실·끊김 | **송신 원인** → 보라 (빨강 아님) |
| 정상 | 모든 수신기가 동시에 끊김 | 공유기 공통 구간(재부팅 의심 NET-001 등) |
| 프로그램은 보냈다는데 NIC로 안 나감 | 끊김 | 송신 PC 네트워크 스택·NIC 문제 → 보라 |

- `송신 수 = 수신 수 + 손실 수` 대조(10-verification 1.5)를 **1초 단위로** 한다. 송신 쪽 수가 먼저 줄었으면 송신 원인.
- 시각 맞추기는 Controller 기준(D39). 판정 창은 사건 앞 1초 ~ 끝난 뒤 2초(5.3 "문제 구간으로 나누기", 2026-09-26).

### 3.4 송신 PC 자체 점검
- 송신은 1초마다 **보낸 패킷 수**를 기록한다. Controller는 `보낸 수`와 `받은 수`를 나란히 비교한다.
- CPU 사용률, 송신 NIC 오류·드롭 카운터를 1초마다 기록한다.
- Controller와 송신을 한 PC에서 돌릴 때는 **사전 준비 파일 모드**를 기본으로 한다.

## 4. 수신 규칙 (수신이 결과를 오염시키지 않게)

### 4.1 그룹 가입과 채널 전환
- 그룹 가입은 OS 표준 소켓 기능(`IP_ADD_MEMBERSHIP`)으로 하고, IGMP 메시지는 OS가 보낸다. 도구가 IGMP 패킷을 직접 만들지 않는다.
- 채널 전환: 이전 그룹 `IP_DROP_MEMBERSHIP`(Leave) → 새 그룹 Join. 전환 시간은 `Join 요청 → 첫 패킷`, `Join 요청 → 첫 PAT`, `Join 요청 → 첫 화면`으로 나누어 기록한다(판정 제외).
- 수신 장비는 IGMP 외에 **시험 경로로 트래픽을 보내지 않는다.** (RTCP 금지. 보고는 Controller가 가져가는 제어 연결 또는 USB. `07-network.md` 7장의 양 제한을 따른다)

### 4.2 계측과 재생 분리 (양방향 독립)
> 수신기는 패킷을 받고 분석하면서 동시에 화면을 재생한다. **분석이 재생에 영향을 주면 안 되고, 재생이 분석에 영향을 주어도 안 된다.**

- **소켓을 따로 쓴다:** 재생기와 분석기가 **각자** 같은 그룹에 가입해 받는다(`SO_REUSEADDR`로 같은 포트 공유). OS가 패킷을 두 소켓에 각각 복사해 주므로, 한쪽이 느려져도 다른 쪽은 영향이 없다.
  - 분석기가 받은 패킷을 재생기로 넘겨주는 구조(중계)는 **쓰지 않는다.** 분석이 느려지면 재생이 끊기기 때문이다.
- **분석은 가볍게:**
  - 패킷마다 하는 일은 헤더 확인과 카운터 증가 등 고정된 적은 연산만 한다. 영상 디코딩은 하지 않는다.
  - 수신 스레드는 받기만 하고, 계산·저장은 별도 스레드에서 1초 단위로 몰아서 한다. 패킷마다 디스크에 쓰지 않는다.
  - 분석기 우선순위는 재생기보다 낮게 둔다. 목표 CPU 사용량: UHD 3채널 기준 코어 1개의 20% 이하(구현 후 실측으로 확정). 단, **PC 수신 시험에서 CPU가 부족하면 예외**(아래 4.2-1).
- **4.2-1 저사양 수신 PC (PC 수신 시험만. 태블릿 시험과는 무관)**
  - 창 크기는 해독 부담을 거의 줄이지 않는다(해독량은 송출 영상 해상도로 정해짐). 효과 순서: 하드웨어 해독 > 재생 끄기(분석만) > 창 작게.
  - **시작 전 성능 점검(RCV-015):** ① 이번 화질 코덱(UHD HEVC / HD H.264)의 하드웨어 해독 지원 확인 ② 준비 파일 10초를 재생기와 같은 설정으로 해독해 **실시간의 1.5배 이상** 속도가 나오는지 ③ 쉬는 상태 CPU 여유. 부족하면 ⚠와 추천 설정(재생 끄기 S-49, 작은 창 S-50, HD로 시험)을 보여 주고 사용자가 고른다(시작을 막지는 않음).
  - **분석기 보호(RCV-016):** 시험 중 전체 CPU 90% 이상이 10초 넘게 이어지면 분석기(수신 스레드) 우선순위를 재생기보다 **높게** 올리고 기록한다. 측정(손실·지터)이 재생보다 중요하기 때문이다. 이때 생긴 재생 이상은 "수신단 원인(성능 부족)"으로 분리한다(4.6).
  - **구현 규칙(2026-09-26, 20장 GAP-61):**
    - RCV-015는 F17 4단계("Disk, time & PC speed")에서 **재생 켠 PC 수신기만** 본다. 해독 시험 영상은 **수신 PC가 처음 한 번 만들어** 모듈 캐시(`perf/sample_<화질>_<Mbps>M.ts`, 송신과 같은 인코딩 값 10초, iptv 3장)에 둔다 — 영상은 Controller를 거치지 않는다(절대 원칙). 만드는 동안은 ⚠ "measuring the PC, ready at the next check"(기다리지 않음). 수신 PC에 ffmpeg가 필요하다(재생 켬일 때 F17 2단계 필요 도구).
    - 해독 속도는 재생기와 같은 해독 라이브러리를 쓰는 **ffmpeg `-hwaccel auto`**로 10초 영상을 끝까지 해독해 `speed=`를 읽는다(VLC 자체 속도 재기는 V6 뒤). 하드웨어 해독 지원은 Linux `vainfo`의 해당 프로필(UHD = `VAProfileHEVCMain`, HD = `VAProfileH264High` — 송신 영상이 H.264 High라 Main만 되는 PC는 "없음") 유무(없으면 `null` = 모름), Windows는 V18 때. 쉬는 상태 CPU는 heartbeat `cpu_pct`, **50% 넘으면** 여유 부족(기본값, 실측 뒤 조정).
    - 결과는 24시간 두고 쓴다(대기 중 가벼운 점검은 저장된 결과만 읽음, Start·`zeroloss precheck`는 24시간 지났으면 다시 잼). **단 CPU 여유(다른 프로그램이 쓰는 %)는 지금 값이라 점검할 때마다 새로 읽고 경고도 그때 다시 만든다**(2026-10-04 기준선 실기, 20장 GAP-113: 24시간 전 값 "56% busy"가 조용해진 PC에도 나옴). 고치기 안내는 화질에 맞춘다 — 이미 HD 시험이면 "HD로 시험"을 권하지 않는다.
    - RCV-016: 수신 세션이 1초마다 PC 전체 CPU를 보고 **90% 이상이 10초 넘게** 이어지면 **재생기 프로세스의 우선순위를 내린다**(nice +10 — 분석기를 올리려면 특별 권한 `CAP_SYS_NICE`가 필요하지만, 재생기를 내리면 권한 없이 같은 효과). 한 세션에 한 번, Problems ⚠, 시각 기록. 그 구간 재생 이상을 보라로 나누는 판정 연결은 **재생 이상을 5분 칸 판정에 넣을 때**(지금은 칸 색에 안 들어감) 함께 한다.
  - 억지 경량화(재생기의 프레임 건너뛰기, 루프 필터 생략 등)는 쓰지 않는다. 패킷이 정상인데 재생 이상이 생겨 판정이 흐려진다.
  - 재생을 끄면(S-49 Off) 손실·지터 판정은 그대로이고, 재생 이상 감지·화면 증거 캡처는 `NOT RUN`으로 남긴다.
  - **실측 사례 (2026-09-23, 저사양 노트북):** ThinkPad T460 — i5-6200U(2코어 4스레드), Intel HD 520 + GeForce 940MX, 16 GB, Ubuntu 22.04, ffmpeg 4.4.2, VA-API iHD 22.3.1. 5초 시험 영상(ffmpeg `testsrc2`)을 해독만 한 속도:
    | 영상 | 해독 방식 | 속도(실시간 대비) | 4.2-1 기준(1.5배) |
    |------|-----------|-------------------|-------------------|
    | UHD HEVC 3840×2160 30fps 35 Mbps | 하드웨어(VA-API, Intel HD 520) | **5.5배** | 통과 |
    | 같음 | CPU만 | 1.8배 | 겨우 통과 — 실제 방송 영상은 더 무거워 위험 |
    | HD H.264 1920×1080 30fps 10 Mbps | 하드웨어(VA-API) | 29.5배 | 통과 |
    - 결론: 6세대 Intel 내장 그래픽이면 **UHD HEVC(8비트)도 하드웨어 해독으로 충분**하다. GeForce 940MX(GM108)는 HEVC 해독이 없어 쓰지 않는다. 하드웨어 해독이 꺼지면 CPU로 넘어가 버거우므로 **점검 ①(하드웨어 해독 확인)이 가장 중요**하다.
    - 한계: 해독만 잰 값이다(화면 그리기·분석기 부하 제외). 시험 영상이 단순해 CPU 해독은 실제보다 좋게 나온다. P1에서 mpv 재생 + 분석기 동시 실행으로 다시 잰다.
    - Linux 수신 PC는 VA-API 드라이버가 있어야 한다: Intel은 `intel-media-va-driver`(확인 도구 `vainfo`). 없으면 설치 목록에 넣는다(06-install 11장).
- **영향 없음을 증명한다:**
  - 재생기 상태(프레임 드롭, 멈춤)를 기록한다.
  - 분석기의 CPU·메모리 사용량을 1초마다 기록한다.
  - 사전 점검에서 **분석기를 켠 상태와 끈 상태의 재생 품질이 같은지** 확인하는 시험을 둔다.
- 태블릿도 같은 원칙이다: 앱 안에서 재생기와 분석기가 **별도 소켓, 별도 스레드**로 동작한다.

#### 4.2.1 분리 방식 비교와 결정
| 방식 | 구조 | 장점 | 문제 | 결정 |
|------|------|------|------|------|
| **A. 소켓 2개 (OS 복사)** | 분석기와 재생기가 각자 그룹 가입. OS가 두 소켓에 복사 | 완전 독립. 한쪽이 멈춰도 다른 쪽 무관. 추가 권한 불필요. PC·Android 모두 가능 | 같은 포트 공유 설정 필요. 채널 전환 시 둘 다 옮겨야 IGMP Leave가 나감 | **기본 방식** |
| B. 파이프 중계 | 분석기가 받아서 파이프/로컬 소켓으로 재생기에 전달 | 소켓 하나 | 분석이 느리면 재생이 끊김. 파이프 버퍼가 작아(Linux 기본 64 KB = 40 Mbps에서 약 13 ms) 조금만 밀려도 막힘. 넘치는 걸 버리면 **도구가 손실을 만든 것**이 됨 | **사용 안 함** |
| C. 패킷 캡처 (pcap) | 재생기는 소켓으로 받고, 분석기는 NIC에서 복사본을 캡처 | 소켓 단계 이전(NIC)에서 보므로 가장 정확. 재생과 완전 분리 | 관리자/root 권한 필요. Windows는 Npcap 설치 필요(배포 조건 확인 필요). Android는 root 없이 불가 | **Linux PC 전용 옵션** (정밀 진단용) |
| D. 공유 메모리 링버퍼 | 수신 스레드 하나가 받아 링버퍼에 쓰고, 분석기·재생기가 각자 읽음 | 복사 1회 | 수신 스레드가 하나라 거기서 막히면 둘 다 영향. 구현 복잡 | 사용 안 함 |

**결정: A(소켓 2개)를 기본으로 하고, Linux 수신 PC에서는 C(패킷 캡처)를 정밀 진단 옵션으로 둔다.**

#### 4.2.2 A 방식 구현 규칙
- PC: 재생기는 VLC(기본)·mpv(옵션)가 직접 `rtp://@239.x.x.x:5004`(또는 `udp://@…`)로 가입해 받는다. 가입 NIC는 반드시 지정한다(VLC `--miface=<NIC>`, FFmpeg 계열 `localaddr`) — 빼면 기본 경로 NIC로 가입한다(15장 3.4, 2026-09-25 실측). 분석기는 ZeroLoss 수신 Agent가 별도 소켓으로 받는다.
- 두 소켓 모두 포트 공유(`SO_REUSEADDR`, 필요 시 `SO_REUSEPORT`)를 켠다.
- Android: 앱 안에서 분석 소켓과 재생 소켓을 따로 연다. 재생기(Media3/ExoPlayer 계열)에는 RTP 헤더를 벗겨 TS만 넘기는 전용 입력 모듈을 붙이되, **재생용 소켓에서 받은 것만** 쓴다.
- **채널 전환은 두 소켓을 함께 옮긴다.** 한쪽만 남아 있으면 OS가 IGMP Leave를 보내지 않아 이전 채널이 계속 흘러오고, 채널 전환 시간 측정이 틀어진다.
- 소켓별 드롭 카운터를 따로 기록한다. 재생 소켓만 드롭이 있으면 재생기 처리 문제, 분석 소켓만 드롭이 있으면 분석기 문제로 구분한다.

### 4.3 수신 장비 자체 드롭 분리
- 소켓 수신 버퍼를 충분히 크게 잡는다(기본 **16 MB** 요청, 실제 적용값 기록). UHD 40 Mbps 기준 약 3초 분량이다.
- 수신 장비 자체 드롭(버퍼 넘침)을 OS 카운터로 **따로** 센다.
  - Linux: 소켓별 drops, `UDP RcvbufErrors`
  - Windows: UDP 수신 오류 카운터
  - Android: 앱이 읽을 수 있는 범위에서 기록(구현 시 확인)
- 수신 장비 자체 드롭이 0이 아니면, 그 구간 손실은 **"수신 장비 원인"**으로 따로 표시한다. 네트워크 손실(DUT 원인 후보)과 섞지 않는다.

### 4.4 수신 시각
- 가능한 한 **커널 수신 시각**을 쓴다(Linux `SO_TIMESTAMPNS`). 불가능한 OS는 수신 직후 고해상도 단조 시계를 쓰고, 보고서에 정밀도 차이를 표시한다.
- 시간 맞추기: 실험실에 인터넷이 없을 수 있으므로 NTP에 의존하지 않는다. Controller가 heartbeat 왕복 시간으로 **장비별 시계 차이(offset)를 계속 계산**하고, 보고서의 모든 시각을 Controller 시각으로 맞춘다. 장비별 추정 오차를 보고서에 적는다. (NTP가 되면 함께 기록)

### 4.5 Android 태블릿 필수 사항
- 대상: **Android 16·17** 태블릿(실기 검증). 앱은 minSdk 29(Android 10)부터 설치되게 만들되, 보증은 16·17만 한다.
- 장시간 실행을 위해 **포그라운드 서비스 유형은 `mediaPlayback`**으로 한다. 매니페스트에 `android:foregroundServiceType="mediaPlayback"`, 권한 `FOREGROUND_SERVICE`·`FOREGROUND_SERVICE_MEDIA_PLAYBACK` 선언(Context7, Android 공식 문서 확인). Android 14 이상은 유형 지정이 필수다. `dataSync` 유형은 최신 Android에서 실행 시간 제한이 있다고 알려져 있어 쓰지 않는다(정확한 제한값은 P1에서 재확인). 배터리 최적화 제외를 요청한다.
- 멀티캐스트 수신: `WifiManager.createMulticastLock()` + 권한 `CHANGE_WIFI_MULTICAST_STATE`(문서 확인).
- Wi-Fi Lock은 **저지연(`WIFI_MODE_FULL_LOW_LATENCY`)**을 쓴다. `WIFI_MODE_FULL_HIGH_PERF`는 사용 중단(deprecated)되어 이것으로 대체됐다(문서 확인). **주의(문서):** 저지연 모드는 **화면이 켜져 있고 앱이 전경일 때만** 동작하며, 처리량을 줄이거나 Wi-Fi 스캔 빈도를 낮출 수 있다 → 화면 켜짐·전경 유지는 필수이고, UHD 3채널에서 처리량 영향이 없는지 V3에서 확인한다(영향 있으면 Lock 없이 비교 시험).
- **큰 화면 대응:** Android 16부터 태블릿 같은 큰 화면에서는 앱의 화면 방향 고정·크기 고정 설정이 무시된다. 재생 화면과 상태 표시는 **가로·세로·창 크기 변화에 모두 대응**하도록 만든다. 화면이 돌아가도 재생·계측이 끊기지 않아야 한다(구성 변경 시 재생기 재생성 금지).
- 필요한 권한은 설치 후 adb로 미리 허용한다(알림, 배터리 최적화 제외 등). 사용자가 태블릿을 만질 필요를 최소화한다.
- 태블릿이 Wi-Fi로 보내고 받는 **영상 외 트래픽**(앱 업데이트, 동기화 등)을 1초마다 기록한다(앱별 트래픽 통계). 시험 중 자동 업데이트·백그라운드 동기화를 끄도록 사전 점검에서 안내한다. 영상 외 트래픽이 많으면 노랑으로 표시한다.
- 멀티캐스트 수신을 위해 **MulticastLock**을 획득한다(없으면 Android가 멀티캐스트를 버린다).
- Wi-Fi 절전으로 인한 수신 누락을 막기 위해 **고성능/저지연 Wi-Fi Lock**을 잡고, 화면 켜짐과 앱 전경 실행을 유지한다.
- 위 설정 상태를 회차마다 기록한다. 설정이 풀리면 해당 구간을 "수신 장비 조건 불충족"으로 표시한다.

### 4.6 재생은 패킷 문제가 있을 때만 이상이 보여야 한다 (핵심)
> 이 도구는 **공유기 안에서 패킷 전달 문제**를 찾는 도구다. 그러므로 **수신단(재생기·수신 장비) 자체 때문에 화면이나 소리에 이상이 생기면 안 된다.**
> 화면·소리 이상은 **받은 패킷에 문제가 있을 때만** 나타나야 하고, 패킷이 완벽한데 재생 이상이 생기면 그것은 **도구·수신 장비 문제**로 따로 분류한다.

#### 4.6.1 재생기 설계 규칙
| 규칙 | 내용 | 근거 |
|------|------|------|
| **스트림 시계에 맞춰 재생** | 수신 장비 자체 시계가 아니라 스트림의 **PCR(27 MHz)**로 시계를 복원해 재생한다. 100시간 동안 송신·수신 시계 차이가 쌓여 생기는 버퍼 넘침·바닥남(주기적 끊김)을 막는다 | ISO/IEC 13818-1 (PCR, 시스템 타깃 디코더 모델) |
| **소리는 리샘플링으로 맞춤** | 시계 차이를 프레임을 버리거나 반복해서 맞추지 않고, 소리를 아주 미세하게 리샘플링해 맞춘다(귀로 구분 안 되는 수준) | - |
| **충분한 지터 버퍼** | 재생 버퍼는 판정 기준 지터(150 ms)보다 넉넉하게(기본 1,000 ms, 설정 가능). 기준 이내의 지터로는 절대 끊기지 않게 한다. 기준을 넘는 지터는 **계측기가** 잡는다 | RFC 7005 (De-Jitter Buffer), ETSI TS 102 034 |
| **재생 속도 고정** | 지연을 줄이려고 재생 속도를 바꾸는 기능(라이브 속도 조절)은 끈다. 속도 변화가 소리·화면 이상처럼 보이지 않게 한다 | - |
| **하드웨어 디코딩** | UHD HEVC 30fps를 실시간으로 여유 있게 디코딩할 수 있어야 한다. 가능하면 하드웨어 디코더를 쓴다. **실측(2026-10-10 T460 HD 520, 20장 GAP-152):** VLC 3.0.20은 VA-API를 못 붙여("no hw decoder modules matched") UHD HEVC를 소프트웨어로 풀며 CPU 317 %, 늦은 프레임 버림·참조 없음으로 화면이 깨짐 → mpv `--hwdec=vaapi`(창에 바로, 복사 모드 아님)는 22 %에 원본과 같은 화면 | GAP-152 |
| **재생 우선순위 높게** | 재생 프로세스는 분석기보다 우선순위를 높게 둔다(4.2). PC 수신 시험에서 CPU 부족 시 분석기를 올리는 예외는 4.2-1 | - |
| **절전 끄기** | 시험 중 절전·화면 꺼짐·CPU 절전 모드를 끈다(Windows 고성능 전원, Linux 성능 모드, Android 배터리 최적화 제외 + 충전 연결 권장). 끝나면 원복 | - |

- PC 재생기: 라이브 MPEG-TS의 PCR 시계 복원과 소리 리샘플링을 지원하는 재생기를 쓴다. **기본 mpv, 선택 VLC**(S-26, 2026-10-10 사용자 결정 — 위 하드웨어 디코딩 실측. 그 전 2026-09-24는 VLC 기본). 구현 초기(V6)에 VLC를 먼저 100시간급 장시간 재생에서 시계 차이로 인한 끊김이 없는지 확인한다. VLC가 V6를 통과하지 못하면 기본값을 바꾸기 전에 사용자에게 알리고 정한다.
- Android 재생기: Media3/ExoPlayer 계열 + MediaCodec 하드웨어 디코더. 라이브 속도 조절 끄기, 버퍼 크기 고정.

#### 4.6.2 재생 이상과 패킷 이상의 자동 대조
- 재생기에서 **재생 이상 이벤트**를 시각과 함께 기록한다: 화면 멈춤, 프레임 드롭, 소리 끊김(버퍼 바닥남), 디코더 오류, 재생기 재시작.
- 각 재생 이상을 같은 시각(앞뒤 여유 포함)의 **패킷 이상**(손실, 지터 초과, TS 오류, PCR 오류)과 자동으로 짝지운다.

| 재생 이상 | 같은 시각 패킷 이상 | 분류 |
|-----------|---------------------|------|
| 있음 | 있음 | **네트워크(DUT) 원인** → 정상적인 검출 |
| 있음 | **없음** | **수신단 원인**(재생기·수신 장비) → DUT 판정에서 제외, "Receiver-side issue" 경고. 시험 신뢰도 문제로 보고서 맨 앞에 표시. 5분 칸은 **노랑** "playback issue with clean packets (receiver side)"(멈춤·프레임 버림·디코더 오류·재생기 재시작이 손실 0·P1 0인 칸에 있음) — **PASS는 그대로 가능**(2026-10-10 사용자, 20장 GAP-152; 합격은 지터·손실만, GAP-132) |
| 없음 | 있음 | 재생기가 가렸지만 패킷 문제는 존재 → 판정은 패킷 기준(FAIL) |

- 목표: **정상 시험에서 "수신단 원인" 재생 이상은 0건.** 0이 아니면 수신 장비·재생기 설정을 먼저 고쳐야 한다.

#### 4.6.3 수신단 기준선 시험 (Baseline test)
- 공유기 없이(송신 PC ↔ 수신 장비를 직접 또는 단순 스위치로 연결) 같은 조건으로 시험하는 모드를 제공한다.
- 기준선 시험에서 **패킷 손실 0, 재생 이상 0**이 나와야 그 수신 장비·재생기 조합을 "검증된 수신기"로 표시한다.
- DUT 시험 보고서에는 해당 수신 장비의 **마지막 기준선 시험 결과와 날짜**를 함께 적는다.
- **구현 규칙(2026-10-02, 20장 GAP-97, 자동 모드 추천안):** S-54 `Test network: Baseline (no router)`로 고른다(툴은 단순 스위치와 브리지 공유기를 구별할 수 없어 사람이 고름). 사전 점검 3단계 NAT 판별이 NAT를 찾으면 NET-020으로 시작 거부. 시험 진행·판정은 보통 시험과 같다(고정 기준 그대로). 끝나면 수신 장비마다 `verified` = 회차 PASS + 손실 0 + 재생 이상 0(정지·프레임 빠짐·소리 끊김·재생기 다시 시작의 합)을 그 장비·재생기 조합(`<장비>|VLC`, 재생 끔은 `|none`)으로 Controller `baselines.json`에 덮어쓴다. 계획 시간 끝까지 가지 않은 기준선 회차(멈춤·안전 정지)는 기록하지 않는다. 모든 보고서(02 10 `receiver_baseline`)와 보고서 화면 장비 표의 `Baseline` 칸에 마지막 결과·날짜를 적는다. 시간은 정하지 않는다(10장 1.4의 도구 검증은 24시간).
- **기준선 모드의 표시(2026-10-04 첫 기준선 실기, 20장 GAP-113):** 공유기가 없으므로 사전 점검 3단계는 "공유기 NAT 없이 닿음 — 공유기 WAN에만 연결" 경고(NET-018의 통신사 역할 경우)를 내지 않는다. 5단계 안내와 보고서 `dut.multicast_path`는 `"direct"`("direct (baseline, no router)"), `dut.mode_detected`는 `null`(시험한 공유기가 없음).

#### 4.6.4 추가 스트림 지표 (TR 101 290 Priority 2)
- PCR 반복 간격(PCR repetition, 100 ms 이하), PCR 정확도(PCR accuracy), PTS 오류를 계측한다. 재생 시계 복원 문제를 패킷 쪽 원인(PCR 흔들림)과 구분하는 데 쓴다.

### 4.7 패킷 캡처(Wireshark) 동시 실행
> 시험 중에 Wireshark 같은 캡처를 함께 돌리면 증거는 강해지지만, **캡처 자체가 시험 PC에 부하를 줘서 측정을 오염**시킬 수 있다(40 Mbps 전체 캡처 ≈ 시간당 18 GB 디스크 쓰기).

**어디서 캡처하나 (우선순위)**
| 방법 | 부하 | 쓰는 때 |
|------|------|---------|
| ① **외부 캡처 장비**: 스위치 포트 미러링·네트워크 TAP → 별도 PC가 캡처 | 시험 PC 부하 0 | 가장 권장. 12-architecture 4-1 외부 장비 연동과 같은 시각 기준 사용 |
| ② 무선은 **모니터 모드 캡처 PC**(10-verification 4장 C) | 시험 PC 부하 0 | M2U·무선 재전송 분석 |
| ③ **시험 PC에서 가벼운 캡처(ZeroLoss가 관리)** | 작음 | 외부 장비가 없을 때 |
| ④ 사람이 시험 PC에서 Wireshark 화면을 직접 켬 | **큼** (화면 그리기·메모리) | 권장하지 않음. 감지해서 경고 |

**③ ZeroLoss가 관리하는 캡처 규칙**
- Wireshark 화면이 아니라 **캡처 전용 프로그램**(dumpcap 또는 tcpdump)을 쓴다. Advanced 설정 `Packet capture: Off / Headers only / Full` (기본 Off).
- **헤더만 캡처(기본 권장):** 패킷 앞부분(예: 128바이트)만 저장 → 순번·타임스탬프·IGMP는 다 보이고 용량은 수십 분의 1.
- **캡처 필터:** IGMP + 시험 채널 그룹 주소 + 제어 포트만. 관계없는 트래픽은 안 받음.
- **순환 파일:** 일정 크기(예: 200 MB) 파일 N개를 돌려 쓰고, 사건(F23)이 나면 그 앞뒤 구간 파일만 증거 폴더로 보존.
- 캡처 프로세스는 낮은 우선순위, 시험 시작 때 같이 켜고 정지 때 같이 끈다(자식 프로세스로 묶어서 남지 않게).
- 캡처 부하(CPU·디스크 쓰기·캡처 드롭 수)를 1초마다 기록. **캡처 드롭이 생기면 캡처가 불완전하다고 표시**(측정 판정에는 영향 없음).
- 저장된 pcap은 보고서에서 [Open in Wireshark]로 연다(Controller PC에서).
- Windows는 Npcap이 필요하고 재배포 조건 때문에 사용자가 설치한다(Action Required 안내, 15-tools).

**④ 사람이 직접 Wireshark 등을 켠 경우**
- 시험 PC에서 캡처·분석 프로그램(Wireshark, dumpcap, tcpdump 등 ZeroLoss가 띄우지 않은 것)이 실행 중인지 **1분마다 감지**.
- 감지되면 Problems에 노랑 경고(ZL-RCV-013) + 보고서에 "External capture tool was running on RECV-01 from … to …". 그 구간 품질 판정은 그대로 하되, 수신 장비 자체 드롭이 늘면 보라 규칙(5.3)이 적용된다.

## 5. 1초 집계와 5분 보고 (통신사 방식)

통신사 IPTV 수신기(셋톱박스)는 여러 RFC 지표를 **매초 정리**하고, **5분마다** 서버로 보내 품질을 평가한다. ZeroLoss도 같은 방식을 쓰고, 서버 역할은 **Controller**가 한다.

### 5.1 흐름
1. 수신기(수신 PC, 태블릿)가 **1초마다** 지표를 계산해 로컬에 저장한다.
2. **5분마다** 5분 요약을 만들어 Controller에 전달한다(메인 화면 `Send quality reports` 체크박스가 켜져 있을 때. 꺼져 있으면 시험 종료 후 파일 회수로 계산, `03-features.md` F12). 연결은 Controller가 먼저 열어 가져간다(NAT 통과, `07-network.md` 6장). (태블릿: USB(adb) → 수신 Agent → Controller)
3. 1초 값은 **수신기 자기 화면**에 매초 표시한다(최근 1,000줄). Controller의 실시간 상태는 heartbeat 응답에 실린 현재 Jitter·Packet Loss로 보여준다(추가 트래픽 없음). 상세: `03-features.md` F12
4. 1초 원본 기록 전체는 시험 종료 후 회수한다. 전송이 실패한 5분 보고는 수신기에 보관했다가 재전송하고, 누락은 보고서에 표시한다.

### 5.2 5분 요약 항목
| 분류 | 항목 | 근거 |
|------|------|------|
| **손실** | 예상/수신/손실 패킷 수, 손실률, 손실 이벤트 수, 최대 연속 손실 길이, 중복, 순서 뒤바뀜 | RFC 3550, RFC 3357, RFC 3611 |
| **지터** | Jitter 평균/최대(ms), IPDV 최대·99백분위 | RFC 3550, RFC 3393/5481 |
| MDI | DF 최대(ms), MLR 최대(패킷/초) | RFC 4445 |
| 스트림 | TS sync loss, PAT/PMT 오류, CC 오류, PID 오류 개수 | TR 101 290 P1 |
| 전송량 | 비트레이트 평균/최소/최대 | - |
| 수신 장비 | 자체 드롭 수, 수신 버퍼 크기, (태블릿) Lock 상태 | 4.3, 4.5 |
| 재생 | 화면 멈춤 횟수, 캡처 결과 | - |
| 채널 | 채널 전환 횟수, 전환 시간 평균/최대 | 4.1 |
| 5분 평가 | 초록/노랑/빨강 (5.3) | - |

### 5.3 5분 단위 색상 평가
| 색 | 의미 | 조건 (기본값, 설정 가능) |
|----|------|------------------------|
| 🟢 초록 | 문제 없음 | 손실 0, 순번 오류 0, Jitter ≤ 150 ms, 수신 정상(최소 패킷·비트레이트 충족). **통과는 지터·손실로만 본다(2026-10-09 사용자 "지터, 로스 문제 없으면 패스", GAP-132)** |
| 🟡 노랑 | 문제 없음 + 주의 | 초록 조건 충족 + 주의 신호: Jitter 경고값(기본 50 ms) 초과, **도착 지연 변동 peak-to-peak 40 ms 초과**(DVB TS 102 034 7.2.1.1, 칸 안 `max(dhi) − min(dlo)`, 2026-09-24 결정), 태블릿 Lock 해제, 영상 외 트래픽 많음, **손실 없이 수신 장비 자체 드롭만 늘어남**(구현 중 결정 2026-09-24), **손실 없는 TR 101 290 P1 오류**(GAP-132, 이전에는 빨강) 등 |
| 🔴 빨강 | **DUT 원인 후보 문제** | 네트워크 손실 1개 이상(정렬 창을 넘긴 늦은 패킷 포함), Jitter > 150 ms, 수신 없음/PAT 없음, **채널 가입 실패(전환 뒤 첫 패킷 5초 안에 없음, NET-003)** — **단, 아래 보라 조건이 아닐 때** |
| 🟣 보라 | **도구·수신 장비 원인** (DUT 판정 불가) | 손실이 있지만 원인이 DUT가 아님: 수신 장비 자체 드롭(버퍼 넘침)으로 인한 손실, 송신 불안정 구간, 패킷 정상인데 재생 이상(4.6.2) |
| ⚪ 회색 | 데이터 없음 | 보고 누락, 장비 끊김, `NOT RUN` |

- 손실 분류 규칙: 같은 구간에 **수신 장비 자체 드롭 카운터가 늘었다면**, 그만큼의 손실은 수신 장비 원인(보라)으로 본다. 자체 드롭보다 손실이 더 많으면 차이만큼은 네트워크 손실(빨강)이다.
- **문제 구간으로 나누기(2026-09-26 사용자 결정, 20장 GAP-68):** 칸 전체가 아니라 **구간 안의 것만** 옮긴다. 구간 밖의 손실·P1 오류·Jitter는 지금처럼 빨강 기준.
  - **송신 문제 구간 → 보라:** 송신 PC의 SND-005(tsp 죽음, 다시 켜져 속도가 돌아올 때까지), SND-016(송신 멈춤·목표보다 5% 넘게 낮음·송신 NIC 드롭 — 그 동안 **매초** 사건), 송신 PC 시험 NIC의 링크 끊김 NET-015(다시 올라올 때까지). 구간 = **사건 앞 1초 ~ 끝난 뒤 2초**. 그 동안 모든 수신기의 손실·P1 오류·Jitter·최소 수신 미달은 보라(도구 원인).
  - **PC 바쁨 구간 → 노랑 경고:** SYS-003(CPU 90% 넘게 10초 이상, 풀릴 때까지) 앞 1초 ~ 뒤 2초와 겹친 칸에 "PC busy"(송신 PC면 모든 수신기, 수신 PC면 그 수신기). 판정 기준은 그대로(손실은 손실).
  - **화면 잠김 구간 → 노랑 경고:** RCV-006(수신 PC 화면이 잠기거나 꺼짐, 풀릴 때까지) 앞 1초 ~ 뒤 2초와 겹친 그 수신기의 칸에 "screen locked".
  - **송신 느려짐 구간 → 노랑 경고:** SND-017(목표보다 1% 넘게 낮음, 매초) 앞 1초 ~ 뒤 2초와 겹친 칸에 "Sender slow". **3초 연속일 때만**(2026-10-09 GAP-147, RealTest 참고 도구의 "비트레이트 하한은 연속 3개 창": 40분 HD 시험에서 −1.0% 1초가 두 번 칸을 노랗게 함). 구간은 그 3초의 첫 초 앞 1초부터.
  - **유선 수신 PC의 받는 NIC 링크 끊김 → 회색:** NET-015(유선) 앞 1초 ~ 다시 올라온 뒤 2초 동안 그 수신기의 손실·P1·최소 수신 미달은 회색(케이블인지 DUT 포트인지 알 수 없음, 판정 불가). **무선 수신 PC의 Wi-Fi 끊김은 DUT(AP) 결함일 수 있으므로 규칙대로(빨강)**, 사건·신호 기록만.
  - 시각은 Controller 기준(D39): 사건과 수신기 1초 기록(heartbeat `last_1s`)을 **Controller가 받은 시각**으로 맞춘다. heartbeat가 놓친 초는 이웃 초로 시각을 채우고, 그 초들의 손실(요약 합계 − 아는 초의 합)은 놓친 초가 모두 구간 밖이면 빨강, 하나라도 구간 안이면 그 구간 색(가를 수 없음).
  - Controller는 사건이 늦게 도착해도 되도록 요약을 받은 뒤 **3초 기다렸다** 칸을 판정하고, 나눈 값을 `summaries.jsonl` 줄의 `trouble`에 남긴다(02 6, 보고서·복구 판정이 같은 값을 씀).
  - 칸 색 순서: 빨강 > 보라 > 회색(수신 링크) > 노랑 > 초록.
- 색은 Controller가 5분 요약 수치로 **직접 계산**한다(수신기 자체 평가는 참고만).

### 5.4 최종 판정 (모든 문서의 기준)
| 판정 | 조건 |
|------|------|
| **PASS** | 계획 시간을 다 채움 + 빨강·보라·회색 없음 (노랑은 허용, 보고서에 "with warnings" 표시) |
| **FAIL** | 빨강이 한 칸이라도 있음 (중단 여부와 무관) |
| **INCOMPLETE** | 빨강은 없지만 PASS 조건을 못 채움: 중간 중단, 회색 있음, 보라 있음(도구·수신 장비 문제로 판단 불가). 보고서에 이유를 적는다 |

- 100시간 시험 = 5분 칸 1,200개(장비별).

## 6. 제어·보고 트래픽 규칙
- 운영 제어와 보고는 TCP 10992로 하고(설치·업데이트는 10991, 결과 조회 웹은 10993), **데이터 양을 최소화**한다(heartbeat + 5분 요약, 원본 기록은 시험 종료 후 회수).
- 태블릿의 보고와 화면 캡처는 **USB(adb)**로 수신 Agent를 거친다. DUT 무선 구간을 쓰지 않는다.
- 유선 수신 PC의 제어 경로가 DUT를 지나는 구성이면 보고 트래픽 양을 기록하고, 보고서에 표시한다.
