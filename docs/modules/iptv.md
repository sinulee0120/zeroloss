# IPTV 모듈 — 1. 송신 명령 구성

> P1(위험 확인) 전에 정할 것. 송출이 흔들리면 모든 측정이 흔들리므로, **송신은 정해진 명령 틀로만** 만든다.
> 표시: **✓** = 공식 문서로 확인(Context7, 2026-09-23: TSDuck 공식 문서, FFmpeg 공식 문서) / **?** = P1에서 실제 명령으로 확인 후 확정.
> 명령은 코드에서 문자열로 흩어 만들지 않는다. 송신 모듈의 **명령 조립 함수 하나**가 아래 표의 값으로만 만든다(12-architecture 1-2).

## 1. 전체 흐름
```
[사전 준비 모드 — 기본]
 원본 mp4 ──ffmpeg(변환, CBR TS)──▶ 준비 파일 .ts ──▶ 검사(tsanalyze) ──▶ 보관
 송출:  tsp -I file(무한 반복) → continuity --fix·pcradjust(반복 이음새) → -P regulate(정속) → -O ip 127.0.0.1(RTP, 7 TS/데이터그램) → zeroloss pace(데이터그램을 바이트 그대로 len×8/rate마다, TTL·송출 NIC, 20장 GAP-160) ──▶ 멀티캐스트

[실시간 인코딩 모드 — 송신 PC가 빠를 때]
 원본 mp4 ──ffmpeg(실시간 변환, CBR TS를 표준 출력으로)──▶ tsp(표준 입력) → regulate → -O ip ──▶ 멀티캐스트
```
- 두 모드 모두 **마지막 송출은 TSDuck(tsp)**이 한다. 정속·RTP·묶음 크기를 한곳에서 통일하기 위해서다.
- 채널 하나 = tsp 프로세스 하나. 채널 3개 = 프로세스 3개(서로 독립, 하나가 죽어도 나머지는 계속).

## 1-1. 원본 영상 (송출 소스, S-48)
- **기본 = 자동 생성(Generated).** 사용자 파일이 설정되지 않았거나, 설정한 파일이 없거나 손상되었거나, 검증·자동 시험 중일 때 쓴다. 사람 손 0, 저작권 걱정 없음, 매번 같은 영상.
  - ffmpeg 가상 입력으로 만든다 ✓(2026-09-25 실측, V12): 움직이는 시험 화면(`testsrc2`, 화질의 영상 해상도·30 fps) + **채널 이름 글자**(`ZeroLoss CH1`) + 프레임 번호 표식(3.4) + 소리(`sine`, 채널마다 다른 높이: CH1 1 kHz, CH2 1.5 kHz, CH3 2 kHz — 다른 채널 소리가 섞이면 알아챔).
  - 길이 10분, 그 뒤 4.2 이음새 처리. 결과는 송신 PC 데이터 폴더 `generated/`에 화질·비트레이트·채널별로 보관하고 없으면 다시 만든다.
  - 한계: 실제 방송보다 화면이 단순해 인코딩 부담이 다르다. 네트워크 판정에는 영향 없음(CBR `-muxrate`로 비트레이트 고정).
- **사용자 파일:** 사용자가 mp4를 송신 PC의 **미디어 폴더**에 넣는다.
  - Windows `C:\ZeroLoss\Media\`, Linux `/var/lib/zeroloss/media/` (설치 때 만들고, 제거 때 사용자 데이터로 보존).
  - **Linux: 사용자의 `~/Videos`도 그대로 쓴다(2026-10-03 사용자 "home/Videos에 넣어놨지" → "니가해", 20장 GAP-109):** 노드 서비스 계정은 홈 폴더를 못 읽으므로 이 모듈의 `module.json` `media_import` = `{"from": "Videos", "into": "media", "ext": ["mp4", "mkv", "mov", "m4v", "ts"]}`로 Deployer가 미디어 폴더에 하드 링크(또는 복사)로 가져온다(규칙은 12 1장 `media_import`). 사용자는 `~/Videos`에 넣기만 하면 몇 분 안에 Source video 목록에 나온다.
  - Controller는 `GET /v1/modules/iptv/sender/sources`로 이 폴더의 파일 목록과 ffprobe 결과를 받아 **Advanced → Source video**에 채널별 선택 목록으로 보여 준다(맨 위 항목은 항상 `Generated (default)`).
  - 선택한 파일도 4.1 변환 때 프레임 번호 표식과 채널 이름을 새겨 넣는다.
- **대체 규칙:** 선택한 파일이 시작 때 없거나 손상 → 시작을 막지 않고 **자동 생성으로 대체**, Problems에 ⚠, 보고서 "Settings used"에 `Source: Generated (fallback, file missing)`로 기록(SND-001).
- **구현 규칙(2026-09-26, 20장 GAP-62):**
  - 계획에는 `settings.S-48` = 채널별 `{"1": "Generated", "2": "시험 영상 UHD (1).mp4"}`(미디어 폴더 안의 **파일 이름만**, 경로·`..` 금지 → RUN-014). 적지 않은 채널은 Generated.
  - 변환은 **앞 10분**(자동 생성과 같은 길이, 2026-09-26 사용자 결정; 더 짧은 파일은 그 길이). **또는 영화 전체(S-55 `Whole movie`, 2026-10-08 사용자 "추천대로 해", GAP-118):** 이름 부분 `_f<digest>_whole`로 10분짜리와 따로 보관, 둘 다 한 번만 만들고 재사용; 디스크 확인은 영화 길이로을 1-1-2와 똑같이(대기열 하나, 진행률, Cancel, 4.3 검사, `.part`) 한다. 보관 이름은 영어 `ch<n>_<화질>_<Mbps>M_f<원본 요약 8자>.ts`(원본 요약 = 이름·크기·수정 시각의 SHA-256) — 원본이 바뀌면 새로 만든다. 설명 `.json`에 원래 이름(NFC)·원본 해상도·fps·`upscaled`.
  - **소리는 영상과 함께 끝낸다(2026-10-04 기준선 실기, 20장 GAP-114):** 송출은 파일 끝에서 처음으로 이어지는데(`--infinite`), 소리가 영상보다 길면 이음매마다 그림이 멈춘다(실측: 소리가 0.3초 길면 그림 0.37초 멈춤, 사람 눈에 보임). 변환(자동 생성 포함)은 소리를 `apad`로 늘리고 `-shortest`로 영상 끝에서 함께 끝내며, 만든 뒤 ffprobe로 마지막 영상·소리 끝의 차이가 **한 프레임(1/30초) 이하**인지 확인한다(넘으면 SND-020, 보관하지 않음). 보관 파일의 확인 값(`.json` `key`)에 **만드는 ffmpeg 명령의 요약(`recipe`)**을 넣어, 명령이 바뀌면 전에 만든 파일은 사람 손 없이 다시 만든다(이 수정이 이미 만든 파일에도 닿게). 이음매의 그림 공백은 실측 약 53 ms(한 프레임 + ffmpeg 다중화가 남기는 약 20 ms, 자동 생성 영상도 같음 — 고치기 전 영화는 0.37초): 시험은 **두 프레임(67 ms) 이하**를 확인하고, 한 프레임 이하로 줄이기는 남은 할 일(20장 GAP-114 ③).
  - 크기·fps는 화질에 맞춘다(`scale`·`fps=30`, 3장). 원본이 화질보다 작으면 늘려서 쓰고 `upscaled: true`(K-28 ⚠, 보고서 "Upscaled").
  - 목록: 노드 `GET /v1/modules/iptv/sender/sources`(02 4) — 미디어 폴더의 영상 파일(`.mp4 .mkv .mov .m4v .ts`)마다 ffprobe로 코덱·해상도·fps·길이·소리 유무와 화질별 맞음(K-28), 그리고 이미 만들어 둔 파일(`made`: 화질·채널·Mbps·전체 여부). 화면 목록은 채널마다 `✔ ready, starts at once`(Start가 바로 씀) 또는 `made first (takes a while)`를 붙인다(2026-10-17).
  - 원본 식별(2026-10-17, 사용자 "이미 만든걸 또 만들필요없게"): 만든 파일 이름의 `f<digest>`는 원본의 **내용**(크기 + 앞뒤 4 MiB의 sha256 앞 8자리)이다. 이름·폴더·수정 시각이 달라도(다른 PC로 복사, 오프라인 키트의 `sample_1_original`) 같은 원본이면 만든 파일을 그대로 쓴다. 그 전에 이름+크기+수정 시각으로 만든 파일도 원본이 그대로면 계속 쓴다(몇 시간짜리 UHD를 다시 만들지 않음). Controller `GET /v1/controller/sources?node=<송신>`(모듈 계약 `sources_step`), CLI `zeroloss sources --node <송신>`(13).
  - 보고서 `source`: 채널별 `generated` / 원본 파일 이름, `source_fallback`: 대체된 채널 목록(송신 상태의 `source` = `generated_fallback`).

- **송출 파일은 수신 장비가 하드웨어로 풀 수 있는 형식으로 만든다(2026-09-26 사용자):** UHD = HEVC **Main(8비트)**, HD = H.264 High(8비트), yuv420p. 원본이 10비트·HDR(예: Dolby Vision 클립)이어도 변환 결과는 8비트 — 6세대 Intel 이상 내장 그래픽·태블릿이 하드웨어로 푼다(05 4.2-1 실측: 첫 실제 환경 T460에서 우리 UHD 파일 VA-API 해독 4.3배, 원본 10비트는 하드웨어 해독 실패). 수신 장비가 이 형식을 하드웨어로 못 풀면 RCV-015 ⚠.

### 1-1-1. 파일 이름에 한글 등 비영어 문자 (2026-09-24 사용자 요구)
영상 파일 이름에 **한글·공백·기호**가 있어도(예: `시험 영상 UHD (1).mp4`) 준비·송출·재생·태블릿 전송·보고서·로그·결과 웹·CLI 어디서도 깨지거나 실패하지 않아야 한다. RPT-002(경로의 비영어 문자)를 영상 파일까지 구체화한 규칙.
- **외부 도구 호출:** 경로는 항상 인자 목록으로 넘긴다(셸 문자열·따옴표 조립 금지). Windows는 유니코드 API(CreateProcessW)로 실행되므로 그대로 전달. 도구 출력은 바이트로 받아 UTF-8로, 안 되면 `errors="replace"`로 읽는다(Windows 콘솔 코드 페이지 cp949에 기대지 않음).
- **유니코드 정규화:** 같은 한글도 NFC(윈도·리눅스 보통)와 NFD(맥에서 복사한 파일)로 바이트가 다르다. 계획 파일의 이름으로 파일을 못 찾으면 NFC·NFD 두 형태로 다시 찾는다. 보고서·기록에는 **NFC로** 적는다.
- **저장 형식:** JSON·JSONL은 UTF-8, 한글을 그대로(`\uXXXX` 대신 읽을 수 있게) 쓴다. 보고서 HTML은 `<meta charset="utf-8">` + HTML 이스케이프. CSV 내보내기는 UTF-8 BOM(엑셀에서 한글이 안 깨지게).
- **준비 파일 이름:** 사전 준비로 만드는 파일(`ch1_UHD_35M.ts` 등)은 영어 이름으로 만들고, 원본 이름은 준비 파일 옆 설명(`*.json`)과 보고서 `source`에 원래대로 남긴다(도구·OS 차이를 한 번에 피함).
- **태블릿 전송(adb push):** 원본 이름 그대로 보내지 않고 준비 파일의 영어 이름으로 보낸다.
- **화면:** 긴 한글 이름은 말줄임 + 툴팁(11-ui 1.11), 글꼴은 한글 글리프가 있는 것.
- **검사:** 자동 시험(10 3장) — 한글·공백·괄호·이모지 이름으로 준비·송출·수신·보고서까지 한 번, NFD 이름 계획 → 찾음, 보고서 HTML·summary.json에 이름이 그대로. Windows는 V17(P1)에서 같은 시험.

### 1-1-2. 자동 생성 영상 만들기: 시점·보관·검사·취소 (2026-09-25 사용자 결정, 20장 GAP-50)
- **만드는 곳:** 송신 PC(그 PC의 ffmpeg). 채널·화질·비트레이트마다 파일 하나: `<데이터 폴더>/modules/iptv/cache/generated/ch<n>_<화질>_<Mbps>M.ts`(모듈 캐시, 06 12장) + 옆에 설명 `….json`(원본 `generated`, 길이, 표식 판, SHA-256, 4.3 검사 결과, ffmpeg 버전). 설명 파일이 없거나 키가 다르거나 검사 불합격이면 없는 것으로 보고 다시 만든다.
- **시점 ① Start 때 없으면:** 시작 절차(F17) 5단계 "Start sending" 앞에서 없는 채널만 만든다. 상태창에 `Preparing videos: CH1 UHD 42% · about 38 min left`. **이때만 버튼이 Cancel(누를 수 있음)** — 누르면 시작만 되돌린다(USR-006). **만들던 파일은 송신 PC가 뒤에서 끝까지 만든다(2026-10-04 GAP-116):** 사용자 "그린랜드 파일 고르고 시작하면 11분을 기다려야해 … 미리 파일을 만든거면 계속 써먹어야지" — 전에는 Cancel·Stop이 만들던 파일을 지워 다시 Start하면 처음부터 만들었다. 다 만든 파일은 남겨 다음에 다시 쓴다. 다른 준비 단계는 지금처럼 Starting…(잠금).
- **시점 ⓪ 영화를 고르는 순간(2026-10-04 GAP-116):** 화면에서 Source video를 고르면(시험 사이, 방송이 꺼져 있을 때) Controller가 바로 미리 만들기(02 2-4, `sources`)를 보낸다. Source video 줄 아래에 `Making the CH1 video: 34% · about 7 min left` / `CH1 video ready`. Start 때는 남은 만큼만 기다린다.
- **최신 선택이 이긴다:** Start나 새로 고른 영화의 만들기 요청은 `only`로 보낸다 — 지금 고른 것에 필요 없는 만들기(다른 영화·바뀐 화질)만 멈추고(만들던 파일 삭제), 필요한 것은 하던 곳에서 계속. 노드 안전 정지(CTL-008)도 만들기를 멈춘다 — **단 시험이 없는데 Controller만 다시 켜진 경우("Controller restarted")는 만들기를 계속한다(2026-10-09 GAP-124):** 창을 닫으면 쉬는 서비스도 끝나므로(06 4.1-1), 창을 닫았다 열기만 해도 45.8%까지 만든 영화가 지워졌음(실기 02:36:35Z).
- **시점 ② 미리:** `zeroloss prepare`(13장) 또는 같은 Core 명령으로 시험 전에 만들어 둔다(첫 UHD 시험의 기다림을 없앰).
- **한 번에 하나씩:** 인코딩은 CPU를 다 쓰므로 채널을 차례로 만든다(작업 줄 하나). 같은 파일을 두 번 만들지 않는다.
- **만드는 중 파일:** `….part.ts`로 쓰고 검사 통과 후에만 이름을 바꾼다(중간에 죽어도 반쪽 파일을 쓰지 않음). 노드 시작 때 남은 `.part` 파일은 지운다.
- **진행률:** ffmpeg `-progress`의 출력 시각 ÷ 길이. 남은 시간 = 지금 속도로 계산. **60초 동안 진행이 없으면** 실패(SND-020).
- **디스크:** 만들기 전에 (예상 크기 + 1 GB) 여유를 확인, 부족하면 SND-020. 예상 크기 = 비트레이트 × 길이(UHD 35 Mbps 10분 ≈ 2.6 GB).
- **시간 참고(2026-09-25 T460 4코어 실측, veryfast):** 10분짜리 HD ≈ 5분, UHD ≈ 66분(채널당). **2026-10-24: UHD를 ProBook에서 veryfast로 만들면 10분 영상에 약 2시간(초당 2.5프레임)** → UHD는 x265 `ultrafast`로 바꿈(아래 인코딩 속도 줄, 약 2배 빠름). 새 Controller PC는 더 빠름.
- **모듈 소유:** `generated/`는 IPTV 모듈 캐시 안에 있다 — 모듈 제거 때 캐시 폴더째 지운다(06 12장, 02 14 `tree`).
- 계획 파일 `files`에 적은 준비 파일이 없거나 손상이면 그 채널도 자동 생성으로 대체(1-1 대체 규칙, SND-001 ⚠).

### 4.2 반복 이음새 처리 (SND-004) — 확정 ✓ (2026-09-24 실측)
- **송출 때 TSDuck 공식 플러그인으로 이음새를 잇는다:** `-P continuity --fix`(CC를 반복 지점에서 이어 붙임) → `-P pcradjust --bitrate <muxrate>`(CBR 위치 기준으로 PCR을 다시 찍고, PTS·DTS도 같은 양만큼 옮김).
  - 실측: UHD 10초 파일을 3회 반복 → 반복 지점 포함 PCR 1,503개가 위치와 1 ms 안으로 일치, PTS 큰 점프 없음, TSDuck `continuity` 검사 0건, 우리 분석기 CC·P1 오류 0.
- **`tsfixcc --circular`는 쓰지 않는다:** 채워 넣는 빈 패킷이 페이로드 없이(afc=10) CC를 올려 ISO/IEC 13818-1 위반 → 반복마다 CC 오류(실측 62개/회, TSDuck 자체 검사도 "incorrect CC increment without payload"로 같은 판정).
- 주의(공식 경고) ✓: CC 고치기는 **손실을 숨길 수 있다.** → **송신 파이프라인(파일 입력 직후)에서만** 쓴다. 이 지점은 네트워크 이전이라 숨길 손실이 없다. 수신·측정 경로에서는 절대 쓰지 않는다. 준비 파일은 4.3 검사로 원본 자체의 CC 오류 0을 먼저 확인한다.
- 남은 확인: VLC 재생에서 반복 지점 끊김 0(V10 재생 부분, 재생기 연동 때).

### 4.3 준비 파일 검사 (보관 전 필수)
- 비트레이트가 목표 ±0.5% 안, CC 오류 0, PAT/PMT 간격, PCR 간격, 서비스·PID가 2장 표와 일치.
- **구현(2026-09-25, 20장 GAP-50):** 외부 도구 대신 우리 TR 101 290 분석기(`core/blocks/ts_analyzer.py`)에 파일을 **CBR 이론 도착 시각**(바이트 위치 ÷ 목표 비트레이트)으로 넣는다 → 우선순위 1 오류 0(CC·PAT/PMT 0.5 s·PID 5 s), PAT 서비스 번호 = 채널, PMT PID 0x1000, 영상·음성 PID 0x100·0x101. 비트레이트 = 첫·마지막 PCR 사이 바이트 ÷ PCR 시간 차(±0.5%), PCR 간격 최대 ≤ 40 ms(3장).
- **표식 검사(2026-09-26 사용자 결정 20장 W-7):** 위 검사가 통과하면 파일을 한 번 해독해 **모든 프레임의 표식**(3.4)이 (채널, 0, 1, 2, …) 순서인지 본다. ffmpeg가 프레임마다 막대 줄만 잘라 96×12 회색으로 줄여 파일로 쓰고(10분 UHD 약 20 MB) 우리가 읽는다. 진행률·취소·60초 무진행 감시는 만들기와 같다(1-1-2). 틀리면(읽을 수 없음·채널 다름·번호 건너뜀·반복) 불합격 → SND-020("frame marker … at frame n"), 다시 요청하면 다시 만든다. 이유: 표식이 틀린 파일은 재생 이상(건너뜀·중복)을 거짓으로 만든다.
- 통과한 파일만 보관소에 넣고 SHA-256·검사 결과를 기록. 시험 보고서에 사용 파일과 해시를 적는다.

### 4.5 프라임(뚫기) 방식 — SDK 공유기 (S-18, 2026-09-25 사용자 결정, 20장 GAP-57)
- **왜:** 공유기 SDK 버전에는 M2U·IGMP 프록시·IGMP 스누핑이 하나도 없다. NAT 모드에서 WAN 쪽 멀티캐스트는 LAN으로 들어오지 않는다. 그래서 수신기가 먼저 LAN→WAN으로 작은 UDP를 보내 NAT 길을 열고("프라임"), 송신이 그 길로 **유니캐스트** RTP를 보낸다 → WAN에서 들어온다(사용자).
- **언제(구분해서 시작, 2026-09-25 사용자):** 상용 펌웨어는 보통 IGMP·M2U가 켜져 있고, 개발용·SDK는 꺼져 있다. S-18 **Auto(기본)**: 사전 점검 5단계에서 ① 보통 멀티캐스트 시험 송출 → 오면 멀티캐스트로 시험 ② 아무도 못 받고 NAT 모드면 프라임 시험 송출 → 오면 **프라임으로 시험**하고 체크리스트·보고서에 "No IGMP proxy on the DUT (development/SDK build?) — primed unicast" ③ 둘 다 안 오면 NET-003. 대기 중 가벼운 점검은 트래픽이 없어 모름(Start에서 정해짐). **Off** = 멀티캐스트만(안 오면 NET-003), **On** = 처음부터 프라임. 정해진 방식은 보고서 `dut.multicast_path` = `"igmp"` / `"primed"`(02 10). 켜면 보고서 맨 위에 "Primed unicast — not the real IPTV path"(K-14), M2U 결과 `n/a`(유니캐스트라 의미 없음), IGMP 버전 칸 `n/a`. Bridge 모드와는 함께 못 씀(K-15 ⛔, 뚫을 NAT가 없음).
- **흐름 둘(분석·재생 별도 소켓 원칙):** 수신 PC의 분석기와 재생기는 **각자 자기 포트에서 따로 프라임**하고, 송신은 그 채널을 **두 벌** 보낸다(분석기 몫·재생기 몫). DUT를 지나는 양이 그 수신기 채널의 2배(UHD 35 → 70 Mbps)임을 사전 점검·보고서에 적는다. 재생 끔(S-49 Off)이면 한 벌. 태블릿 앱도 같은 규칙(P4).
- **송신이 목적지를 아는 법("송신이 프라임에 답함"):** 송신 PC는 채널·흐름마다 프라임 포트 하나에서 기다린다. 수신기가 그 포트로 프라임(작은 UDP, 내용 `ZLPRIME <run_id> <ch> <flow>`)을 보내면, 송신은 **보이는 출발 주소:포트**(= DUT WAN IP와 NAT가 고른 포트)로 그 흐름을 보낸다 — NAT가 포트를 바꿔도 된다. 흐름의 **출발 포트 = 프라임을 받은 포트**여야 한다(포트 제한 NAT가 다른 출발 포트는 막음).
- **유지:** 수신기는 **10초마다** 같은 소켓에서 프라임을 다시 보낸다(NAT UDP 만료 전에). 송신은 30초 동안 프라임이 없으면 그 흐름을 멈춘다(수신기가 사라진 흐름을 계속 보내지 않게, 사건 기록). 출발 주소가 바뀌면(NAT 재시작) 새 주소로 옮기고 기록 — 그 경계 손실은 원인 후보로 표시.
- **시작·정지 순서(05 2.1-2):** 송신 준비(프라임 포트 열기, 영상 준비) → 수신 소켓 열기 → 프라임 → 송신이 흐름 시작·안정 → 안정화 후 측정. 정지는 수신 마감 → 프라임 멈춤 → 송신 흐름 정지.
- **사전 점검 5단계:** 시험 송출도 같은 방식(프라임에 답해 1 Mbps 2초). 0개면 NET-003("The primed path did not open").
- **2026-09-25 루프백 실측(scratch 시험, TSDuck 3.45):** ① tsp `-O ip … --local-port P`로 출발 포트를 정할 수 있다 ✓(받는 쪽에서 출발 포트 = P 확인). ② 그런데 우리 프라임 소켓을 같은 포트 P에 함께 묶으면(SO_REUSEPORT) **들어오는 프라임 20개가 모두 tsp 소켓으로 가고 우리 소켓엔 0개** ✗ — 한 포트를 두 소켓이 나눠 쓰는 방식은 못 쓴다.
- **그래서 설계(P1 ③ 실기 확인 전 제안):** 송신은 흐름마다 포트 둘 — tsp가 보내는 **P**(`--local-port P`)와 프라임을 듣는 **Q**(우리 소켓만). 수신기는 받는 포트에서 **P와 Q 둘 다로** 프라임을 보낸다: P로 보낸 것은 NAT의 걸러내기(포트 제한 NAT)를 열고, Q로 보낸 것으로 송신이 NAT가 고른 주소:포트를 안다. NAT가 목적지와 상관없이 같은 바깥 포트를 쓰는 것(RFC 4787 REQ-1, 끝점 무관 매핑)에 기댄다 — 목적지마다 포트를 바꾸는 NAT(대칭형)면 흐름이 안 오고 NET-003 "The router's NAT changes the port per destination"(18장 RFC 4787). 재생기(VLC) 포트에서 보내는 프라임은 그 포트에 소켓을 묶지 않도록 **raw 소켓으로 출발 포트를 적어** 보낸다(Linux `CAP_NET_RAW`, 06 4.3에 있음) — 분석기 프라임은 분석기 자기 소켓에서 보낸다.
- **구현 규칙(2026-09-25):**
  - 포트(채널 c, 흐름 f = 0 분석기 / 1 재생기, 기준 = S-14 포트): `base = 포트 + 100×c + 10×f` → 송신 tsp 출발 **P = base**, 송신 프라임 듣기 **Q = base+1**, 수신 소켓 **R = base+2**. 한 PC가 송수신을 같이 해도 겹치지 않는다(루프백 시험).
  - 프라임 내용: `ZLPRIME <run_id> <ch> <f>` ASCII. 송신은 run_id·채널·흐름이 맞는 것만 받는다.
  - **채널 전환(F19, 2026-10-01, 20장 GAP-91):** 수신기는 옛 채널을 떠나기 직전 같은 소켓에서 Q로 `ZLPRIME <run_id> <ch> <f> STOP`을 보낸다. 송신은 지금 보내는 목적지에서 온 STOP이면 그 흐름을 바로 멈춘다(사건 `ZL-INFO`, SND-021 아님). STOP이 안 닿으면 전처럼 30초 뒤 멈춘다. 다른 주소에서 온 STOP은 무시한다.
  - 송신 흐름(`sender/start` params `prime: {"flow": f, "p": P, "q": Q, "run_id"}`): Q를 열고 바로 돌아온다(상태 STARTING, `waiting_prime`). 첫 프라임이 오면 그 출발 주소:포트로 tsp(`--local-port P`)를 띄우고 속도 안정 확인(SND-019 규칙 그대로) → RUNNING. 출발 주소가 바뀌면 tsp를 새 주소로 다시 띄우고 SND-021 ⚠. 30초 동안 프라임이 없으면 그 흐름의 tsp를 멈추고 SND-021 ✖(다시 오면 다시 보냄).
  - 수신(`receiver/start` params `prime: {"sender_ip", "flows": [{"f": 0, "p", "q", "r"}, {"f": 1, …}]}`): 분석기는 R₀에 유니캐스트로 묶고(가입 없음) **그 소켓에서** P₀·Q₀로 프라임. 재생기는 `rtp://@:R₁`로 받고, 프라임은 raw 소켓으로 출발 포트 R₁을 적어 보낸다(`core/blocks/udp_prime.py`). 시작 때 1초 간격 3번, 그 뒤 10초마다. raw 소켓을 못 열면(권한) RCV-024로 시작 실패(재생 끔이면 raw 불필요).
  - `sender_ip`(수신기가 프라임을 보낼 곳) = 계획 `nics`의 송신 NIC IP, 없으면 Controller가 채우는 `hosts`(02 11-1)의 송신 PC 주소.
  - 시작 단계: ① 송신 흐름 열기(프라임 기다림) ② 수신 시작(프라임 시작) → 송신이 흐름 시작 → 수신 안정화 → 측정. 송신이 안 오면 수신 안정화 실패(RUN-009)와 송신 SND-021.
  - 필요 대역(05 1.8): 프라임은 수신기마다 따로 보내므로 송신 WAN = 채널 × 수신기 × 흐름 수, 수신 LAN = 받는 채널 × 흐름 수.
  - 사전 점검 5단계(S-18 Auto): 멀티캐스트 시험이 0개이고 NAT(07 4)이면 Controller가 모듈에 `probe_fallback(plan)`을 물어 프라임 계획으로 다시 시험 → 되면 그 계획으로 시험. 모듈 계약 `path_note(plan)` = `{"path": "igmp"|"primed", "note"}`(보고서 `dut.multicast_path`, 체크리스트 한 줄). 프라임이면 M2U는 `{"state": "n/a"}`.
- **P1 확인 ?(실제 소켓·tsp로 먼저 시험):** ① tsp `-O ip`에 출발 포트를 정하는 옵션(`--local-port`)과 같은 포트에서 기다리는 프라임 소켓이 함께 쓰일 수 있는지(한 포트를 두 소켓이 쓸 때 들어오는 프라임이 우리 소켓으로 오는지) ② 수신 PC에서 재생기(VLC)의 포트로 프라임을 보낼 때 들어오는 영상이 재생기 소켓으로 가는지(연결된 UDP 소켓 우선 규칙) ③ 실제 SDK 공유기의 NAT 종류(포트 유지·주소 제한)와 UDP 만료 시간.

## 5. 실시간 인코딩 모드

- `-re`(원본 속도로 읽기), `-stream_loop -1`(무한 반복) 사용 여부와 조합은 P1 확인 ?

- 반복 지점 시간값 되감김은 ffmpeg가 이어서 찍는지 P1 확인 ?

## 6. 송출 중 감시 (05-standards 3.4, 3.4-1)
- tsp가 보고하는 비트레이트·패킷 수 + **NIC 전송 카운터**를 1초마다 비교.
- 기준: 목표 ±1% / 최대 공백 50 ms(노랑), ±5% / 100 ms(보라), 1초 0(멈춤 → 3초면 강제 재시작).
- 채널마다 tsp를 자식 프로세스로 묶어(Job Object·프로세스 그룹) Agent가 죽으면 함께 종료.

# IPTV 모듈 — 2. 원인 분석 규칙표

> P4 전에 정할 것. 문제가 생기면 수신 자료의 **패턴**으로 원인 후보를 자동으로 적는다(01-overview 핵심 기능 5).
> **규칙은 판정을 바꾸지 않는다.** 색·PASS/FAIL은 05-standards 5.3~5.4로만 정하고, 규칙은 "왜 그랬을 것 같은지"를 근거와 함께 **후보**로 보여준다.

## 2.0 공통
- 규칙은 **5분 요약 + 1초 기록 + 사건 기록 + 송신 기록**만으로 계산한다(수신기·송신기가 이미 모으는 값, 02-data).
- 여러 규칙이 동시에 맞으면 모두 보여주고 **확신도 순**으로 정렬: 높음 / 중간 / 낮음.
- 문장 형식(보고서·Problems 공통, 영어): **무엇이 → 왜 그렇게 보는지(수치) → 다음에 확인할 것**.
  예: "Router: IGMP membership timeout suspected (Tablet-2). Loss began 261 s after the join and stopped at the next join. Next: check that the router sends IGMP queries."
- 분류: **Router**(공유기) / **Receiver**(수신 장비) / **Sender**(송신) / **Environment**(무선 환경 등)
- 규칙마다 시험 데이터(합성 자료)로 **맞는 경우·안 맞는 경우** 자동 시험을 둔다(10-verification).
- IGMP 기본 시간값(RFC 2236): Query Interval 125초, Query Response Interval 10초, Robustness 2 → **Group Membership Interval = 2×125+10 = 260초(IGMPv2), IGMPv3(RFC 9776)·MLDv2(RFC 9777)는 2×125+2×10 = 270초** — 05 1.11. 공유기가 질의를 안 하거나 유지가 잘못되면 이 근처에서 끊기는 일이 흔하다.

# IPTV 모듈 — 3. 재생 이상 감지 값

> P3 전에 정할 것. 재생 이상(화면 멈춤·깨짐·끊김, 소리 끊김)을 **어떤 값으로 읽어서** 판단하는지 정한다. 05-standards 4.6.2(재생 이상 ↔ 패킷 이상 대조), F23(증거 수집)의 입력이다.
> 표시: **✓** = 공식 문서로 확인(Context7, 2026-09-23: mpv 공식 매뉴얼, AndroidX Media3 소스·API) / **?** = P1(V6)에서 확인 후 확정.

## 3.0 원칙
- 재생기마다 알려 주는 값이 다르므로, **ZeroLoss 공통 재생 이상 종류**로 바꿔서 기록한다(재생기 연결 코드 한 곳에서 변환).
- 재생기 값만 믿지 않는다. **재생기와 무관한 두 번째 감지**(3.4 영상 속 표식)를 함께 써서 서로 대조한다.
- 값 읽기는 **변할 때 알림을 받는 방식**(observe)을 우선하고, 안 되면 1초마다 읽는다. 재생에 부담을 주지 않는다(05-standards 4.2).

## 3.1 공통 재생 이상 종류 (1초 기록의 `pb` 값, 02-data 7장)
| 종류 | 뜻 | 기록 |
|------|----|------|
| `ok` | 정상 재생 | — |
| `freeze` | 화면이 멈춤(새 프레임이 안 나옴) | 시작·끝 시각, 멈춘 시간 |
| `drop` | 프레임 버림(늦게 도착·처리 못 함) | 1초당 버린 수 |
| `glitch` | 디코딩 오류·블록 깨짐 | 오류 수, 블록 깨짐 정도 |
| `audio_gap` | 소리 끊김(오디오 버퍼 바닥) | 횟수, 길이 |
| `av_desync` | 영상·소리 어긋남이 기준 초과 | 어긋난 시간(ms) |
| `buffering` | 재생기가 데이터를 기다리며 멈춤 | 시작·끝 |
| `restart` | 재생기 오류 후 재시작 | 오류 내용 |
| `none` | 재생해야 하는데 재생기가 없거나 표시 프레임이 오래 늘지 않음(RCV-020·TAB-016) | 재생 없는 시간 |
- 한 초에 여러 종류가 겹치면 하나만 쓴다: `none` > `restart` > `freeze` > `glitch` > `drop` > `audio_gap` > `av_desync` > `buffering` > `ok`. 수는 따로(02 7 `pdr`·`pau`).
- **채우는 값(2026-10-10, 20장 GAP-152):** mpv(기본) `ok`·`freeze`·`restart`·`none`·`drop`(디코더+화면 출력 단계 버림)·`glitch`. VLC(선택) `ok`·`freeze`·`restart`·`none`·`glitch`, 그리고 통계가 살아 있을 때만(파일·UDP 입력) `drop`·`audio_gap`. **`glitch` = 그 초에 재생기 자기 기록에 디코더 오류 줄이 1개 이상**(mpv `Error while decoding frame`, VLC `late video -> dropping frame`·`Could not find ref with POC`), 수는 02 7 `pde`. 패킷이 깨끗해도 화면이 깨질 수 있어(수신 PC가 못 따라감) 이 값이 필요하다. `av_desync`·`buffering`은 아직(P3).

| 오디오 버퍼 부족 표시 | ? | → `audio_gap` |
- 연결: mpv를 `--input-ipc-server`로 띄우고 0.1초 고정 간격으로 `get_property`(요청 번호로 답을 짝지음, 사건은 건너뜀) ✓.
- **구현(2026-10-10, GAP-152, T460 mpv 0.37 ✓):** `--hwdec=vaapi`(Windows `d3d11va`, ◐) **창에 바로**(복사 모드는 가입 때 첫 복사 실패로 하드웨어 디코더를 버림, 15장) + `--vd-lavc-software-fallback=300`(연속 300프레임 실패 뒤에만 소프트웨어 — 하드웨어가 없는 PC). 그룹은 `rtp://@그룹:포트?localaddr=<받는 카드 IP>`로 그 카드에서 가입. `--cache-secs` = S-25. 입력 소켓 버퍼 16 MB(`--stream-lavf-o=buffer_size=16777216`; URL 쿼리 `buffer_size`는 적용 안 됨, ffmpeg 기본 약 384 KB(커널 표시 768 KB)는 UHD 0.17초분이라 시작 때 5,643개 넘침 — 2026-10-10 T460 실측). 진행 = `estimated-frame-number`(보이는 프레임마다 늚, 송신이 멈추면 멈춤 ✓), 버림 = `decoder-frame-drop-count`+`frame-drop-count`(`drop`), 디코더 오류 = 기록 줄(`glitch`), `hwdec-current`는 보고에 함께. **2026-10-23(GAP-180):** 버림은 `pdr`(합)과 그중 디코더 단계 `pdd`로 나눠 적는다(디코더가 못 따라감 ↔ 화면 출력이 늦음을 구분). 기록 줄마다 mpv 시작부터의 시각(`--msg-time`)을 붙이고, 재생이 끝나면 기록(`player.log`)을 지우지 않고 Agent Desktop 폴더의 `player-logs/<작업>.log`로 옮겨 최근 10개만 남긴다(시험 뒤 원인 확인). 소리 끊김 수는 mpv에 없어 `pau` 재지 않음(`null`). 경고만 기록(`--quiet --msg-level=all=warn`).
- 주의(공식 설명 ✓): `estimated-vf-fps`는 프레임 버림이 있으면 부정확할 수 있음 → 단독 판정에 쓰지 않고 보조로만.

## 3.4 재생기와 무관한 감지: 영상 속 표식 (권장)
사전 준비 단계(iptv 1장 4.1)에서 시험 영상에 **기계가 읽는 표식**을 넣는다.
- 화면 구석에 **프레임 번호**(사람이 읽는 숫자 + 기계가 읽는 흑백 막대 코드)를 새겨 넣는다. **방법 확정 ✓(2026-09-25 실측, V12):**
  - 칸 크기 c = 2 × round(영상 높이 ÷ 144) (UHD 30 px, HD 16 px). **왼쪽 아래**, 왼쪽·아래에서 한 칸 띄움, 한 줄 22칸(UHD 660 px = 폭의 17%).
  - 칸 순서: 흰·검(시작 기준) · 채널 2비트 · 프레임 번호 16비트(큰 자리부터) · 검·흰(끝 기준). 1 = 흰, 0 = 검.
  - 프레임 번호 = 파일 안 번호(0부터, 10분 파일은 0~17999). 파일 반복 지점에서 0으로 돌아가는 것은 정상(반복 길이는 설명 파일에).
  - 사람이 읽는 숫자(`drawtext %{frame_num}`, 글자 2c)는 막대 바로 위.
  - 만들기: ffmpeg `color` 작은 화면 + `geq`(프레임 번호 N으로 칸 밝기 계산) → `overlay` → **`addroi`(막대 영역 qoffset −1 = 최고 화질)**. ROI 이유(2026-09-26 W-7, 20장 GAP-77): CI에서 x265가 B-프레임의 막대를 **뒤 프레임에서 복사**해 3번 프레임에 4번 표식이 찍힘 — 막대 칸을 늘 제대로 부호화하게 한다(B-프레임은 실제 방송처럼 유지). 읽기: 칸 가운데 밝기를 시작 기준 흰·검의 가운데 값과 비교. 기준 칸 대비가 64단계 미만이거나 끝 기준이 안 맞으면 "읽을 수 없음"(추측하지 않음).
  - 실측: HD 3초 90프레임 인코딩 후 전부 정확히 읽음, 화면 숫자와 일치. 작게 줄인 캡처(640×360, 칸 약 5 px)에서도 읽혀야 한다(자동 시험).
- 증거 캡처(F23)·주기 캡처에서 표식을 읽으면:
  - 번호가 안 바뀜 → `freeze` (재생기가 뭐라고 하든)
  - 번호가 건너뜀 → `drop` (몇 프레임인지 정확히)
  - 번호가 되돌아감·반복 → 재생기 이상
- 사진에 찍힌 번호로 **"정확히 몇 번째 프레임에서 깨졌는지"**가 증거에 남는다.
- 선택: 소리에도 일정 간격 짧은 신호음을 넣어, PC에서는 재생 소리를 되받아(시스템 소리 녹음) 끊김을 잰다(태블릿은 어려움 → 재생기 값만).
- 표식은 **작고 구석에** 두어 블록 깨짐 감지(`blockdetect`)가 표식 영역을 제외하게 한다.

- **구현(2026-10-23, 앱 1단계):** 재생기는 계측과 **같은 소켓**의 TS를 받는다(앱 안 파이프, 받는 스레드는 절대 기다리지 않음 — 재생기가 늦으면 가장 오래된 조각을 버리고 `/v1/status`의 `pipe_overflow`로 셈, 망 손실이 아님). 재생기는 **서비스가 가진다**: 화면 회전·크기 변화·화면 나감은 그림만 붙였다 뗀다. 버퍼 = `POST /v1/receiver/start`의 `buffer_ms`(300~5,000, 없으면 S-25 1,000 ms), 재생 끔 = `play: false`(S-49). 1초 줄에 `pb`·`pdr`·`pau`·`pfs`·`prs`·`pde`를 PC와 같은 뜻으로 넣는다: 멈춤 = 새 프레임 0.5초 없음(`VideoFrameMetadataListener`), `pde` = `onVideoCodecError` 수, `pau` = `onAudioUnderrun` 수, 오류 뒤 0.5초에 다시 준비(`prs`).

## 3.6 판단 기준 (기본값, S-설정으로 조정 가능한 것만 조정)
| 종류 | 기준 |
|------|------|
| `freeze` | 새 프레임 없음 ≥ 0.5 초 (표식 번호 기준 우선) |
| `drop` | 1초에 1프레임 이상 버림 |
| `audio_gap` | 오디오 버퍼 부족 1회 이상 |
| `av_desync` | |차이| > 100 ms가 2초 이상 |
| `glitch` | 디코더 오류 1회 이상 또는 블록 깨짐 정도 > 기준(F23, P1에서 값 결정 ?) |
- **안정화(2026-10-10, GAP-152):** 첫 화면 뒤 `pb` 2초 연속 `ok`(늦어도 첫 화면 5초 뒤)여야 안정화가 끝난다(05 2.1-2). 채널 전환 시간 `zp`(첫 패킷 → 정상 재생)는 그대로 첫 화면 기준.
- **mpv(2026-10-10):** 같은 0.1초 고정 간격으로 IPC를 읽고, `freeze` = `estimated-frame-number`가 **0.5초** 넘게 안 늘 때(하드웨어 디코딩이어도 됨, CPU 필터 없음). `glitch` = 그 초 기록에 디코더 오류 줄 1개 이상(가입·채널 전환 직후 오류는 안정화 구간이라 판정 밖). `none`·재시작 규칙은 VLC와 같다.
- **P2 VLC(2026-09-25):** 자체 보고를 **0.25초 고정 간격**(앞 읽기가 끝난 뒤 쉬는 방식이 아니라 정해진 시각마다)으로 읽고, `freeze`는 **마지막으로 새 그림이 나온 뒤 지난 시간**으로 정한다: 통계가 살아 있으면 표시된 프레임 수(`displayedpictures`, 프레임마다 늚)가 **0.5초** 넘게 안 늘 때, 아니면 scene 프레임 번호가 **1초** 넘게 안 늘 때. 두 판정 사이에 시작해 끝난 멈춤도 그 초의 `freeze`로 센다(2026-10-04 첫 기준선 실기, 20장 GAP-114: 예전 "1초 쉬고 읽기 + 지난번과 같은 번호면 멈춤"은 읽기 주기 1.023초와 판정 1초가 어긋나 **약 43초마다 가짜 멈춤 1초**를 만들었다 — 유선·무선·공유기 유무와 상관없이 같은 주기). 첫 화면은 시작 후 **10초** 안(RCV-019, 안정화 조건 `first_frame`). 표시 프레임이 **10초 넘게** 안 늘거나 재생기가 죽으면 `none` → 종료 확인 후 다시 띄움(RCV-020, 한도는 RCV-003의 시간당 3회, 넘으면 `none`으로 두고 Problems).
- 모든 재생 이상은 같은 시각(±2초) 패킷 이상과 대조해 **Router 쪽 / Receiver 쪽**으로 분류(05-standards 4.6.2, 규칙 R-08).
- **안정화 구간**(첫 화면 전, 채널 전환 직후)의 재생 이상은 판정·분류에서 제외하고 Start-up 기록에만(05-standards 2.1-2).
