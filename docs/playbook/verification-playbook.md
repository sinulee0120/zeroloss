# 검증 플레이북 (AI와 함께 만드는 모든 툴에 공통)

> 목적: AI(바이브 코딩)로 만든 소프트웨어가 **사람의 예측 못 한 조작, 랜덤 상황, 장시간 운영**에서 꼬이지 않게 하는 검증 방법 모음.
> ZeroLoss에서 시작했지만 **다른 툴 개발에도 그대로 쓴다.** 새 프로젝트의 CLAUDE.md에서 이 파일을 가리킨다.

## 0. 왜 필요한가 (근거)
| 근거 | 핵심 |
|------|------|
| Yuan et al., *Simple Testing Can Prevent Most Critical Failures*, OSDI 2014 | 치명적 장애의 **92%가 "치명적이지 않은 오류를 잘못 처리"**해서 생김 → 예외 경로를 시험해야 한다 |
| Liu et al., *Debt Behind the AI Boom*, 2026 (30만 AI 커밋 분석) | AI 커밋의 15% 이상이 문제를 넣고, **22.7%는 끝까지 안 고쳐짐**. 대표 오류: 정의 안 된 변수, 주변 맥락과 불일치 |
| Chong et al., *AI-Generated Code Considered Harmful*, 2024 | AI 코드는 **방어 코드가 빠지기 쉽고**(모든 입력이 정상이라고 가정), 퍼징에서 멈춤·충돌이 더 많음. **"고쳐 달라"는 반복이 다른 곳에 새 문제를 넣기도** 함 |
| Fu et al., Copilot 코드 보안 약점 연구, TOSEM | 실제 GitHub의 AI 코드 약 30%에 보안 약점 |
| Perry et al., 2023 사용자 연구 | AI를 쓴 사람이 **덜 안전한 코드를 쓰면서 더 안전하다고 믿음** → 눈으로 "괜찮아 보임"은 검증이 아니다 |
| 이번 시안 검증에서 직접 확인 | 무작위 섞어 누르기로 3건 발견: 버튼 상태 초기화 오류, 시험 중 열린 설정 창, **빠른 연타로 같은 항목 5번 추가** |

**결론:** AI가 만든 코드는 "읽어 보니 맞다"로 끝내지 않는다. **자동으로, 반복해서, 무작위로, 예외 경로까지** 돌려서 불변 조건이 깨지지 않음을 보여야 완료다.

## 1. 기법 목록 (언제 무엇을 쓰나)
| 기법 | 한 줄 설명 | 잘 잡는 것 | 출처·도구 |
|------|-----------|-----------|-----------|
| **불변 조건(Invariant)** | "항상 참이어야 하는 것"을 코드로 적고 매 단계 확인 | 상태 꼬임, 화면·실제 불일치 | 모든 기법의 판정 기준 |
| **속성 기반 시험** | 입력을 무작위로 수천 개 만들어 속성이 유지되는지 | 경계값, 드문 입력 | QuickCheck(Claessen & Hughes, ICFP 2000), Python **Hypothesis** |
| **상태 기계(모델 기반) 시험** | 가능한 동작을 무작위 순서로 이어 붙이고, 간단한 "모델"과 실제 결과를 비교 | 순서 의존 버그, 상태 전이 오류 | Hypothesis `RuleBasedStateMachine`, QuickCheck state machine |
| **몽키 / 섞어 누르기** | UI를 무작위·연타·지연 섞어 조작하며 불변 조건 확인 | 버튼 상태 오류, 중복 실행, 팝업 폭탄 | Android Monkey, Sapienz(Mao et al., ISSTA 2016) |
| **결정적 시뮬레이션(DST)** | 시계·네트워크·난수를 가짜로 바꿔 한 프로세스에서 결정적으로 재현. **시드만 있으면 같은 버그 재현** | 동시성·타이밍·경쟁 상태 | FoundationDB(SIGMOD 2021), Antithesis, TigerBeetle |
| **스웜 시험** | 실행마다 켜는 기능·장애 종류를 무작위로 바꿔 다양성 확보 | 기능 조합 버그 | Groce et al., ISSTA 2012 (FoundationDB도 사용) |
| **버그 부추기기(Buggify)** | 코드 곳곳에 "가끔 일부러 늦게·실패하게" 하는 지점을 시험 모드에서만 켬 | 드문 예외 경로 | FoundationDB |
| **장애 주입 / 카오스** | 프로세스 kill, 네트워크 끊김·지연, 디스크 가득 등 실제 사건을 넣고 "정상 상태 지표"가 유지되는지 | 복구·원복·데이터 보존 | Basiri et al., *Chaos Engineering*, IEEE Software 2016 |
| **쌍별(조합) 시험** | 옵션이 많을 때 모든 값 쌍이 한 번씩 만나도록 시험 세트를 자동 생성. 전부 조합하지 않아도 대부분의 조합 결함을 잡음 | 옵션 충돌, 설정 조합 버그 | NIST 조합 시험(Kuhn et al.), PICT·allpairspy |
| **메타모픽 시험** | 정답을 모를 때 "입력을 이렇게 바꾸면 결과는 이렇게 바뀌어야 한다"는 관계로 확인 | 계측·계산 오류 | Chen et al., ACM CSUR 2018 |
| **차분(비교) 시험** | 같은 입력을 두 구현(또는 두 버전)에 넣어 결과 비교 | 회귀, 계산 차이 | R2Z2(ICSE 2022) |
| **화면 배치 실패 자동 검출** | 요소 겹침·틀 밖 넘침·잘림을 DOM/화면에서 자동 확인 | 글자 겹침, 해상도별 깨짐 | ReDeCheck(ISSTA 2017), Viser·VERVE(ICST 2019, STVR 2021) |
| **시각 회귀 시험** | 화면 캡처를 기준 이미지와 비교 | 모르는 사이 바뀐 화면 | 스크린샷 비교 |
| **변이 시험** | 코드에 일부러 작은 버그를 넣고 시험이 잡는지 → **시험 자체의 품질** 측정 | 약한 시험(검사 안 하는 시험) | mutmut(Python), PIT(Java) |
| **정형 명세(선택)** | 핵심 프로토콜을 TLA+ 등으로 모델 검사 | 설계 수준 경쟁 상태 | Newcombe et al., AWS, CACM 2015 |

## 2. 규칙 (프로젝트마다 적용)
1. **완료 = 자동 시험 통과.** AI가 "고쳤다"고 해도, 해당 불변 조건 시험이 통과해야 완료. 읽어서 확인하는 것은 검증이 아니다.
2. **불변 조건부터 쓴다.** 화면·상태·데이터에 대해 "항상 참"인 것을 먼저 목록으로 만든다(예: 버튼 글자 = 실제 상태, 모달 최대 1개, 같은 작업 동시 1개, 요약 숫자 = 다시 계산한 값, 타이머는 상태당 1개).
3. **몽키 회귀는 필수:** UI가 있는 모든 화면에 섞어 누르기 + **연타(같은 버튼 2~5번 즉시)** + 짧은/긴 대기 섞기. 고정 시드 목록 + 매번 새 무작위 시드.
4. **실패한 시드는 영구 회귀 시험으로:** 몽키가 버그를 찾으면 그 시드·단계를 고정 시험으로 추가한다. 같은 버그가 다시 들어오지 않게.
5. **예외 경로를 일부러 연다:** 버그 부추기기 스위치(시험 빌드 전용)로 늦게·실패하게 만들어 복구·원복·알림이 동작하는지 본다.
6. **시간·난수·네트워크를 갈아 끼울 수 있게 설계:** 시계와 난수를 주입 가능하게 만들면 100시간짜리 상황을 몇 초에 재현할 수 있다(DST의 핵심).
7. **서로 살아 있는지·상태가 맞는지 상시 확인:** 여러 프로그램(노드)이 있으면 "A가 보는 B의 상태 = B의 실제 상태"를 불변 조건으로 두고, 무작위 kill·지연·끊김 중에도 일정 시간 안에 맞춰지는지 확인.
8. **설치·제거·업데이트도 몽키:** 중간 취소, 잘못된 입력, 같은 설치 두 번 실행, 설치 중 전원 차단, 제거 중 설치, 잘못된 비밀번호 반복 → "설치 전과 같거나 완전히 설치됨" 둘 중 하나만 허용.
9. **화면 배치 자동 검사:** 모든 화면을 해상도·배율별로 캡처하고 겹침·넘침·잘림·대비를 자동 판정.
10. **시험을 시험한다:** 변이 시험으로 가끔 시험 품질을 잰다. 버그를 넣어도 통과하는 시험은 고친다.
11. **AI에게 고치게 할 때:** 한 번에 한 문제, 수정 후 **전체 회귀**(주변 파일에 새 문제가 들어오는 일이 연구로 확인됨). 고친 코드 설명보다 시험 결과를 믿는다.

## 2-1. 옵션 규칙
- 기본값만 시험하지 않는다. **모든 설정의 목록 + 조합 규칙표**를 만들고, 조합 규칙 전부 + 쌍별 조합 시험을 돌린다. 화면과 CLI가 같은 검사를 쓴다.

## 3. 불변 조건 예시 (UI 앱)
- 시험 상태별 버튼 글자·활성 여부 = 조작 상태표
- 모달(작업을 막는 창) 동시 최대 1개
- 같은 작업(시작, 추가, 설치, 보고서 생성) 동시 최대 1개 — 연타해도 1번만
- 상태가 대기가 아니면 설정 창·장비 설정 창 닫힘
- 대기·장애 상태에서 도는 타이머 0개, 그 외 상태당 최대 1개
- 화면의 요약 숫자 = 현재 보기 조건으로 다시 계산한 값
- 선택된 항목은 항상 보이고, 사라지면 이유 알림
- 오류가 나면 반드시 사용자에게 What/Why/Fix 표시(조용한 실패 없음)
- 글자가 틀 밖으로 나가거나 겹치지 않음, 대비 기준 충족

## 4. 불변 조건 예시 (여러 노드 시스템)
- 각 노드: 살아 있음(heartbeat) + 상태가 지휘 노드의 기록과 N초 안에 일치
- 무작위 kill·지연·끊김 뒤: 안전 정지 → 원복 → 깨끗한 상태 점검 통과
- 재시작된 노드는 옛 명령을 실행하지 않음(세대 번호)
- 측정 자료는 어떤 장애에서도 잃지 않음(최대 손실 한도 명시)
